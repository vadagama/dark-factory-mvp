# План закрытия T043 — E2E-пилот (операционный)

Рабочий план доведения T043 до DoD. Отвечает на вопрос «что конкретно делать, в каком
порядке и чем это доказывается».

- Основание: `specs/001-dark-factory-mvp/tasks.md` (T043), `docs/plan-t043-e2e-pilot.md`
  (объём инкрементов), `docs/t043-pilot-journal.md` (живой ход пилота).
- Живой срез ранов и продукта — 2026-09-18 (см. §2); перед стартом каждой фазы срез
  перепроверять (`deploy/local/pilot/increment-1.sh status`).
- Роли: `dark-factory` (оркестрация, план, отчёт), `develop` (код), `ci-cd` (ветка, коммиты,
  MR), `quality` (независимая проверка); решения и гейты — оператор (ADR-011).
- Merge в `main` — только человек; агенты не мержат.

## 1. Что считается закрытием (DoD)

Цель T043: 10 реальных задач (5 quick R1 + 5 standard R2) по сквозному сценарию
`intake → SDD → реализация → MR → CI/review → merge`, метрики vision §7 / FR-024,
журнал отклонений, отчёт по SC-001…SC-008.

**Уточнено (2026-09-18, решение оператора D9 — стабилизация одной формы).** Первый проход
сводится к **одной форме изменения — standard-R2** и гоняется в ручном режиме до чистого
сквозного прогона: K = 1 (второй — по отдельной команде оператора). Основание: наблюдённые
дефекты сквозные (B1, B2, B6, B7, B8), а не задачные; десять параллельных изменений давали шум;
метрика vision §7 считает **запуски** («≥ 7 из 10 запусков»), а не задачи. Матрица
5 quick + 5 standard становится **следующей фазой**; её отсутствие в отчёте SC называется явно (§8).

| Критерий DoD | Как проверяем | Evidence |
|---|---|---|
| **D9:** один чистый сквозной прогон standard-R2 до merge | `review_verification` = `succeeded`; ноль ручных правок артефактов агента; вмешательств человека не-approvals ≤ 1; `blocked` по дефекту конвейера — 0; rework ≤ 1; гейты `passed` на текущем head SHA | журнал + `run status` + run records |
| Матрица 5 quick + 5 standard (≥7/10) — **следующая фаза** (D9), не первый проход | если оператор решит добирать — рецепт §7 по формам; иначе фиксируется как ограничение объёма | журнал + трекер |
| Метрики FR-024 (стоимость с учётом попыток, first-pass, раунды rework, время до принятого MR, ручные вмешательства) | свод по всем ранам (см. §8) | таблица в отчёте |
| Отчёт по SC-001…SC-008 | по каждому SC — вердикт и evidence (см. §9) | `docs/report-t043-sc.md` |
| Журнал отклонений | каждая находка/решение — запись с датой и следствием | `docs/t043-pilot-journal.md` |
| Git-цикл: отдельная ветка, Conventional Commits, MR, merge — человек | все изменения T043 в PR | PR-история |

**Сужение объёма (вариант C, решение оператора, 2026-09-18).** Инкремент 1 покрывает путь до
`merge` (`review_verification`); промоушен/`release` (`image → GitOps → dev → smoke`) **вынесен**
из объёма — модель промоушена не описывает multi-image продукт (TD-031). Далее по тексту
«покрыто до merge» = `review_verification` завершена; парковка рана на `release` — ожидаемое
следствие сужения, а не дефект пилота.

## 3. Критический путь

1. **W1 — фикс B1** (без него 5 standard-задач закрыть нельзя, см. §5).
2. **W2 — пере-intake p01** (лечит B3).
3. **W3 — стабилизация одной формы standard-R2** (§7.2, решение D9): ручные прогоны до чистого
   сквозного прогона (K = 1); добор матрицы quick/standard — следующая фаза.
4. **W4/W5 — метрики и независимая проверка** (параллельно W3).
5. **W6 — отчёт SC-001…SC-008, обновление трекера и TD, финальный MR.**

Статус (2026-09-18): W1 закрыт (фикс B1 — MR #103 в `main`), W2 закрыт (пере-intake p01 —
MR #104 в `main`); приняты D6–D9 (журнал). Изменение объёма (D9) затрагивает только W3.

Почему B1 обязателен и почему его нельзя обойти порядком шагов:

- для R2 человеческий гейт стадии `planning` — `Gate.PLANNING`
  (`rules/gates.py`: `RISK_HUMAN_GATES[R2] = {UI, PLANNING}`, `required_human_gates`);
- чисто человеческая стадия резолвится только наблюдаемым APPROVED-решением, чей гейт входит
  в человеческий набор (`orchestration/stages/gates.py::gate_resolved`), и точка
  `solution` привязана к паре `(PLANNING, Gate.PLANNING)`
  (`orchestration/policy/risk.py::CONTROL_POINT_BINDING`);
- ревью plan-CR провайдер отдаёт с гейтом `Gate.REVIEW` (`runtime/facts.py::_approvals`),
  поэтому ни wait не резолвится, ни точка не закрывается;
- операторский `pilot_api.py approve` (таблица `decision`) драйвером **не читается**:
  `advance_run` принимает `human_decisions` параметром с дефолтом `()`, а CLI его не
  передаёт (`cli/runner.py::_advance_in_session`). Решения наблюдаются только из SCM.

Следствие: контракт нужно утверждать **до** резолва перехода planning→construction (иначе B2),
но ровно тогда R2-план требует человеческого гейта — то есть без фикса W1 deadlock.

## 5. Работы

### W1. Фикс B1: риск-осознанный маппинг гейтов в `ScmFactsProvider`

- Роль: `develop`; ветка `fix/t-043-risk-aware-gate-mapping`; MR — `ci-cd`.
- Файл: `src/dark_factory/runtime/facts.py`. Метод `ScmFactsProvider.__call__` уже получает
  `run`, но не использует; `_approvals` (строки ~103–136) считает гейт как
  `HUMAN_GATES & required_gates(Route.STANDARD, stage)` с фолбэком `Gate.REVIEW`.
- Суть правки:
  1. в `__call__` вычислить эффективный класс рана:
     `effective_change_risk_class(run.implementation_contract, run.route)`;
  2. передать `route=run.route` и `risk_class` в `_observe` → `_approvals`;
  3. в `_approvals` выбирать гейт из `required_human_gates(route, stage, risk_class)`
     (первый по значению при непустом наборе), фолбэк `Gate.REVIEW` — для гейта
     авторизации merge (стадия `review_verification`).
- Совместимость: `runtime/` — composition root, импорт core разрешён (ADR-024 п.5);
  поведение `specification`/`review_verification` не меняется (их человеческий набор тот же);
  `quick`-маршрут не затрагивается (у него нет `ui` и `planning`-гейта человека для R1);
  ветка `observation.merged` в `gate_resolved` срабатывает раньше проверки гейтов, поэтому
  merge-пути не регрессируют.
- Тесты (обязательны, в том же PR):
  - R2 + `planning`: ревью plan-CR → решение с `gate=Gate.PLANNING`; `gate_resolved` = True;
    `missing_control_points` для R2 (stage `planning`) не содержит `solution`;
  - R1 + `planning`: поведение прежнее (фолбэк `Gate.REVIEW`);
  - R1/R2 + `specification` и `review_verification`: гейты маппятся как раньше;
  - регрессия: `merged`-наблюдение резолвит стадии независимо от маппинга.
- Критерий приёмки: unit-тесты зелёные; полный `pytest` зелёный; `ruff check` + `ruff format
  --check` + `mypy` чистые (регламент репозитория); живая проверка — p06: после approving review
  на plan-CR `advance` резолвит planning и ран уходит в construction.
- Если D1 = (b) (сужаем объём): W1 не выполняется, вместо неё — запись в
  `docs/tech-dept.md` (TD на B1) и явная фиксация в отчёте, что R2-контрольные точки пилотом
  не валидировались.

## 7. Рецепт прогона одного изменения

Все команды — через драйвер (`deploy/local/pilot/increment-1.sh`); exit 10 = waiting,
20 = blocked — норма. Гейты (approve/merge) подаёт **только человек**; решение выражается
review/merge в GitHub (не через `pilot_api.py approve` — см. §3). Целевая форма первого
прохода по D9 — §7.2 (standard-R2); §7.1 остаётся для следующей фазы.

### 7.1 Quick-R1 (p04, p05, p01b)

1. `advance <id>` — спецификация/планирование агентной стадией (LLM) → `waiting` (CI).
   Для p01b сначала спецификация: human-гейт решается approving review или merge спека-CR.
2. Дождаться зелёного CI на CR стадии.
3. `advance-contract <id> contracts/<id>.contract.json --approve` — контракт прикреплён и
   утверждён; в этом же вызове стадия планирования может резолвиться (R1 — машинный гейт).
   **Порядок обязателен:** контракт до резолва перехода, иначе retry перезапустит planning (B2).
4. `advance <id>` — construction (LLM) → `waiting` (CI).
5. Дождаться CI → `advance <id>` — construction `succeeded` → `review_verification` (pending).
6. `advance <id>` — review-агент (LLM) → `waiting`.
7. Оператор: approving review на итоговом SHA + merge CR.
8. `advance <id>` — `review_verification` `succeeded`; далее ожидаемая парковка на `release`.

### 7.2 Standard-R2 (p06…p10)

Отличие — шаги 3–4:

3. `advance-contract <id> contracts/<id>.contract.json --approve` — контракт объявляет R2,
   эффективный класс поднимается → стадия planning становится **человеческой** → этот вызов
   вернёт `waiting` (replay).
4. Оператор: **approving review на plan-CR** (не merge) — это и есть решение точки `solution`.
5. `advance <id>` — planning резолвится, точка `solution` закрывается → construction (LLM).

Далее шаги 5–8 как в 7.1. Внимание: review должен стоять на текущем head plan-CR — биндинг
контрольной точки идёт по SHA, на котором прошёл человеческий гейт (ADR-009 п.7);
`dismiss_stale_reviews` на защищённой `main` снимает устаревшие ревью при новом коммите.

## 9. Риски

| Риск | Эффект | Снятие |
|---|---|---|
| Фикс B1 меняет маппинг гейтов шире, чем ожидалось | регресс резолюции wait | тесты на R1/R2/quick + `specification`/`review_verification`; `quality` проверяет негативные кейсы |
| Параллельные изменения трогают один файл → конфликтующий CR без CI (тупик) | ран не резолвится | сериализовать изменения по файлам (журнал, вариант 3) или merge-forward вручную (считается как ручное вмешательство) |
| Оператор мержит plan-CR вместо approving review (R2) | точка `solution` не закрывается (`merged` не создаёт решений) | в рецепте §7.2 явно: review, не merge |
| Ревью поставлено не на текущий head | точка не биндится по SHA | ставить review после последнего коммита стадии; проверять SHA в `run status` |
| Повторные `advance` на `blocked`-стадии выжигают LLM | расход | `advance-all` не использовать; по одному вызову с наблюдением |
| `usage` теряется при supersede | метрика стоимости занижена | явно в отчёте; кандидат в TD (W4) |
| Долгие прогоны standard-задач (LLM + CI) | сроки | сначала quick (банкуют счёт), standard — по минимальному набору |
