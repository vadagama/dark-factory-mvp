## 1. Резюме (Executive Summary)

**Software Dark Factory** — конвейер разработки ПО, в котором специализированные агентные роли (Product → Design/Architect → Develop → Quality → CI/CD → Operation) превращают короткое описание задачи в работающее, протестированное, задокументированное изменение, доведённое до merge и деплоя в dev-контур, с минимальным участием человека. Участие человека избирательно по фазам (ADR-018): **Human-in-the-loop** — на discovery/design (требования, UX/UI, значимые архитектурные решения) и на merge; **Human-off-the-loop** — на реализации; **Human-on-the-loop** — на планировании и проверках качества. Человек определяет, что и в каких границах строить, и управляет через гейты и approval'ы, а не через диалоги с агентами; фабрика автономно решает, как довести согласованное изменение до готового к merge состояния и dev-контура.

MVP подтверждает **один сквозной сценарий** на одном пилотном продукте и одним оператором: инициатива → спецификация (SDD-модель: единый OpenSpec, профиль `product-sdd`, ADR-017) → реализация агентами в изолированном worktree → change request (PR/MR) → CI + независимый Quality review → ограниченный rework (≤3 циклов) → merge по политике → immutable OCI-образ → GitOps MR → Argo CD → dev-деплой → smoke → evidence. Каждое изменение оставляет проверяемую цепочку доказательств (спека, diff, тесты, findings, usage, бюджет, статус деплоя).

Ключевая ценность для компании SMALL: рост скорости и объёма разработки **без роста команды**, исполнение корпоративных стандартов кодом (гейты, а не договорённости), полная трассируемость «требование → код → тест → релиз». Ключевая метрика — **стоимость принятого изменения** (LLM-токены + человеко-часы на одно слитое изменение) и её динамика.

Целевой контур MVP: модульный монолит **Python** (Factory Core), PydanticAI как первый harness-адаптер, Pydantic Graph только внутри стадии, SC/CI-провайдер как внешний control plane (код, change request, CI) через адаптеры — MVP стартует на GitHub, GitLab вторым (ADR-019), PostgreSQL как state store фабрики (состояние выполнения, leases, outbox, очередь задач), локальный Kubernetes в Docker Desktop + Helm + Argo CD для доставки, Console (React + FastAPI) для контроля. Долгоживущая истина — в Git/MR/CI/run-records; исполнение — ephemeral job pods + идемпотентный reconciler CronJob, без постоянного воркера; Temporal в MVP не используется (подключение позже через WorkflowEnginePort). Решения по всем спорным вопросам — в ADR-002…ADR-019 (см. plan.md §5).

## 2. Конкурентный контекст

Сводка конкурентного анализа:

| Игрок | Что даёт | Чего не хватает / наш ответ |
|---|---|---|
| EPAM DMTools (+dmtools-agents, MIT) | Операционный цикл задача→PR→review→rework→merge, recovery, review-контракты | Привязка к Jira/GitHub, JS; берём ~70% процессных идей как референс |
| Factory.ai (droid-action, factory-plugins) | CI-триггеры агента, plugin marketplace, runtime-enforced политики | Не управляет полным SDLC, vendor lock-in; берём паттерны: event-driven fast jobs, capability-пакеты, технические ограничения |
| Warp, Devin, OpenHands, GitLab Duo, GitHub Agentic Workflows | Автономный coding agent / CI-интеграция | Нет слоя спецификации, независимой приёмки, корпоративных стандартов и GitOps-доставки как системы |
| StrongDM (Digital Twin) | Независимая приёмка результата вне зоны агента | Взято как принцип: Quality — отдельный контекст, verifier един |
| 8090 | SDD + knowledge graph | SDD-слой у нас — OpenSpec с профилями `factory-sdd` / `product-sdd` (ADR-017); knowledge graph (OKF) — Out of Scope MVP |
| Spotify Honk, Stripe Minions, OpenAI/Anthropic harness (кейсы) | Единый verifier, сохраняемое состояние, изолированные окружения — работают на 1000+ PR | Подтверждение реализуемости; масштаб — за горизонтом MVP |

**Вывод:** рыночные инструменты закрывают «агент пишет код в CI», но не закрывают управляемый полный SDLC с корпоративными стандартами, спецификацией до кода и проверяемой доставкой. Ниша SMALL — управляемый Change end-to-end на собственных продуктах, с открытым стеком и без vendor lock-in.

## 3. Новые функции (Features)

### 3.1. Сквозной автономный конвейер изменения (Change Flow)

- **Проблема:** сейчас каждое изменение требует полного ручного цикла; агентные инструменты ускоряют лишь фрагменты.
- **Описание:** оператор заводит инициативу (Tracker/Console/CLI); фабрика профилирует риск, строит план стадий, исполняет их агентами, проходит гейты и доводит изменение до dev-деплоя. Режимы: «с согласованиями» и «автономно до MR». Лимиты: ≤2 параллельных агентов, 1 тяжёлый job, 3 раунда rework, бюджет на запуск.
- **Конкуренты:** частично — Factory.ai/Warp (только CI-фрагмент); полный цикл не предлагает никто из исследованных.
- **Приоритет:** P0.
- **Слой / Модуль:** Factory Core — Changes, Orchestration.
- **Зависимости:** 3.2, 3.3, 3.4, 3.5, 3.6.

### 3.2. Спецификация до кода: SDD-слой на OpenSpec

- **Проблема:** агенты, пишущие код «из тикета», дают нестабильный результат; бизнес-правила и AC теряются в диалогах.
- **Описание:** SDD-слой конвейера — единый OpenSpec с профилями `factory-sdd` / `product-sdd` (ADR-017): граф артефактов изменения (proposal → spec deltas → design → test plan → tasks → evidence → verification) отображается на стадии Flow (Specification, Planning, Construction). Spec Kit (ADR-001, `/speckit-*`) обслуживает bootstrap-фазу до контрольной точки T-020; далее — только OpenSpec, импорт legacy — через `SpecKitAdapter`. Гейт спецификации — машинно проверяемые AC и трассировка поверх нормализованного контракта; наличие артефакта не равно пройденному гейту, свободный текст агента не является контрактом. Уровни входа L0–L4 (Idea → Spec Ready).
- **Конкуренты:** 8090 (SDD+graph); у остальных нет формализованного контракта изменения.
- **Приоритет:** P0.
- **Слой / Модуль:** Factory Core — Context + SDD-интеграция; артефакты — `openspec/` репозитория продукта (до T-020 — `specs/` bootstrap-фазы, ADR-017).
- **Зависимости:** 3.1.

### 3.3. Агентные роли и Harness

- **Проблема:** один «универсальный агент» не даёт ни качества, ни безопасности полномочий.
- **Описание:** 9 ролевых профилей (Product Kevin, Design Bob, Architect Stuart, Infrastructure Dave, Security Mel, Develop Carl, Quality Phil, CI/CD Tim, Operation Jerry) — каталог, не 9 процессов. Flow подключает роли по маршруту изменения (quick/standard). Первый vertical slice: **Product → Develop → Quality**. Исполнение — через HarnessPort; первый адаптер PydanticAI; типизированные TaskEnvelope/AgentResult/Finding/GateResult.
- **Конкуренты:** dmtools-agents (развиваем идею типизированных операций), Factory.ai (проприетарный droid).
- **Приоритет:** P0 (ядро из 3 ролей); полный каталог — P1 (см. 3.9).
- **Слой / Модуль:** Factory Core — Agents, ports/adapters.
- **Зависимости:** 3.1.

### 3.4. Независимая приёмка и bounded rework

- **Проблема:** самооценка агента не является доказательством качества; бесконечные циклы «исправь ещё раз» сжигают бюджет.
- **Описание:** Quality-роль работает в чистом контексте от закреплённой спецификации, актуального diff и evidence (не наследует контекст Develop). Findings — структурированные (severity, evidence, category), rework ограничен 3 циклами и стоп-условиями (budget, конфликты требований, повторяющиеся ошибки → Blocked с диагностикой человеку).
- **Конкуренты:** StrongDM (Digital Twin), кейс Spotify Honk (единый verifier) — принцип подтверждён, реализаций в открытых стеках мало.
- **Приоритет:** P0.
- **Слой / Модуль:** Factory Core — Quality, Agents.
- **Зависимости:** 3.3, 3.5.

### 3.5. SC/CI-контур провайдера: change request, CI, merge policy (GitHub → GitLab)

- **Проблема:** нужна детерминированная истина по коду, проверкам и допуску, а не состояние внутри LLM-диалога.
- **Описание:** SC/CI-провайдер — внешний control plane, выбирается **на уровне репозитория** (`gitlab` | `github`); работа через короткоживущие ветки/worktrees + change request — единая модель `ChangeRequestRef` (GitHub PR / GitLab MR, ADR-019). CI запускает агентные стадии (временные job pods) и детерминированные проверки; статусы гейтов — Checks API / pipeline status по итоговому SHA; merge — по политике (human approval в MVP). Аутентификация GitHub — GitHub App с короткоживущими installation tokens и минимальными permissions (рекомендации GitHub). Один run исполняется ровно в одном провайдере; адаптеры проходят единую контрактную тест-сюиту. MVP стартует на GitHub-адаптере, GitLab-адаптер — следующим шагом. CI-событие ускоряет реакцию, но не единственный журнал.
- **Конкуренты:** у всех; отличие — CI как «durable» верхнеуровневый оркестратор через StageResult/NextAction, без отдельного workflow-движка.
- **Приоритет:** P0 (GitHub-адаптер, T-030); GitLab-адаптер — P1 (T-034).
- **Слой / Модуль:** Execution + SC/CI-адаптеры (ports).
- **Зависимости:** 3.1.

### 3.6. GitOps-доставка в dev на локальном Kubernetes

- **Проблема:** деплой должен быть воспроизводимым и подтверждаемым, а «сделал агент» — не равно «работает».
- **Описание:** после merge доверенный job собирает immutable OCI-образ (SBOM, сканы), создаёт GitOps MR; Argo CD синхронизирует `apps-dev`; smoke-проверки дают release evidence; неуспешный smoke не переводит изменение в Released. Контур: Docker Desktop K8s на MacBook 24GB, Helm, self-hosted CI-раннеры в K8s (GitHub Actions runners в MVP; GitLab Runner — T-034), изоляция `factory-runs` (non-root, NetworkPolicy, TTL). Production — Out of Scope MVP.
- **Конкуренты:** внутренняя разработка эквивалентов — руками; у agent-платформ delivery-слоя нет.
- **Приоритет:** P0.
- **Слой / Модуль:** Execution (deployment), dark-factory-gitops / dark-factory-runs.
- **Зависимости:** 3.5.

### 3.7. Console + API: наблюдаемость и контроль

- **Проблема:** человеку нужна одна картина: что происходит, где остановилось, какие решения требуются.
- **Описание:** 5 экранов MVP (список изменений, карточка изменения с evidence, гейты/approvals, бюджеты/лимиты, настройки/профили). Console — проекция источников (Git, MR, CI, run records), не новый source of truth. Режимы «с согласованиями» / «автономно до MR». API (FastAPI) доступен CLI и CI.
- **Конкуренты:** аналоги — панели вендоров; Plane остаётся work management слоем.
- **Приоритет:** P0 (минимум: статусы+evidence+approval через CLI-фолбэк); полный UI — P0/P1 в пределах MVP.
- **Слой / Модуль:** api, console.
- **Зависимости:** 3.1, 3.10 (частично).

### 3.8. Бюджеты, риск-классы и маршрутизация

- **Проблема:** автономность без лимитов денег, времени и риска — неуправляема.
- **Описание:** бюджет-координатор (токены/время на запуск и роль, allowance, exhaustion → Awaiting Decision); риск-классы R0–R4 определяют обязательные гейты и участие человека (4 точки контроля: problem, solution, UX, discovery/release); маршруты quick/standard/auto-merge-after-stats.
- **Конкуренты:** Factory.ai CI Steward (частично, runtime-политики).
- **Приоритет:** P1 (минимальный budget — P0 внутри 3.1).
- **Слой / Модуль:** Factory Core — Orchestration, Policy.
- **Зависимости:** 3.1.

### 3.9. Полный каталог ролей и гейтов

- **Проблема:** UI, архитектура, безопасность, инфраструктура и эксплуатация требуют специализированных проверок.
- **Описание:** подключение Design/Architect/Infrastructure/Security/CI/CD/Operation по риску; 7 гейтов (Specification, Planning, Code, UI, Review, Verification, Release); skills-каталог MVP; engineering pack пилота (React + UI Kit + FastAPI + PostgreSQL).
- **Конкуренты:** плагины Factory.ai; у нас — версиируемые skills/packs в Git.
- **Приоритет:** P1.
- **Слой / Модуль:** Agents, Quality, packs.
- **Зависимости:** 3.3.

### 3.10. Run records и трассируемость evidence

- **Проблема:** «докажи, что изменение корректно и кто решил» — сегодня невозможно.
- **Описание:** каждое изменение — run manifest + StageResult/NextAction + usage + findings + ссылки на MR/pipeline/deploy в репозитории `dark-factory-runs`; корреляция change → run → stage → agent call → CI job → deployment через TelemetryPort (OpenTelemetry). Полная цепочка: требование → спека → задача → коммит → тест → релиз.
- **Конкуренты:** частично у enterprise-платформ; в открытом стеке — нет.
- **Приоритет:** P1 (минимум для P0-сценария — в 3.1).
- **Слой / Модуль:** Factory Core — Changes/Context, dark-factory-runs.
- **Зависимости:** 3.1, 3.5.

### 3.11. Reconcile и самовосстановление

- **Проблема:** рассинхронизации (зависший job, merged MR без завершённого run, потерянные события) ломают доверие к автономности.
- **Описание:** периодический reconcile по StageResult/Git/MR-состоянию; recovery-правила (release lease, restore state, stop дубликатов, эскалация); оповещение webhook'ом как ускоритель.
- **Конкуренты:** dmtools dfManager (референс, переписываем на Python).
- **Приоритет:** P1.
- **Слой / Модуль:** Execution, Orchestration.
- **Зависимости:** 3.5.

### 3.12. Small UIKit и UI-гейты

- **Проблема:** UI, сгенерированный агентом «с нуля», расходится со стандартами и ломается между версиями.
- **Описание:** Small UIKit на React (Radix + shadcn-основa, токены DTCG, patterns, Storybook как живая спека вместо Figma); агент собирает UI из разрешённых блоков; гейты: UIKit-policy (ESLint), stylelint, axe/WCAG 2.2 AA, visual regression (Playwright), E2E. Прототип из UIKit = рабочий код (Figma не нужна).
- **Конкуренты:** нет прямых; self-improvement-контур SMALL.
- **Приоритет:** P1 (для UI-задач пилота; UI pack зафиксирован — ADR-014).
- **Слой / Модуль:** packs (UI), Quality (гейты).
- **Зависимости:** 3.9.

### 3.13. Learning loop: фабрика улучшает себя

- **Проблема:** ошибки агентов повторяются, если знания не возвращаются в конвейер.
- **Описание:** сигнал (finding, инцидент, дорогой run) → eval-case → RuleProposal/SkillProposal → проверка на eval-наборе → MR → независимый review → постепенный rollout. Агент может только предложить; защищённые наборы недоступны изменяющему их агенту. В MVP — минимальный контур (предложения + базовые evals).
- **Конкуренты:** Factory.ai autoresearch (фрагментарно).
- **Приоритет:** P2.
- **Слой / Модуль:** Factory Core — Learning, Evals.
- **Зависимости:** 3.10, 3.9.

### 3.14. Автономный merge/release низкого риска (policy-controlled)

- **Проблема:** 100% ручных approval не масштабируется; 100% автономности — риск.
- **Описание:** после накопления статистики качества (доля успешных auto-runs, escaped defects) политика разрешает авто-merge для R0/R1-изменений с обязательными гейтами; production-релиз — вне MVP.
- **Приоритет:** P2.
- **Слой / Модуль:** Policy, SC/CI-адаптер (T-030/T-034).
- **Зависимости:** 3.8, статистика по 3.10.

### 3.15. Foundation: каталог блоков, scorecards, marketplace packs

- **Проблема:** ценность фабрики растёт, когда стандарты переиспользуются и улучшаются централизованно.
- **Описание:** Factory Packs (UI/backend/standards), каталог версий и совместимости, scorecards adoption/качества, миграционные codemods. В MVP — только каркас packs (engineering pack пилота); развитие — после MVP.
- **Приоритет:** P3.
- **Слой / Модуль:** packs, Console.
- **Зависимости:** 3.9, 3.12, 3.13.

## 4. Улучшения существующих функций

Продукта ещё нет (pre-MVP), поэтому «улучшения» — относительно текущего ручного процесса SMALL и относительно первой итерации самой фабрики:

1. **Постановка задач:** вместо диалогов — структурированный Initiative Brief (L0–L4), фабрика сама проводит уточнение и фиксирует допущения [assumption: принят для пилота].
2. **Code review:** вместо ручного — независимый Quality-агент + человек утверждает merge; ручной review остаётся для foundation-изменений фабрики.
3. **Тестирование:** тесты генерируются из AC спецификации и попадают в CI как детерминированные проверки.
4. **Деплой:** вместо ручных выкладок — GitOps с immutable digest и smoke-evidence.
5. **Знания:** спецификации и решения живут в Git (`openspec/`, ADR; до T-020 — `specs/`), а не в чатах; приёмка изменений фабрики — через тот же MR/CI-процесс.
6. **Event-driven fast jobs** (референс droid-action): мелкие операции (обновить MR description, классифицировать падение теста) — короткими job'ами без полного Change Flow — во второй итерации [P2].

## 5. Не войдёт в эту версию (Out of Scope)

- **Production-релиз и его автоматизация** — только dev-контур; production требует отдельного контура и human approval.
- **Temporal / DBOS, постоянный workflow worker, Kafka** — координация через ephemeral job pods + reconciler CronJob, события — PostgreSQL outbox (ADR-004, ADR-006, ADR-016); SQLite опционально как кэш-проекция Console.
- **Корпоративный observability-стек локально** (Prometheus/Grafana/Loki/Tempo, Sentry), Keycloak/Vault/MinIO/Harbor как обязательные — минимальный bootstrap + OTel-контракт; registry — любой OCI-совместимый.
- **Langfuse как обязательная зависимость** — опциональный адаптер AI-traces.
- **OKF knowledge graph, OpenMetadata, Notion-интеграции** — ландшафтный контекст после MVP.
- **Preview/test/stage-контуры, multi-node, HA** — один K8s-узел, один пилот.
- **Локальная LLM** — внешний LLM endpoint (существующий LiteLLM).
- **Figma и Web Components UIKit** — исполняемая UI-спецификация на Small UIKit + Storybook.
- **Marketplace/packs как продукт, multi-team/multi-tenant, upgrade campaigns, codemods** — после MVP.
- **Автономный production release, Human-off-the-loop полностью** — уровень автономности ограничен гейтами и риск-политикой.
- **Второй SC/CI-провайдер (GitLab) в пилоте, Azure DevOps и другие SCM** — адаптеры вводятся последовательно за портами: пилот на GitHub, GitLab-адаптер (T-034) — следующим шагом (ADR-019); прочие трекеры (кроме одного выбранного) и harness (кроме PydanticAI) — через порты позже.

## 6. Риски и допущения

### Риски

| Риск | Влияние | Митигация |
|---|---|---|
| Качество/стоимость LLM: бесконечный rework, деградация на сложных задачах | Сценарий не доходит до merge; бюджет горит | Жёсткие лимиты (3 rework, budget), стоп-условия → Blocked с диагностикой; evals с 3.13 |

| Лицензия Docker Desktop для корпоративного использования | Юридический/бюджетный риск | Проверка на bootstrap-этапе; запасной вариант — VM (открытый вопрос на ADR) |
| GitLab edition (второй провайдер, T-034): merge train/merged-results требуют Premium/Ultimate | Часть CI-паттернов GitLab-контура недоступна | Критический путь MVP — на GitHub (ADR-019); версию/лицензию GitLab подтвердить перед T-034 |
| SaaS-зависимость пилота от GitHub.com (доступность, rate limits, изменения API) | Остановка конвейера, троттлинг на пиках | GitHub App с минимальными permissions и короткоживущими токенами; идемпотентный reconciler переживает простой API (ADR-006); webhook — только ускоритель; запасной путь — GHES или смена провайдера конфигурацией репозитория |
| Безопасность агентов (prompt injection, неверные side effects) | Утечка секретов, деструктивные действия | Изоляция pods, deny-by-default egress, разделение publisher/finalizer, без merge/deploy credentials у агентов, негативные egress-тесты |
| Внутренние противоречия исходных материалов → разные прочтения у исполнителей | Переделки, споры в конвейере | Данный vision + план + ADR по каждому конфликту (plan.md) до начала кода |
| Автобус-фактор 1 оператора | Остановка при недоступности | Документация bootstrap/воспроизводимость; Console вместо «магии» |
| Расползание скоупа (источник описывает «целевое», не MVP) | MVP не финиширует | Строгое P0 из настоящего документа; остальное — P1–P3/Out of Scope |

### Допущения

- [assumption] Горизонт MVP ≈ 3–3.5 месяца при 2 параллельных потоках (Core/Agents ∥ Delivery/Console) и ~6–7 месяцев при одном исполнителе (оценка plan.md §3, P0); оценки — экспертные, не из документов.
- [assumption] Пилотный продукт — веб-приложение типа «трекер задач» (React + FastAPI + PostgreSQL), как трекер задач (dogfooding); допустим другой продукт SMALL на том же pack.
- Трекер для пилота — Plane (self-hosted, webhook+HMAC); выбор зафиксирован ADR-013, TrackerPort изолирует замену.
- [assumption] GitHub-репозитории пилота доступны (github.com; GHES — запасной вариант), заведение GitHub App и self-hosted runners допустимы политиками компании.
- [assumption] GitLab 16 доступен компании (есть gitlab16-инстанс) — второй SC/CI-провайдер (ADR-019, T-034); лицензии достаточно для MVP-функций GitLab-контура (без merge train).
- [assumption] LLM endpoint через существующий LiteLLM доступен, квоты/бюджет токенов выделены.
- UI pack пилота — Small UIKit на React (Radix+shadcn); зафиксировано ADR-014.
- Термин «OpenSpec» в исходных материалах соответствует SDD-слою изменения; он же принят каноническим инструментарием (ADR-017). Spec Kit (ADR-001, `/speckit-*`) остаётся только в bootstrap-фазе до T-020. [assumption] Профили `factory-sdd` / `product-sdd` реализуемы через custom schemas OpenSpec без изменения его кода — подтверждается на T-020.
- [assumption] Роли и имена агентов (Kevin, Bob…) — нейминг профилей, не отдельные процессы.

## 7. Метрики успеха

Базовый принцип из research: главная метрика — **стоимость принятого изменения** (токены + человеко-часы на слитое изменение), измеряется с 10-го запуска и должна снижаться от итерации к итерации.

| Метрика | Цель MVP | Источник |
|---|---|---|
| Сквозной сценарий e2e (initiative → dev-деплой со smoke) проходит без ручных правок артефактов агента | ≥ 7 из 10 запусков [assumption] | run records |
| Доля изменений, завершившихся merge без эскалации | ≥ 70% [assumption] | run records |
| Lead time задача → merge (quick / standard) | ≤ 1 раб. день / ≤ 3 раб. дня [assumption] | run records |
| Человеко-часы оператора на принятое изменение | ≤ 1 ч (кроме approvals) [assumption] | run records + учёт |
| Стоимость принятого изменения (LLM $) | Baseline после 10 запусков; тренд ↓ | usage в StageResult |
| Распределение rework-циклов | ≤ 3 (жёсткий лимит); медиана ≤ 1 | run records |
| Escaped defects (fix-MR после merge в dev) | ≤ 15% изменений [assumption] | трекер/run records |
| Нетворкинг-вмешательства человека на запуск (не approvals) | ≤ 1 | run records |
| Трассируемость: изменения с полной evidence-цепочкой | 100% | run records |
| Blocking-гейты, проходящие детерминированной проверкой (не LLM-самооценкой) | 100% | CI/gate results |
| Время восстановления после падения job (reconcile подхватывает) | ≤ 1 ч без участия человека [assumption] | run records |
