# ADR-024: Durable Run Driver and the Composition Root

- **Статус**: принято с условиями
- **Дата**: 2026-09-17
- **Автор**: architect
- Закрывает разрыв, зафиксированный в `docs/tech-dept.md` (TD-007, TD-014) и в `docs/descriptions/crm-end-to-end-flow.md` §12 («сквозной сервис не собран», «нет вызовов из рабочего пути»); разблокирует T-072 (e2e-пилот). Реализует историческую задачу T-092 (исторический реестр задач, удалён 2026-09-17), чеклист `specs/001-dark-factory-mvp/tasks.md` T057.

## Контекст

- **Что уже есть.** Порознь готовы и покрыты тестами все части P0-цепочки: домен и таблицы переходов (`changes/`), межстадийный FSM `flow.apply_result` (ADR-005), схема состояния с lease/fencing и effect ledger (ADR-004, ADR-006), порты и адаптеры — `HarnessPort`/`PydanticAIHarness`, `RepositoryPort`/`MergeRequestPort`/`PipelinePort`/`CIPort`/`GitHubAdapter`, `SDDPort` + `NativeChangeSetAdapter`, `TrackerPort`, `TelemetryPort`, политики (spec-gate, merge policy, риск-классы, budget, rework), run records (ADR-015).
- **Чего нет и почему это не «недостающая деталь», а разрыв.** Ни один модуль в `src/` не вызывает `apply_result`: `factory stage run` (`cli/stage.py`) исполняет детерминированные шаги стадии и всегда завершается `waiting`/`blocked` (ни harness, ни гейты по product SHA он не исполняет — FR-009), `run status`/`stage resume` — заглушки, `cli/run_records.py` сознательно обходит `apply_result`. У драйвера нет и быть не могло: правила границ (ADR-015 п.3, `tests/test_import_boundaries.py`) запрещают импорт из core в `adapters` (правило A) и из `adapters` в core, кроме `dark_factory.ports` (правило B). Значит, **внутри `src/dark_factory` нет ни одного места, которому разрешено соединить сервисы ядра с реализациями портов** — именно поэтому harness и SCM не подключены к рабочему пути ни в одной задаче реестра.
- **Следствие.** Сквозной сценарий «intake → SDD → реализация → MR → CI/review → merge → image → GitOps → dev → smoke» неисполним, и DoD задачи T-072 (≥7/10 e2e без ручных правок артефактов агента) недостижим, пока разрыв не закрыт.

## Решение

1. **Недостающее звено — durable-драйвер запуска, и он живёт в ядре.** `orchestration/runner.py` (одна стадия за один вызов: lease → `running` по доменной таблице → открытие операции и попытки → `StageContext` → результат → `apply_result` → атомарная запись решения) и `orchestration/state/run_store.py` (реконструкция `ChangeRun` из `execution`+`stage`, идемпотентное создание запуска, продвижение стадии, финализация попытки, запись решения). Драйвер зависит только от `dark_factory.ports` (`Protocol`), домена и state store; **ни одного импорта адаптеров**.

2. **Решение — единственный авторитет перехода.** В памяти переходы считает `apply_result`; durable-writer зеркалит решение по тем же доменным таблицам (`RUN_STATUS_TRANSITIONS`/`STAGE_STATUS_TRANSITIONS`), а не переписывает статусы напрямую. Одна стадия = одно решение = одна транзакция: `stage_result` + статусы `stage`/`attempt`/`run` + **строки стадий, созданных решением** (successor) + событие outbox; коммит — ровно один (`session_scope`), ошибка откатывает всё, включая lease.

3. **Replay-first.** Повтор того же логического действия (та же `operation_key` при том же `input_revision`) инертен: committed-результат со статусом из `REPLAYABLE_RESULT_STATUSES` возвращается как `replayed`, и **не пишется ничего** — включая строку lease и мутации попытки. Семантика совпадает с `factory stage run` (`EvidenceOperationStore`); committed `failed`/`blocked` требует новой попытки (ADR-006 п.7), а не тихой перезаписи.

4. **Драйвер — CLI-команда, а не сервис** (ADR-006 п.1/п.10): `factory run advance --change-id|--run-id` выполняет одну стадию и завершается по контракту кодов выхода (`0` запуск завершён, `10` waiting, `20` blocked, `1` failed, `2` невалидный вход/недостижимое состояние); `factory run status` — реальное чтение запуска. Продолжение — новый вызов (оператор или reconciler/CronJob), «waiting — не ошибка»: результат уже durable до ожидания (ADR-006 п.8).

5. **Связывание адаптеров выносится в отдельный слой — composition root.** Новый пакет `dark_factory.runtime` — **единственное** место, которому разрешено импортировать и ядро, и адаптеры; тест границ получает для него явный allowlist. Обратного ребра нет: ни `adapters/`, ни core не импортируют `runtime`. Правила A и B для всех остальных модулей не меняются. `runtime` собирает реализации портов из окружения (`HarnessConfig`, `GitHubConfig`, `TelemetryConfig`), но не содержит логики — только связывание и конфигурацию.

6. **Модель состояния расширяется аддитивно.** `execution.budget` и `execution.implementation_contract` (nullable JSONB, обратимая миграция `0004_runner_state`): без них реконструкция запуска теряет счётчики rework и утверждённый контракт, на которые опирается `apply_result` (FR-016, ADR-018).

7. **Нарезка на срезы** (каждый — проверяемый инкремент, отдельная задача не заводится, работа идёт в рамках T-092):
   - **S1 — durable-драйвер (выполнен).** Пункты 1–4, 6 для детерминированного исполнения стадии; инжектируемый шов `StageExecutor`; CLI `run advance`/`run status`.
   - **S2 — агентная реализация.** `StageExecutor` поверх `HarnessPort` (инструменты по профилю роли, изолированный workspace), **ветка и change request** через `RepositoryPort`/`MergeRequestPort`; первый потребитель `runtime` (пункт 5). **Commit в объём S2 не вошёл:** ни `RepositoryPort` (`get_revision`, `ensure_branch`), ни `ExecutionPort` commit/push не выражают, поэтому правки агента в изолированном workspace не публикуются, а `head_sha` change request — голова ветки (при первом создании входная ревизия), а не коммит стадии. Разрыв зафиксирован как TD-024 и вынесен в отдельный инкремент (см. «Дальше»).
   - **S3 — гейты и merge.** Результаты машинных проверок по итоговому SHA через `CIPort`/`PipelinePort`, независимый review, bounded rework, merge policy с человеческими решениями из `decision`.
   - **S4 — релиз.** digest → GitOps-MR → Argo sync → smoke → release evidence; публикация run record в `dark-factory-runs`.

8. **Зафиксированные ограничения S1** (осознанно не входят в срез):
   - retry/resume с инкрементом номера попытки — протокол ADR-006 п.7 и срез S2;
   - `ExecutionRepository.update_status` проверяет `state_revision` и `fencing_token`, но **не** таблицу `RUN_STATUS_TRANSITIONS` (существующий код, первый вызывающий — этот драйвер);
   - `input_revision` стадии выводится из снапшота изменения (SHA-256 канонического JSON), а не из commit SHA продукта — цель ADR-006 п.4, достижима в S2;
   - решение не защищено lease: `release_lease` удаляет строку в той же транзакции, поэтому проигравший гонку останавливается гардом финализированной попытки, а не fencing.

## Альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| CLI как composition root (status quo) | Ноль новых слоёв | Невозможен по правилу A, как только появляется адаптер: CLI — core, импорт адаптеров ему запрещён. Именно поэтому связывания нет | Противоречит ADR-015 п.3; потребовал бы либо удалить границу, либо перенести оркестрацию в `adapters/` |
| Драйвер внутри `adapters/` | Формально «сбоку» от core | Правило B запрещает `adapters` → core за пределами `ports`: FSM, таблицы переходов и state store недоступны — пришлось бы дублировать переходы | Дублирование единственного авторитета переходов (ADR-005) |
| Постоянный execution controller/worker | Реакция за секунды, очереди, приоритеты | Второй orchestration control plane рядом с CI при сценариях, выражаемых job-моделью; постоянный процесс в профиле ноутбука | ADR-006 п.10: контроллер — целевая эволюция с триггерами hard/soft/capacity, не MVP |
| Ослабить правила A/B глобально (любой модуль может импортировать адаптеры) | Просто, не нужен новый слой | Гарантия «ядро не зависит от SDK внешних систем» перестаёт быть проверяемой; дрейф неизбежен | Выбран один именованный слой-исключение — проверяемый и обозримый |

## Последствия

**Позитивные**
- У доменного FSM появляется durable-вызывающий: запуск становится объектом состояния (виден через `GET /api/v1/runs`, Card Console, reconciler), а не набором файлов evidence.
- Появляется шов `StageExecutor`, поэтому срез S2 (harness, SCM, MR) не трогает ни драйвер, ни FSM, ни запись решения.
- Границы репозитория сохранены: единственное исключение названо, узко и проверяется тестом границ; обратное ребро запрещено.
- Реконструкция запуска стала lossless (budget/contract), что снимает часть TD-007.

**Негативные / риски**
- `runtime` — точка, которая соблазняет накапливать логику; слой обязан оставаться связыванием (условие ниже).
- Гард идемпотентности держится на `attempt_id` и финализации попытки, поэтому **при появлении инкремента попытки (S2) два конкурентных продвижения смогут вычислить разные номера попыток и исполнить стадию дважды** — проверку replay придётся перепривязать (перепроверка под lease / после вставки попытки) и покрыть конкурентным тестом.
- `waiting`/`blocked` запуск без S2 не продвигается: срез S1 честно останавливается, но end-to-end ценности сам по себе не даёт — до S2 он лишь фундамент.
- **Сам S2 (части 1–2) сквозного пути не замыкает:** шаг commit/push в агентной стадии не реализован (TD-024), а собранное связывание не подключено к консольному entry point (TD-023). До этих двух инкрементов агентская стадия не даёт end-to-end результата, и её нельзя подавать как почти готовую.

**Условия финального принятия**
1. Срез S2 реализует `runtime` строго как composition root (связывание + конфигурация, без логики) и добавляет allowlist в тест границ.
2. Перепривязка replay-проверки выполнена вместе с инкрементом номера попытки (S2), с конкурентным тестом.
3. `RUN_STATUS_TRANSITIONS` в `update_status` либо валидируется, либо ограничение остаётся явно задокументированным (сейчас — в `docs/descriptions/cli.md`).

- **Прогресс (2026-09-17): TD-023 погашен — entry point процесса.** Консольный скрипт `factory` ре-поинтится на тонкий entry point в composition-слое (`dark_factory.runtime.entrypoint`) с ленивой сборкой `Runtime` только для `factory run advance`, поэтому связывание S2 впервые востребовано рабочим процессом. Решение и trade-offs — ADR-025; агентный путь по-прежнему не активен до TD-022 (реальный адаптер `ExecutionPort`), commit/push — TD-024.
- **Прогресс (2026-09-17): TD-024 погашен — commit/push в агентной стадии.** Публикация правок изолированного workspace стала отдельным идемпотентным внешним эффектом. Контракт расширен аддитивно, без нового ADR (ADR-015 п.3, по образцу `write_file` из S2): `RepositoryPort.publish_commit(repository, branch, changes, /, *, message, idempotency_key)` — коммит и push одним эффектом (локальный коммит не внешний, разрыв публикации на два порта ломает per-effect ledger — ADR-006 п.3), и read-половина `ExecutionPort.collect_changes(workspace, /, *, idempotency_key)` — текущее файловое множество workspace. Решения по направлению из этого раздела: **единица переноса — файловое множество** (`path → bytes`), не дифф — снапшот самосогласован, при replay сходится к тому же дереву, а REST-адаптеру дифф пришлось бы применять серверно; **`WorkspaceHandle` сознательно не входит в сигнатуру SCM-порта** — адаптер репозитория не может читать workspace, поэтому стадия собирает значения через `collect_changes` и передаёт их по значению (связка портов в сигнатуре сделала бы фейк/адаптер зависимыми друг от друга). Идемпотентность: ключ эффекта `effect:commit:<branch>` рядом с `workspace`/`branch`/`change_request`; replay-dedup — lookup-first по невидимому маркеру в теле commit message (тот же приём, что `add_comment`), поэтому повтор и холодный старт адаптера возвращают SHA первого коммита без второго; в GitHub-адаптере публикация идёт через Git data API (tree поверх дерева головы → commit object с маркером → fast-forward ветки), гонка head-read/PATCH даёт 422 → честный retryable `blocked`. «Изменений нет» — решение стадии: пустой workspace останавливает попытку в `blocked` **до** создания ветки/коммита/CR (ноль внешних эффектов), пустой `changes` в порту — громкий `ValueError`, а не молчаливый пустой CR; `head_sha` change request и `revision` артефакта — SHA коммита публикации, а не входная ревизия. Сообщение коммита структурное (`factory: <change id> (<stage>)`), без свободного текста из change — гигиена ADR-009, как и причины `blocked` только с типом исключения. Синхронизированы: фейк `FakeRepository` (read-view `commits_of`/`commit_files` для тестов), GitHub-адаптер, эмулятор GitHub API (Git data API: деревья, commit-объекты, fast-forward обновление ref), контрактная сюита портов (binding-agnostic: голова = SHA, replay → тот же SHA и один коммит, пустой → ValueError, нет ветки → KeyError), сюита агентной стадии (один коммит с контентом workspace; retry → один коммит и тот же CR; «нет изменений» → blocked без ветки и CR; сбой публикации → blocked без текста провайдера) и `specs/.../contracts/ports.md`. Валидация (фактически запущено): ruff check + format --check + mypy strict — чисто; pytest без БД 1539 passed + 64 skipped; с PostgreSQL 1598 passed + 5 skipped (среди них 20 новых: 6 контрактных × 2 биндинга, 5 контрактных `collect_changes`, 3 сценария стадии). **Осталось/не вошло:** удаления файлов не представимы в файловом множестве MVP (инструменты ролей не удаляют; полный перенос — вместе с реальным worktree-адаптером); durable-строки effect ledger ведутся существующим механизмом стадии, wiring `ensure_effect` в state store придёт вместе с durable-драйвером — так же, как у трёх существующих эффектов; двоичные файлы GitHub-адаптер через trees API не переносит (нужен blob API) — единица переноса MVP текстовая.
- **Прогресс (2026-09-17): TD-022 погашен — реальный адаптер `ExecutionPort`.** Агентный путь впервые исполним в проде без инъекции извне: `execution/workspace.py` — `WorktreeExecution`, изолирующий каждую попытку в git-worktree от закреплённой ревизии. Решения: **источник — локальное зеркало оператора** (`DARK_FACTORY_WORKSPACE_MIRROR_ROOT`, `<provider>/<slug>`; `git fetch` + `git worktree add --detach` в `DARK_FACTORY_WORKSPACE_ROOT/workspaces/<id>`) — клонирование с провайдера и credentials сознательно не в MVP (путь workspace остаётся без секретов, ADR-009; режим «клон с провайдера» — вместе с подами T-091); **идемпотентность replay без состояния** — id и каталог workspace детерминированно выводятся из `idempotency_key` (ограниченный слаг + префикс sha256 полного ключа), валидный worktree переиспользуется как есть (правки агента переживают retry), сломанный пересоздаётся от ревизии — replay сходится к пригодному workspace и никогда не минтит второй; **`collect_changes` — дельта** относительно закреплённой ревизии через `git status --porcelain=v1 -z` (свежий workspace пуст — «нет изменений» остаётся решением стадии; удаления пропускаются — файловое множество их не выражает, TD-024); **гигиена** — сбои git поднимаются value-free `WorkspaceError`, пути проверяются на выход за workspace (включая symlink-escape), `run_command` — argv без shell с таймаутом (`DARK_FACTORY_WORKSPACE_COMMAND_TIMEOUT`, дефолт 600 с) и лимитом вывода 1 МиБ на поток; **конфигурация** — `WorktreeExecutionConfig.from_env` по образцу `GitHubConfig`: незаданные переменные → отсутствие адаптера, заданные криво (относительный путь, нечисловой таймаут) → fail-closed `ValueError`. Подключён в `build_runtime` (явная инъекция приоритетна, как `token_provider`/`transport`). Контракт не менялся: `WorktreeExecution` удовлетворяет `ExecutionPort` структурно, как фейк. Синхронизированы: контрактная сюита парамeтризована по биндингам fake/worktree (по образцу `_RepositoryBinding` — binding-провайдерные хуки `seed_file`/`make_state_fail` и биндинг-нейтральные команды), юнит-тесты `tests/test_execution_workspace.py` (26: replay-сходимость, path safety, таймаут, лимит вывода, дельта), wiring-тесты `tests/test_runtime_composition.py`, `specs/.../contracts/ports.md` и описания (`docs/descriptions/execution.md` §1.1, `runtime.md`, `cli.md`).
