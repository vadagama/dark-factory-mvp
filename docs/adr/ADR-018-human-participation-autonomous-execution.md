# ADR-018: Human Participation and Autonomous Execution Boundaries

- **Статус**: принято
- **Дата**: 2026-09-13
- **Автор**: software-architect
- Принят по ревью [ADR-011](ADR-011-risk-based-merge-release-policy.md) (пользователь, 2026-09-13): ADR-011 ограничен merge/release; режим участия человека по фазам создания решения фиксируется этим ADR.
- **Уточнено** (2026-09-13, архитектурное ревью ADR-пакета): условия эскалации согласованы с bounded rework (T-014) и утверждённым Implementation Contract (п.5)

## Контекст

- Прежняя редакция ADR-011 («Human Off The Loop Release Policy») регулировала преимущественно merge/deployment, но название создавало впечатление, что вся фабрика работает без человека. Фактически это две независимые политики: (1) участие человека в создании решения и (2) участие человека в merge/deployment ([ADR-011](ADR-011-risk-based-merge-release-policy.md)).
- Требования, UX/UI и значимые архитектурные решения содержат много неформализованных предпочтений. Убирать человека из этих фаз рискованно: вероятен не столько технический брак, сколько «правильно реализованное, но ненужное» решение.
- Написание кода, напротив, хорошо автоматизируется, если фабрика получила: утверждённые acceptance criteria; архитектурные ограничения; UI-прототип или дизайн-контракт; разрешённый scope изменений; автоматические тесты и quality gates; риск-класс; бюджет итераций, времени и стоимости; правила эскалации.
- Целевая модель — Human Off The Loop; ревью показало, что применять её нужно избирательно, по фазам жизненного цикла.

## Решение

1. Режим участия человека фиксируется по фазам:

| Фаза | Роль человека | Режим |
|---|---|---|
| Формирование проблемы и требований | Уточняет цели, ограничения, acceptance criteria | Human-in-the-loop |
| UX/UI | Итерационно оценивает сценарии, прототипы и визуальный результат | Human-in-the-loop |
| Архитектура | Совместно утверждает значимые решения и исключения | Human-in-the-loop |
| Планирование реализации | Проверяет границы задачи и уровень риска | Human-on-the-loop |
| Написание кода | Агенты автономно реализуют, тестируют и исправляют | Human-off-the-loop |
| Проверки качества и безопасности | Автоматические gates; человек подключается по исключениям | Human-on-the-loop |
| Merge в MVP | Явное подтверждение человека | Human-in-the-loop |
| Deploy в dev | Автоматически после merge и успешных gates | Human-off-the-loop |
| Prod | Ручное разрешение после evidence | Human-in-the-loop |

2. Целевая модель: **Human-in-the-loop — для намерения и значимых решений; Human-off-the-loop — для исполнения; Human-on-the-loop — для наблюдения и исключений.** Человек определяет, что и в каких границах строить; фабрика автономно решает, как довести согласованное изменение до готового к merge состояния и dev-контура.
3. Discovery/design (требования, UX/UI, значимые архитектурные решения) выполняются итерационно при участии человека. Результат — утверждённый **Implementation Contract**: scope, acceptance criteria, архитектурные ограничения, UI evidence, риск-класс, бюджет (итерации, время, стоимость), правила эскалации.
4. После утверждения Implementation Contract реализация выполняется в режиме **Human Off The Loop**: агенты самостоятельно пишут код, запускают проверки, исправляют дефекты и формируют release evidence. Человек не участвует в промежуточных шагах реализации, если не сработало условие эскалации.
5. Автономная реализация останавливается (эскалация человеку), если:
   - требования противоречат друг другу или недостаточны;
   - требуется выйти за утверждённый scope;
   - требуется изменение публичного API, схемы данных, IAM или архитектурной границы, не предусмотренное утверждённым Implementation Contract (несовместимое изменение — также при отсутствии утверждённого migration plan);
   - агент предлагает новый ADR;
   - риск повышен до R2+;
   - не пройдены security/quality gates, неисправимые в рамках bounded rework: исправимые findings возвращаются в rework-цикл (T-014, лимит 3); эскалация — при non-retryable нарушении политики либо исчерпании rework/retry-бюджета;
   - превышен бюджет автономных итераций;
   - UI нельзя подтвердить автоматическим сравнением и acceptance criteria;
   - требуется необратимая операция.
6. Архитектурные решения разделяются на три класса:
   - **Known path** — решение уже закреплено ADR, шаблоном или golden path: агент применяет самостоятельно;
   - **Bounded choice** — несколько разрешённых вариантов: агент выбирает и фиксирует rationale;
   - **New path** — новая технология, граница сервиса, хранилище, протокол, IAM-модель: требуется человек (и ADR).
7. Merge в MVP, auto-merge (T-085) и Prod — release authorization, регулируется [ADR-011](ADR-011-risk-based-merge-release-policy.md): merge — человек, deploy в dev после merge — автоматически, Prod — ручной.

Связанные задачи: **T-016** (Implementation Contract, классификация Known/Bounded/New path, машинно проверяемые условия эскалации — основная реализация настоящего ADR), T-004 (стоп-условия и переход в Blocked), T-011 (профили ролей discovery/design), T-014 (bounded rework и эскалация по исчерпании лимитов), T-020 (Implementation Contract как часть OpenSpec-change), T-062 (бюджет автономных итераций), T-080 (риск-классы: условие эскалации «риск повышен до R2+» становится машинно проверяемым только с этой задачей). Release authorization — [ADR-011](ADR-011-risk-based-merge-release-policy.md): T-032, T-085.

## Альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| Полный Human Off The Loop на всех фазах | Максимальная автономия и скорость цикла | Риск «правильно реализованного, но ненужного» решения там, где много неформализованных предпочтений (требования, UI, архитектура) | Отклонено для MVP: Human-in-the-loop на discovery/design и на merge |
| Human-in-the-loop на каждой фазе (традиционный процесс) | Максимальный контроль | Не проверяет автономию исполнения; медленный цикл; ручные согласования без добавленной ценности | Отклонено: автономия исполнения — ядро ценности фабрики |
| Один ADR, совмещающий участие человека и release policy (прежняя редакция ADR-011) | Один документ | Смешивает release policy с операционной моделью; название вводит в заблуждение | Отклонено: разделено на [ADR-011](ADR-011-risk-based-merge-release-policy.md) (merge/release) и этот ADR |

## Последствия

**Позитивные**
- Предсказуемые точки участия человека: намерение, значимые решения, merge; остальное — автономно или по исключениям.
- Условия эскалации формализованы: поведение агентов при выходе за границы детерминировано.
- Разделение Known/Bounded/New path снижает лишние согласования: человек обязателен только для New path.

**Негативные / риски**
- Implementation Contract — новый обязательный артефакт: нужен шаблон и место хранения (в MVP — в задаче/MR).
- Эскалация останавливает автономный цикл; требуется SLA реакции человека [assumption].
- Режимы фаз связаны с риск-классами (T-080): ошибка классификации может лишить человека нужной точки контроля — митигируется запретом LLM-понижения класса ([ADR-011](ADR-011-risk-based-merge-release-policy.md)).

- T-080: риск-классы R0–R4 — до них условие эскалации «риск повышен до R2+» действует как ручная оценка, а не как гейт.
