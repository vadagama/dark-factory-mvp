# ADR-026: Параметризуемые этапы CI — переключатели repository variables (T058)

- **Статус**: принято
- **Дата**: 2026-09-17
- **Автор**: ci-cd

## Контекст

- `.github/workflows/ci.yml` — единственный обязательный MR-пайплайн (GitHub-first, [ADR-019](ADR-019-multi-provider-sc-ci-github-first.md)); в нём 20 независимых этапов-проверок: Python-гейты (`lint`, `typecheck`, `test`, `build`, `security`), factory-гейты dogfooding (`factory-us1-parity`, `factory-stage-smoke`), Console-гейты (T036, [ADR-021](ADR-021-console-mvp-delivery.md)), UIKit-гейты (T042, [ADR-014](ADR-014-react-uikit-storybook.md)) и две доверенные сборки образов (`factory-image`, `console-image`).
- Разработка требует быстрых итераций, а самые долгие этапы не зависят от конкретного изменения: multi-arch сборка образов со сканами и SBOM, `storybook build`, визуальная регрессия (она же ещё раз собирает Storybook), Playwright e2e с установкой браузера. Эти этапы гоняются на каждом MR, хотя при итерации по Python-коду или по одному экрану консоли их результат не нужен.
- Другого способа, кроме правки workflow в ветке задачи, сейчас нет: временный коммит в `ci.yml` расходится с `main`, рискует утечь в merge и «съедает» ревью-внимание. Ждать полный прогон — тоже не вариант по времени.
- Ограничения, которые решение не имеет права нарушить:
  - merge — человек и по зелёным гейтам ([ADR-011](ADR-011-risk-based-merge-release-policy.md));
  - доверенные образы собираются только после зелёных детерминированных гейтов и публикуются immutable-тегом `sha-<sha>` (T033, [ADR-021](ADR-021-console-mvp-delivery.md) п.7);
  - отключение проверки ради «зелёного» пайплайна — антипаттерн (скилл `ci-cd`); конфигурация обязана быть **fail-safe**: её отсутствие означает полный набор проверок, а не пустой.
- В GitHub Actions `pull_request`-прогоны не принимают `workflow_dispatch`-инпуты, поэтому вход управления должен читаться самим workflow: остаются repository variables, метки PR и `paths`-фильтры.

## Решение

1. **Каждый этап `ci.yml` получает выключатель — repository variable `CI_SKIP_<JOB>`**, где `<JOB>` — идентификатор job'а заглавными буквами с `-` → `_` (`uikit-storybook` → `CI_SKIP_UIKIT_STORYBOOK`). Правило именования выводится из `ci.yml` механически, поэтому не требует отдельного реестра.
2. **Семантика opt-out и fail-safe**: этап выполняется, пока его переменная не равна ровно `true` (строчными). Пустая переменная, `false`, `True`, `yes`, `1`, опечатка — этап выполняется. Любое состояние, кроме явного `true`, не может убрать гейт из пайплайна; «отключить по ошибке» невозможно (в отличие от opt-in, где забытая переменная молча выключает проверку, а опечатка в значении — тем более).
3. **Условие — job-level `if` на контексте `vars`**, без новых сущностей: `if: vars.CI_SKIP_UIKIT_STORYBOOK != 'true'`. Отдельного конфигурационного job'а, профилей и реестра переменных нет — одна переменная на этап, одно правило чтения.
4. **Доверенные сборки образов получают толерантный к пропускам страж зависимостей**:
   `vars.CI_SKIP_FACTORY_IMAGE != 'true' && !cancelled() && !contains(needs.*.result, 'failure') && !contains(needs.*.result, 'cancelled')` (и симметрично для `console-image`).
   Смысл: гейт, выключенный намеренно (его job пропущен), не должен «глушить» сборку образа — иначе выключение `security` или `uikit-storybook` неожиданно отменяло бы и образ; упавший или отменённый гейт сборку, как и раньше, блокирует.
5. **Переключатели — только на время разработки.** Полный набор возвращается до merge; merge остаётся за человеком (ADR-011). Правило зафиксировано в `docs/development-workflow.md` и в инструкции `docs/instructions/manage-ci-stages.md` (управление плюс описание каждого этапа и его локального эквивалента).
6. **Контракт проверяется тестом** `tests/test_ci_stage_toggles.py`: у каждого job'а `ci.yml` есть переключатель, сравнение идёт ровно с `'true'` (fail-safe), image-этапы сохраняют толерантный страж и `needs`-цепочку, список переменных в инструкции совпадает с объявленным в workflow (drift невозможен незамеченным).
7. **Вне схемы**: переиспользуемые workflow (`factory-image.yml`, `console-image.yml`, `factory-stage.yml`) управляются через вызывающие их этапы; `uikit-baselines.yml` запускается меткой `uikit-baselines` и остаётся отдельным on-demand workflow.

## Альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| Правка `ci.yml` в ветке задачи (закомментировать/удалить этап) | Ноль инфраструктуры | Расхождение ветки с `main`; правка рискует утечь в merge; переключатель не виден в ревью; нельзя применить к чужому MR | Отклонено |
| `workflow_dispatch`-инпуты (`fast`, `skip_storybook`, …) | Явные параметры прогона | `pull_request`-события не принимают инпуты — задача «выключить этап при разработке на MR» не решается | Отклонено: не покрывает основной сценарий |
| Метка PR (`ci:fast` / `ci:skip-storybook`) с расширением триггера `types: [labeled, unlabeled]` | Точное управление на уровне MR, не влияет на чужие прогоны | Усложнение триггера (метка запускает новый прогон), второй источник истины рядом с переменными, нужен парсинг меток в условиях; больше путей ошибиться | Отклонено сейчас; зафиксировано как возможная доработка |
| Единый профиль `CI_PROFILE=fast` (+ оверрайды на этап) | Одна переменная для частого сценария | Два источника истины и неявные пресеты: «что именно выключил fast» не видно; при изменении набора тяжёлых этапов поведение пресета меняется молча | Отклонено в пользу одного правила «переменная на этап» |
| Конфигурационный job: валидация значений и сводка включённых этапов | Ранняя диагностика опечаток, наглядный summary | Новый job + новая точка отказа всей пайплайна; при opt-out семантике невалидного состояния нет, а пропущенные этапы и так видны в UI прогона как `Skipped` | Отклонено как избыточное |
| `paths`-фильтры на job'ах (запускать UIKit-гейты только при изменениях в `packs/ui`) | Автоматически экономит прогоны | Это не выключатель этапа, а фильтр триггера: при ошибке в фильтре проверка тихо не запускается; не даёт ручного контроля «выключить сейчас» | Отклонено для этой задачи (возможное отдельное решение) |
| `continue-on-error: true` | Прогон не краснеет | Этап всё равно выполняется — время не экономится; маскирует гейт вместо его выключения | Отклонено |
| Opt-in семантика (`CI_RUN_UIKIT_STORYBOOK = true` включает этап) | «Явное включение» выглядит безопасно | Забытая/опечатанная переменная молча выключает гейт — ровно тот риск, который недопустим | Отклонено: opt-out fail-safe |

## Последствия

**Позитивные**

- Итерация ускоряется без правок workflow: тяжёлые этапы выключаются и возвращаются парой команд либо в UI; список выключенного виден (`gh variable list`, `Skipped` в прогоне).
- Пайплайн остаётся fail-safe: по умолчанию включены все 20 этапов, опечатка не может убрать проверку.
- Переключатели не меняют состав этапов, их `needs`-цепочки и evidence-контракты сборок образов: `factory-image`/`console-image` по-прежнему не идут после упавшего гейта и публикуют только immutable `sha-<sha>`.
- Появился единый документ по каждому этапу (что проверяет, вес, локальный эквивалент) и drift-тест `tests/test_ci_stage_toggles.py`.

**Негативные / риски**

- Пропущенный этап не проверяет ничего: регрессия может уехать в `main`, если забыть вернуть набор. Митигация: правило в `docs/development-workflow.md`, п. 2 «Правил безопасности» в инструкции и то, что выключение всегда явное и заметное (`Skipped`).
- Переменные действуют на весь репозиторий, а не на один MR, — временно «замедляя» проверки и для чужих веток. Для одиночного разработчика это приемлемо; при росте команды триггером пересмотра станет per-PR управление метками.
- Если этап входит в required status checks ветки, пропущенный чек блокирует merge PR — ограничение branch protection, задокументировано в инструкции.
- Образ может быть собран из SHA, где часть гейтов была выключена намеренно. Промоушен между окружениями остаётся ручным GitOps-MR по digest (ADR-010/ADR-011), поэтому автоматического «протаскивания» непроверенного SHA нет.
- Ещё одна поверхность конфигурации (репозиторные переменные) — состояние живёт в настройках GitHub, а не в git; значения перечислены и объяснены в инструкции, но историю изменений git не хранит (для временных переключателей это осознанный компромисс).

**Дальше**

- При росте команды или числа этапов — рассмотреть per-PR метку (`ci:fast`) как дополнение, а не замену (сохранение fail-safe обязательно).
- При появлении в пайплайне новых job'ов правило обязательно: новый этап добавляется вместе со своим `CI_SKIP_*` и строкой в инструкции — иначе тест `tests/test_ci_stage_toggles.py` краснеет и merge блокируется по гейту.
