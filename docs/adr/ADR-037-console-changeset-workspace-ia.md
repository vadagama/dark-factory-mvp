# ADR-037: Console IA and the ChangeSet workspace

- **Статус**: принято с условиями
- **Дата**: 2026-09-19
- **Автор**: architect
- Решение согласовано оператором 2026-09-19 (предложенная UX-спецификация консоли, разделы 1–4, 14). Условие: конкретика экранов финализируется ролью `design` при реализации соответствующего milestone.

## Контекст

- Сегодня Console — 6 экранов наблюдателя: список изменений, карточка, гейты/approvals, бюджеты, переключатели CI, настройки (`console/README.md`, ADR-021). Это «приборная панель», а не рабочее пространство.
- Видение оператора: три уровня навигации (Продукты → Продукт → ChangeSet), компактная глобальная навигация, сквозной inbox «Требует внимания», главный экран ChangeSet, markdown-редактор как ключевая часть.
- Прямое требование: на каждом шаге оператор понимает «что подготовлено, что изменилось, что мешает, какое решение требуется» ([ADR-033](ADR-033-operator-guidance.md)).
- Видение явно запрещает показывать «готово на 63%» по всему изменению: доработки и пересмотр требований делают такой показатель недостоверным.
- Требование разделять **принятое состояние продукта** (baseline) и **предлагаемые изменения**.
- Ограничение MVP: порядок API → CLI → Console (вопрос 8); объём консоли наращивается по milestone, а не сразу.

## Решение

1. **Три уровня навигации:**
   - **Продукты** — список продуктов, активные изменения, запросы внимания;
   - **Продукт** — baseline, изменения в работе, состояние dev, история доставок;
   - **ChangeSet** — фазы, артефакты, агенты, обсуждения, проверки.
2. **Глобальная навигация компактна:** `Продукты · Требует внимания · Активность`. Настройки фабрики, интеграций и агентов — в отдельной служебной области (существующие экраны бюджетов/CI/настроек переезжают туда).
3. **Inbox «Требует внимания»** — сквозной по продуктам; каждый пункт ведёт к **конкретному вопросу, фрагменту или решению**, а не просто на страницу ChangeSet.
4. **Главный экран ChangeSet** — основное рабочее пространство, постоянная структура:
   - **верхняя панель**: название и ID, текущая фаза и её состояние, бюджет (факт, лимит, прогноз), блокеры, участники, меню и история;
   - **левая колонка — фазы** (Ф0–Ф8, [ADR-032](ADR-032-phase-projection.md)): состояние, число нерешённых замечаний, номер итерации; завершённые фазы доступны для просмотра;
   - **центр — рабочая область выбранной фазы** с вкладками **Результат · Изменения · Проверки · История**;
   - **правая панель — контекст**: обсуждение выделенного фрагмента, вопросы агента, поручения на доработку, сведения о выбранной задаче/проверке; сворачиваемая, с полноэкранным режимом для редактора и UI-представления;
   - **нижняя панель решения** — только когда требуется действие: состояние проверок, блокирующие вопросы, открытые замечания и **одна** основная кнопка с этапной подписью («Согласовать требования», «Утвердить план и запустить»).
5. **`Guidance` — единственный источник подсказки**: верхняя панель, нижняя панель решения, inbox и пустые состояния рендерят его ([ADR-033](ADR-033-operator-guidance.md)); логика «что дальше» в UI не дублируется.
6. **Никакого «процента готовности» всего изменения.** Показываются состояния фаз, количества открытых замечаний/вопросов и номер итерации.
7. **Принятое отделено от предлагаемого**: baseline продукта и предлагаемые изменения визуально и структурно разделены; при открытии документа baseline видны связанные активные изменения.
8. **Визуальный характер:** светлая спокойная основа, выразительная типографика, минимум постоянных рамок, основной документ занимает большую часть экрана; цвет — только для состояний и внимания, всегда с текстом/иконкой; агенты представлены именем роли и текущим действием; анимация — только там, где помогает понять выполнение.
9. **Порядок реализации:** сначала **экран ChangeSet, markdown-редактор, контекстные комментарии и панель согласования** — они задают UX; графы, превью и мониторинг исполнения — специализированные представления внутри того же пространства.
10. Существующие экраны не выбрасываются: бюджеты, этапы CI и настройки переносятся в служебную область; список изменений и карточка поглощаются уровнями «Продукты»/«ChangeSet».

## Альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| Оставить 6 экранов наблюдателя (статус-кво) | Ничего не делать | Оператор не может вести изменение из интерфейса — это и есть блокер MVP | Противоречит цели |
| Сразу полный редизайн со всеми представлениями (графы, canvas, мониторинг) | Целевой UX в один заход | Дорого, поздно даёт ценность, риск не успеть к приёмке | Порядок API → CLI → Console и инкрементальность |
| Одностраничное приложение без уровней (всё в ChangeSet) | Проще навигационно | Нет области продукта/baseline, невозможно «начать новую фичу» и видеть доставки | Не покрывает видение §2–§3 |

## Последствия

**Позитивные**

- Оператор проходит весь цикл в одном пространстве, сохраняя контекст.
- Требование «один следующий шаг» получает постоянное место (верхняя и нижняя панели).
- Существующие экраны переиспользуются без переписывания с нуля.

**Негативные / риски**

- Объём работ по консоли наибольший среди workstreams; митигация — инкрементальность по milestone и приоритет API/CLI.
- Инбокс и фазы требуют новых read-model на API — без них UI неполон.
- Риск «красивого, но пустого» интерфейса: каждый экран обязан закрываться рабочим API (иначе не реализуется вовсе).
