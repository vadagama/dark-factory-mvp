# ADR-031: Repository provisioning (validate, clone, bootstrap)

- **Статус**: принято с условиями (ревизия 2, accepted with amendments)
- **Дата**: 2026-09-19
- **Автор**: architect
- Решение согласовано оператором 2026-09-19 (вопросы 1–3). Условия: механика секрета для репозиториев вне установки App и поведение пустого репозитория уточняются при старте M1 (T062).
- **Уточнено** (2026-09-19, T069): `bootstrap_baseline` реализуется на `ProviderClone` (пишущая операция в продуктовый репозиторий); «`contents:read`» п.3 описывает путь клона, а не весь набор прав App; `LocalMirror` остаётся без bootstrap; состав сборки следует за контуром (полные `DARK_FACTORY_GITHUB_*` + корень зеркала → `ProviderClone`, иначе `LocalMirror`); запись остаётся в trusted composition root (п.7). Детали — ниже, «Поправка (ревизия 2)».

## Контекст

- Видение оператора, шаги 2–3: «Фабрика валидирует репо и клонирует, чтобы с ним можно было работать» и «Фабрика подтверждает, что с репо всё ок».
- Сегодня **клона нет вообще**: `WorktreeExecution` минтует воркспейсы из операторских локальных зеркал (`DARK_FACTORY_WORKSPACE_MIRROR_ROOT`, `<root>/<provider>/<slug>`); клон с провайдера и credentials — явный non-goal MVP (TD-022: «клон с провайдера и credentials — non-goal MVP до T-091»).
- Аутентификация в GitHub — **GitHub App** (`DARK_FACTORY_GITHUB_APP_ID`/`_PRIVATE_KEY`/`_INSTALLATION_ID`): RS256 JWT → короткоживущий installation token (~1 ч). Патент (PAT) не используется; приложение уже имеет `contents:read` для установленных репозиториев (T024/T033).
- Оператор подтвердил: клон разрешён (вопрос 1), репозиторий демо — новый и чистый (вопрос 3), то есть возможен пустой репозиторий без коммитов (unborn HEAD).

## Решение

1. Вводится порт **`RepositoryProvisioningPort`** с тремя операциями:
   - `validate` — доступность репозитория, права, состояние ветки по умолчанию, наличие baseline;
   - `ensure_mirror` (clone/fetch) — подготовка локального зеркала/воркспейса, с которого работает `WorktreeExecution`;
   - `bootstrap_baseline` — применение `packs/product-baseline` (и blueprint-пака, если задан) к пустому или неподготовленному репозиторию.
2. **Два адаптера** за одним портом: `LocalMirror` (текущее поведение, оператор готовит зеркала) и `ProviderClone` (клон с провайдера). Ядро не знает, откуда взялось зеркало; воркспейс-механика не меняется.
3. **Клон выполняется на GitHub App installation-токене** существующего контура (короткоживущий, `contents:read`) — отдельный PAT не вводится. Если репозиторий не входит в установку App, вводится отдельный секрет только для чтения; значение — в Kubernetes Secret namespace `factory`, имя ключа — в `.env.example` (без значения). Секреты в код и git не попадают (ADR-009).
4. **Пустой репозиторий — штатный случай:** отсутствие HEAD не является ошибкой; результат валидации различает «пуст: baseline будет создан» и «не пуст: baseline отсутствует/актуален/устарел».
5. Валидация **не мутирует** репозиторий: правки (baseline, ветки) выполняются только явным шагом bootstrap с идемпотентным `effect_key` (ADR-006) и наблюдаемым статусом продукта (`validating → ready | error`, [ADR-030](ADR-030-product-registry.md)).
6. Результат провижининга — evidence продукта: наблюдаемая ревизия, применённые паки и версии, факт доступности. «С репо всё ок» — это evidence, а не сообщение в UI.
7. Repository credentials не попадают в agent-поды: провижининг выполняется trusted-исполнителем (composition root), а агентные стадии продолжают работать от подготовленного зеркала/воркспейса.

## Альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| Только локальные зеркала (статус-кво, TD-022) | Нет работы, нет обращения к сети, минимальный риск | «Добавить продукт по ссылке» невозможно без операторских шагов вне интерфейса; видение не выполняется | Противоречит видению и цели MVP |
| Клон PAT'ом | Проще App-механизма | Долгоживущий секрет, нарушает инвариант «короткоживущие токены» (ADR-019 п.3, TD-016) | Противоречит ADR-019 |
| Клон внутри agent-пода | Единый механизм | Credentials внутри границы agent-пода — прямое нарушение инварианта «agent-под без credentials» (TD-018) | Нарушает границу доверия |
| ProviderClone как единственный адаптер (убрать LocalMirror) | Один код-путь | Ломает локальный пилот и TD-022-воркфлоу, требует сети всегда | Регрессия по среде; два адаптера дешевле |

## Последствия

**Позитивные**

- «Добавить продукт по ссылке» становится сквозной операцией интерфейса.
- Провижининг отделён от исполнения и от агентной границы; секреты остаются в trusted-слое.
- Появляется база для превью и доставки (репозиторий уже клонирован и подготовлен).

**Негативные / риски**

- Сетевой доступ и новые credentials в контуре: нужна аккуратная работа с секретами и fail-closed диагностикой без их эха (ADR-009).
- Провижининг может быть длительным → необходимы асинхронность, идемпотентность и наблюдаемый статус (не блокировать UI).
- Расхождение «зеркало vs репозиторий» (устаревшее зеркало) — нужна сверка ревизии перед стартом стадии.

**Дальше**

- T062 (M1): порт, адаптеры, статусы продукта, API/CLI, живой прогон на новом репозитории.
- Долгосрочно — заменяет non-goal TD-022 «клон с провайдера» для продуктового слоя.

## Поправка (ревизия 2, 2026-09-19, T069): `bootstrap_baseline` и границы доступа

Поправка не меняет решения п.1–п.7, не вводит новых контрактов, стека и границ доверия; исходный текст выше сохранён без изменений. Снимается условие «поведение пустого репозитория уточняется при старте M1»: пустой репозиторий подтверждён штатным случаем (p.4) и покрыт `validate`/bootstrap (`EMPTY` → первый коммит). Остаётся условие про отдельный секрет для репозиториев **вне** установки App — bootstrap его не вводит и по-прежнему fail-closed (`validate` → `UNAVAILABLE`, `ensure_mirror` → `KeyError`).

**a) «`contents:read`» (п.3) — область клона, а не весь набор прав App.** Токен installation читается на `validate`/`ensure_mirror` (клонирование, fetch). Применение baseline — пишущая операция: коммит и push в ветку по умолчанию продуктового репозитория. Запись не новая и не вводится этой поправкой: change flow уже коммитит installation-токеном через Git data API (`RepositoryPort.publish_commit`, `src/dark_factory/adapters/scm/github/repository.py` — tree → commit → fast-forward ref; T-024/T092), то есть фабричный контур уже зависит от пишущего доступа. Поэтому п.3 следует читать как «клон идёт на короткоживущем токене с правом чтения», а не как «App ограничен чтением»: разрешения App на установленных продуктовых репозиториях должны включать `contents:write`, иначе bootstrap честно падает, а не рапортует об успехе.

Наблюдение к сведению (вне скоупа T069, требует сведения формулировок): `deploy/ci/README.md` описывает App раннеров (Secret `factory-github-app` в ns `ci`) как имеющий **только** `Administration (write)` и прямо указывает «ни `contents:write` (merge/commit)». Либо контур runtime/CLI использует другой App (`DARK_FACTORY_GITHUB_*`), либо формулировка устарела относительно T-024. Свести — при wiring M1; на само решение T069 это не влияет, кроме требования fail-closed диагностики.

**b) Разделение способностей адаптеров (уточнение п.2).** `bootstrap_baseline` реализуется на `ProviderClone` (`adapters/scm/github/provisioning.py`): канонический Product Baseline принадлежит продуктовому репозиторию (ADR-020 п.3), а провайдерский доступ есть только у клона. `LocalMirror` остаётся адаптером операторского зеркала без credentials (п.2/п.7) и продолжает бросать `ProvisioningOperationUnsupportedError` с именем операции — молчаливый success запрещён (п.6). Состав сборки следует за контуром: при заданном корне зеркала и полных `DARK_FACTORY_GITHUB_*` composition root выбирает `ProviderClone`, при одном корне зеркала — `LocalMirror`, без корня порт отсутствует. `FakeRepositoryProvisioning` сохраняет replay-дедуп и служит эталоном контрактной сюиты.

**c) Запись — в trusted composition root, не в agent-подах (п.7 без изменений).** Клонирование, запись payload пака и push выполняет trusted-исполнитель (composition root) installation-токеном; дочернему процессу git токен передаётся **только** через окружение (инвариант T068: `http.<base>/.extraheader`, `GIT_TERMINAL_PROMPT=0`; ни argv, ни URL), диагностика — fail-closed и без эха секрета (ADR-009). Agent-стадии продолжают работать от подготовленного зеркала и credentials не получают.

**Механика (детали — `docs/descriptions/ports.md` §3.9/§4.6 и README пака `product-baseline`).** Паки — данные из необязательного корня `DARK_FACTORY_PACKS_ROOT`: без него клон и валидация работают, а bootstrap падает fail-closed (нельзя заявить baseline, которого нет). Манифест `product-baseline/pack.yaml` (`dark-factory.dev/pack/v1`, `name` + SemVer `version`) даёт evidence `applied_packs`, поддерево `baseline/` переносится в корень репозитория как `.factory/`, а `changeset/` остаётся шаблоном изменения, не payload'ом bootstrap. Перед записью рабочее зеркало выравнивается на текущую вершину ветки по умолчанию провайдера (`git reset --hard origin/<default>`; на несозданной удалённой ветке шаг пропускается), payload записывается **всегда** и ставится в индекс принудительно (`git add --all --force` — в том числе в репозитории, игнорирующем `.factory/`), коммит уходит как `HEAD:refs/heads/<default>`, и перед выдачей evidence адаптер сверяет фактическую вершину ветки у провайдера (`git ls-remote`) с заявленной ревизией. Идемпотентность двойная: replay по `idempotency_key` возвращает тот же результат, а физический no-op — это не «baseline уже есть», а «payload не поставил ни одного изменения, при этом `.factory/product` присутствует в HEAD»: коммит не создаётся, evidence — паки, записанные в subject существующего коммита baseline (`bootstrap: apply name@version, …`), а baseline, созданный не bootstrap'ом, не несёт ни одного пака. Если же ничего не поставилось, а baseline в HEAD отсутствует, bootstrap падает fail-closed, а не выдаёт чужую ревизию за readiness. Bootstrap не является механизмом апгрейда: смена версии манифеста без изменения содержимого даёт тот же no-op, а `BASELINE_STALE` (сравнение с желаемой версией пака) остаётся зарезервированным словарём. Результат — `BaselineBootstrapResult(repository, revision, applied_packs)`: evidence, а не сообщение (п.6).

**Ограничение MVP.** Порт называет один репозиторий (`repository`), поэтому bootstrap применяет baseline к тому же репозиторию — случай «один продукт — один репозиторий» (ADR-020 п.3). Multi-repo продукт с отдельным product-spec репозиторием потребует явного указания репозитория baseline; в MVP это не выражается и этой поправкой не вводится.

**Ограничения механизма и открытые вопросы** зарегистрированы в `docs/tech-dept.md`: секреты контура в окружении git-подпроцессов (TD-035), устаревающая `MirrorRef.head_revision` у `ensure_mirror` (TD-036), прямой push в защищённую ветку по умолчанию (TD-037), недостижимость `BASELINE_STALE` (TD-038) и расхождение формулировок о правах App с `deploy/ci/README.md` (TD-039).
