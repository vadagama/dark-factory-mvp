# ADR-015: Repository Boundaries for Factory, Operational State and Products

- **Статус**: принято с условиями
- **Дата**: 2026-09-13
- **Автор**: software-architect
- Решение согласовано пользователем (ответы на вопросы раздела 5 plan.md, 2026-09-13)
- **Пересмотр 2 (2026-09-13)**: по результатам ревью (оценка 7/10) статус изменён на «принято с условиями»; продуктовые репозитории переформулированы в динамическую модель, содержимое `dark-factory-runs` ограничено компактным индексом доказательств, добавлены протокол межрепозиторного версионирования, направление зависимостей, правила защиты модульного монолита и границы доверия внутри `dark-factory`. - **Пересмотр 3 (2026-09-13, архитектурное ревью ADR-пакета)**: исправлено направление зависимостей adapters/core (п.3); `okf` помечен целевым репозиторием вне MVP (п.1).

## Контекст

- Q-14 plan §5 формулирует альтернативу как «5 репозиториев (`git-structure.md`)» против `dark-factory-orchestrator` (`dm-ai-agent-instructions.md`), трёх репо platform/sdk/plugins (`factory-modularity.md` §10), `dark-factory-capabilities` (`droid-improvements.md` §6) и `foundation/*` (`self-improvement.md`). **Формулировка вопроса неточна:** `git-structure.md` не предлагает общий репозиторий `products`. Его §2 перечисляет `product repositories` (по репозиторию на продукт, в MVP — один пилотный), §16 п.7 предусматривает вынос `product-template` в отдельный репозиторий позднее, а Итог формулирует целевую модель как «четыре платформенных репозитория плюс независимые product repositories». Аналогично §8 уже ограничивает `dark-factory-runs` компактными manifests, запрещает screenshots, большие логи, build output и бинарники, а `evidence-index` хранит URI + checksum.
- Исходная редакция настоящего ADR («пять постоянных репозиториев») была написана по формулировке Q-14, а не по источнику, и потеряла оба этих ограничения. Ревью восстановило их, зафиксировав риски:
  1. **общий репозиторий для всех продуктов не масштабируется**: общая история и общий CI несвязанных продуктов, конфликтующие права и `CODEOWNERS`, невозможность независимо архивировать/версионировать/переносить продукты, слишком широкий blast radius автоматических изменений, слабая изоляция при автономной реализации, противоречие принципу «trunk-based в каждом репо» (у разных продуктов — разные trunk, релизы и владельцы);
  2. **Git непригоден как полный execution journal**: токеновые и трассировочные события, логи, десятки–сотни промежуточных `StageResult` на run, частые параллельные записи, конфликты push, раздувание истории и медленные clone/fetch, сложные retention и выборочное удаление, чувствительные prompt/output данные. Git пригоден для компактных человекочитаемых manifest-файлов.
- Пересмотр 2 возвращает решение к модели `git-structure.md` и доопределяет то, чего в источнике нет: критерий извлечения продукта в отдельный репозиторий, протокол записи в `-runs`, протокол межрепозиторного версионирования, направление зависимостей и границы доверия внутри `dark-factory`.
- Влияние: границы кода/CI/релизов с первого дня; имена `-gitops`/`-runs` нужны уже в P0 (T-002, T-061).

## Решение

**Четыре системных репозитория, один пилотный продуктовый репозиторий и правило автоматического создания отдельных репозиториев для последующих продуктов.**

1. **Четыре постоянных системных репозитория**:
   - `dark-factory` — модульный монолит (core, CLI, API, Console, adapters, agents, skills, flows, rules, packs, CI templates, charts), выпускается одной согласованной версией (совместимость core, adapters, agents, flows, Console);
   - `dark-factory-gitops` — желаемое состояние окружений: Argo CD Applications, values, immutable digests; без secrets (отделяет код платформы от фактически развёрнутого состояния);
   - `dark-factory-runs` — компактный immutable индекс доказательств, не execution journal (см. п. 4; отделяет операционный журнал от исходного кода);
   - `okf` — knowledge graph с самостоятельным жизненным циклом, не привязан к релизам runtime. **Целевой репозиторий вне MVP**: в MVP не создаётся и не требуется (vision §5, Out of Scope); фактический MVP-набор — `dark-factory`, `dark-factory-gitops`, `dark-factory-runs` и пилотный продуктовый репозиторий.

2. **Продуктовые репозитории — динамические, не один общий**:
   - `products` — GitLab group/namespace. В P0 — один пилотный продуктовый репозиторий и версионированный blueprint (blueprint-плагин, ADR-008; T-070). `product-template` из `git-structure.md` — **не отдельный репозиторий**.
   - Каждый следующий независимо выпускаемый продукт создаётся **отдельным репозиторием** из версионированного blueprint. Целевая модель:

     ```text
     dark-factory
     dark-factory-gitops
     dark-factory-runs
     okf
     products/          # GitLab group/namespace
       product-a        # пилот (P0)
       product-b        # следующие продукты — отдельные репозитории
       product-c
     ```

   - **Критерий извлечения**: после появления второго независимо выпускаемого продукта либо разных наборов владельцев/прав каждый продукт создаётся в отдельном репозитории из версионированного blueprint. Постоянное хранение всех продуктов в одном репозитории запрещено.
   - Архитектурно это не «пять репозиториев», а четыре системных репозитория плюс динамически создаваемые продуктовые.

3. **`dark-factory` — защищённый модульный монолит**:
   - Без дробления на platform/sdk/plugins (преждевременно до появления SDK-потребности, ADR-008 поэтапен); отказ от отдельного `dark-factory-capabilities` до появления внешних потребителей и marketplace.
   - «Границы модулей проверяет CI» — это минимальный набор правил, а не декларация: публичные интерфейсы модулей; зависимости направлены от adapters к контрактам ядра: adapters импортируют только публичные порты/контракты core, импорты из core в adapters и в SDK внешних систем вне adapter-слоя запрещены; схемы `RunManifest`, `StageResult`, `NextAction` — versioned contracts; contract tests для packs; migration policy для схем; dependency graph check; запрет прямого доступа agents/flows к GitLab, Kubernetes и хранилищам в обход портов.
   - **Границы доверия внутри одного репозитория**: trusted core и security/risk policies — с одной стороны; agents, prompts/skills, packs, CI templates — с другой. Для Human Off The Loop это разные уровни доверия: разные `CODEOWNERS`, разрешённые пути изменений, risk classes, pipeline gates, правила self-modification. Агент не должен через обычный R0/R1-процесс (ADR-011) одновременно менять реализацию, правила классификации риска и собственные quality gates (ADR-018).

4. **`dark-factory-runs` — компактный immutable индекс доказательств**. В Git — сжатый индекс доказательств, а не полный execution journal. Состав хранилищ в MVP определяет [ADR-009](ADR-009-minimal-bootstrap-otel.md) (минимальный bootstrap; Loki/Prometheus/MinIO/Harbor — вне MVP); настоящий ADR определяет только **распределение данных по классам хранилищ**, а не обязательный набор сервисов:

   | Данные | Хранилище в MVP (ADR-009) | Целевой DC-контур (T-091) |
   |---|---|---|
   | `RunManifest`, итоговый `StageResult`, approvals, decisions | Git (`dark-factory-runs`) | Git (`dark-factory-runs`) |
   | Ссылки, digest и provenance | Git (`dark-factory-runs`) | Git (`dark-factory-runs`) |
   | Логи и трассировки | Job logs + GitLab CI artifacts; OTLP-экспорт во внешний backend — опционально (ADR-009 п.2) | Loki / Tempo или иной OTLP-backend |
   | Evidence, отчёты, скриншоты, SBOM | GitLab CI artifacts через `ArtifactStorePort`; в `-runs` — только URI + checksum | Объектное хранилище (S3/MinIO) через тот же порт |
   | Метрики usage/cost/duration | PostgreSQL (ADR-004) + usage/cost-атрибуты OTel (ADR-009 п.3) | PostgreSQL + Prometheus/ClickHouse |

   Смена backend не меняет ни структуру `-runs`, ни код фабрики: доступ к тяжёлым данным идёт через `ArtifactStorePort` и `TelemetryPort`. Ограниченный retention CI artifacts — известный риск MVP (ADR-009, «Негативные»): срок хранения обязан перекрывать максимальное человеческое ожидание и повторный запуск, иначе продолжение блокируется.

   Протокол записи (детализирует T-061):
   - один commit на run или стадию;
   - partitioning, например `YYYY/MM/project/run-id`;
   - single-writer либо merge-request-free append protocol;
   - максимальный размер записи;
   - retention и архивирование;
   - sanitization секретов и персональных данных;
   - неизменяемость (immutability) завершённого run record;
   - подпись manifest и проверка digest evidence.

5. **Протокол межрепозиторного версионирования**: связи между `dark-factory`, `gitops`, `runs`, `okf` и продуктовым репозиторием — не ветки и не `latest`, а конкретные идентификаторы (immutable commit SHA, semantic versions, artifact digests), иначе run невозможно воспроизвести:

   ```yaml
   factory_version: 0.3.1
   factory_commit: 4f86c2a
   pack_name: backend-go
   pack_version: 1.4.0
   blueprint_version: 2.1.0
   product_commit: 731ac91
   gitops_commit: ca31c10
   okf_revision: 9f12a44
   ```

6. **Направление зависимостей**:

   ```mermaid
   flowchart TD
       DF["dark-factory"] --> P["Product repository"]
       DF --> R["Run manifest"]
       K["okf"] --> R
       P --> G["dark-factory-gitops"]
       G --> R
       R --> E["External evidence"]
   ```

   - runtime не импортирует содержимое `gitops`;
   - `gitops` ссылается на immutable image/chart versions;
   - run record ссылается на точные revisions всех входов;
   - продукт не зависит от внутреннего Python API фабрики — интеграция через схемы, CLI и versioned packs.

7. Принципы `git-structure.md` сохраняются: код отделён от состояния, Git — источник истины, trunk-based в каждом системном и продуктовом репозитории (у каждого продукта — свой trunk, релизы и владельцы), runs не хранит бинарные артефакты.

Связанные задачи: T-002, T-043, T-061, T-070, T-088.

## Альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран / статус |
|---|---|---|---|
| 4 системных репо + динамическая группа `products` (переработка `git-structure.md`) | Изоляция продуктов (trunk, релизы, владельцы); компактный `-runs`; воспроизводимость run по SHA/semver/digest | Больше репозиториев и пайплайнов; нужна автоматизация bootstrap продуктовых репо | **Выбрано (пересмотр 2)** |
| 5 репозиториев с общим `products` (исходная редакция ADR) | Чёткие источники истины; атомарный релиз фабрики | Общий `products` не масштабируется (см. Контекст); `-runs` рискует превратиться в execution journal | Заменено пп. 2 и 4 |
| `dark-factory-orchestrator` | Один репо-сервис | Сужает фабрику до оркестратора; не покрывает gitops/runs/okf | Отклонено |
| Три репо: platform/sdk/plugins | Готовность к marketplace | Преждевременное дробление до SDK-потребности (ADR-008 поэтапен) | Отклонено (вернуть при появлении независимых потребителей, отдельных релизных циклов или marketplace) |
| `dark-factory-capabilities` | Отдельный каталог расширений | Дублирует packs внутри `dark-factory` до появления marketplace | Отклонено (вернуть при T-088 при необходимости) |
| `foundation/*` | Иерархия групп | Групповая структура без нужды в MVP | Отклонено |

## Последствия

**Позитивные**
- Код, состояние доставки и evidence с первого дня в разных источниках; откат — revert GitOps-коммита.
- Продукты изолированы: свой trunk, релизы и владельцы у каждого; blueprint версионируется.
- `dark-factory-runs` остаётся компактным и человекочитаемым; тяжёлые данные — в профильных хранилищах.
- Run воспроизводим: все межрепозиторные связи — immutable SHA/semver/digest.

**Негативные / риски**
- Оверхед синхронизации релизов фабрики с blueprint — версии pack явные.
- Нужны append-протокол для runs и автоматизация создания продуктовых репозиториев (T-061, T-070).
- Несколько `CODEOWNERS` и pipeline gates внутри `dark-factory` усложняют CI.

**Дальше**

- T-043: подключение `dark-factory-gitops`; ссылки через immutable digests (пп. 5–6).
- T-061: run records в `-runs` — компактный индекс и протокол записи (п. 4).
- T-070: группа `products`, пилот и blueprint, критерий извлечения (п. 2).
