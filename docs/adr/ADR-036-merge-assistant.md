# ADR-036: Merge assistant — human-initiated merge from the console

- **Статус**: принято с условиями
- **Дата**: 2026-09-19
- **Автор**: architect
- Решение согласовано оператором 2026-09-19 (вопрос 7: «approve в консоли фиксирует решение, и нужна помощь в мерже из консоли — это должно быть юзабельно и понятно»). Условие: набор провайдерских действий (запрос review, постановка approving review) уточняется при реализации T066.
- Уточняет [ADR-011](ADR-011-risk-based-merge-release-policy.md) в части операторской поверхности; существо политики (merge — человек) не меняется.

## Контекст

- ADR-011: в MVP merge — только человек; низкорисковое изменение автономно доводится до готового к merge состояния; после ручного merge deploy в dev выполняется автоматически; auto-merge R0/R1 — отдельная задача T-085.
- Merge policy (`orchestration/policy/merge.py`, T-026) требует **version-bound approving review на итоговом SHA**: при несовпадении SHA — `blocked`, при отсутствии человеческого APPROVED-решения на гейте `review`, привязанного к head SHA, — `manual`. Агентский executor мержить не может.
- `MergeRequestPort` умеет `open`, `find_existing`, `add_comment`, `merge(expected_sha)` и `observe` (`ChangeRequestObservation`: head SHA, состояние merge, человеческие reviews). Постановка review отдельным методом порта **не выражена** — только наблюдается.
- Живая боль пилота T043: оператор смержил CR `product-1#12`, но ран не закрылся — «merge policy требует version-bound approving review на итоговом SHA, а у #12 ревью не было». Принятый протокол — ставить approving review **до** merge. Второй факт: branch protection неполна (TD-026 — нет `required_status_checks`, `enforce_admins=false`).
- Операторский `approve` в пилоте жил в операторском скрипте (`pilot_api.py`, таблица `decision`) и драйвером долго не читался — то есть поверхность решения отсутствовала, а не просто «была неудобной».

## Решение

1. Merge остаётся **человеческим решением** (ADR-011 не меняется). Меняется исполнение: вводится **«Помощник merge»** — поверхность в Console и CLI, делающая это решение исполнимым и понятным.
2. Помощник показывает **чек-лист готовности**, собранный из наблюдаемого состояния (не из желаемого):
   - обязательные проверки CI на итоговом SHA;
   - version-bound approving review на head SHA;
   - требования branch protection (по `MergeProtectionPolicy`, T-026);
   - пройденные согласования фаз.
3. Каждый невыполненный пункт формулируется человекочитаемо и сопровождается действием по снятию: «Нужен approving review на `f61f247a` → [Открыть PR] / [Запросить review]». Недоступное действие объясняет причину (правило [ADR-033](ADR-033-operator-guidance.md)).
4. **Approve в консоли фиксирует версионно-привязанное человеческое решение** на соответствующем гейте (ADR-009 п.7) — это то, что читает merge policy. Провайдерские требования, которые фабрика не может выполнить за человека (approving review при включённой branch protection), снимаются явным действием оператора в провайдере по ссылке из чек-листа.
5. **Merge выполняется как явное человеческое действие** с подтверждением: `MergeRequestPort.merge(expected_sha)`; несовпадение SHA (`HeadMismatchError`) блокирует и не создаёт эффекта; решение фиксируется как человеческое. **Автомержей в MVP нет** — auto-merge остаётся задачей T-085.
6. После merge фабрика продолжает по **наблюдаемому** merge (`observe`), а не по предположению: переход к `release`/доставке не требует ручного «дотолкнуть».
7. Отклонения branch protection (TD-026) не маскируются: чек-лист показывает фактически наблюдаемые настройки и явно называет расхождения.

## Альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| Оставить merge только в GitHub UI (статус-кво) | Ничего не делать | Ровно та боль, из-за которой ран пилота не закрылся: оператор не видит требования политики | Не закрывает цель MVP |
| Разрешить консоли автомерж при зелёных гейтах | Удобно | Нарушает ADR-011 и опережает T-085 (нет статистики и переключателя) | Противоречит принятой политике |
| Ослабить политику (не требовать version-bound review) | Проще мержить | Убирает единственную привязку согласования к ревизии; снижает доверие к «принято» | Регрессия политики ADR-009 п.7 |
| Ограничиться записью решения без действий | Минимум работы | Оператор по-прежнему не знает, что именно мешает мержу | Не выполняет требование «юзабельно и понятно» |

## Последствия

**Позитивные**

- Merge-решение становится исполнимым без знания внутренних команд и требований политики.
- Расхождение «решение в консоли vs review в провайдере» становится видимым и устранимым, а не「молчаливым» блокером.
- Fail-closed поведение политики сохраняется: помощник объясняет блок, а не обходит его.

**Негативные / риски**

- Мутирующий merge-эндпоинт требует роли operator и явного подтверждения; риск ошибочного клика митигируется подтверждением и сверкой `expected_sha`.
- Часть действий пока ведёт в провайдер (approving review) — до появления соответствующего метода порта UX будет содержать переход наружу.
- Неполнота branch protection (TD-026) остаётся ограничением контура и должна быть видна оператору.
