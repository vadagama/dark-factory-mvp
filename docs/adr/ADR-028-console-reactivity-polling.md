# ADR-028: Reactivity of the Console — polling, WebSockets rejected (T095)

- **Статус**: принято
- **Дата**: 2026-09-18
- **Автор**: architect
- Решение подготовлено по итогам проработки реактивности UI консоли (вопрос «нужны ли WebSockets»); реализация — задача T095, ветка `feat/t-095-console-polling`

## Контекст

- Console (T036, [ADR-021](ADR-021-console-mvp-delivery.md)) — пять read-mostly экранов плюс экран управления этапами CI. Слой данных намеренно минималистичен (ADR-021 п.6): тонкий `useAsync` без react-query — один запрос на монтировании и ручной `reload()`. На долго открытой вкладке оператор видит устаревшие данные: статусы стадий, гейты и бюджеты обновляются только вручную.
- Темп обновления данных: reconciler проходит раз в 2–5 минут ([ADR-006](ADR-006-ephemeral-job-pods-reconciler-cronjob.md)), агентные стадии живут минутами; контур — один оператор, локальный ([ADR-009](ADR-009-minimal-bootstrap-otel.md) п.7).
- Спека (US6, FR-019) требует отображать статусы/гейты/блокеры/стоимость — требований на обновление в реальном времени нет; потеря локального кэша допустима (SC-008).
- Мутации уже имеют REST-семантику: `Idempotency-Key`, version-bound approvals ([ADR-011](ADR-011-risk-based-merge-release-policy.md), [ADR-009](ADR-009-minimal-bootstrap-otel.md) п.7, [ADR-018](ADR-018-human-participation-autonomous-execution.md) п.3) — консоли не требуется двунаправленный канал.
- Источник событий для push в будущем существует — outbox ([ADR-016](ADR-016-postgresql-outbox.md)).
- Топология отдачи: same-origin через nginx-прокси `/api` (ADR-021 п.2), в dev — vite-прокси; e2e перехватывает fetch через `page.route` (ADR-021 п.6).

## Решение

1. **Модель реактивности MVP — фоновый поллинг внутри `useAsync`** (опциональный третий параметр `UseAsyncOptions { pollMs }`), без новых зависимостей и без изменений API/nginx/chart:
   - единый интервал для всех динамических экранов — константа `POLL_MS = 10_000` (10 с) в `hooks.ts`; поллинг включён на списке изменений, карточке изменения, гейтах/approvals и бюджетах; экран этапов CI — без поллинга (экран операторских действий, состояние меняется только явными переключателями);
   - цепочка `setTimeout` вместо `setInterval`: следующий запрос планируется только после завершения предыдущего — запросы не накладываются, отложенных таймеров не больше одного; ручной `reload()` выполняет немедленный refresh, пере-планирование всегда снимает висящий таймер (цикл не удваивается);
   - без экспоненциального backoff: неудачный фоновый тик пере-планирует цикл через один интервал; осознанное упрощение — для локального однопользовательского контура backoff оценён как лишняя сложность; при переезде API в разделяемый контур — вернуться к вопросу (вместе с п.3);
   - пауза в скрытой вкладке (`document.visibilityState`): в hidden запланированный таймер снимается и новые не планируются; при возврате видимости — немедленный refresh и возобновление цикла;
   - семантика ошибок: `error` показывается только когда нечего показать (первичная загрузка или новые deps); фоновая неудача сохраняет последние хорошие данные и не меняет `error` — ошибки не мигают на живом экране; успешный тик сбрасывает `error`. Неудачная первичная загрузка поллинг не запускает (нет retry-шторма по недоступному API) — цикл возобновляется по `reload()`;
   - `updatedAt` — время последнего успешного ответа; на списке изменений и карточке изменения показывается индикатор «обновлено HH:MM:SS» (UTC, `formatTime` в `lib/format.ts`) — свежесть данных видима оператору;
   - без опций (falsy `pollMs`) поведение хука ровно прежнее (ADR-021 п.6), слушатель `visibilitychange` не ставится.
2. **WebSockets в MVP отклонены**: двунаправленность не нужна (мутации остаются REST), требования на моментальность отсутствуют, а стоимость — жизненный цикл соединения (reconnect/heartbeat), аутентификация handshake, серверный fan-out, переработка e2e-перехвата — непропорциональна темпу данных (минуты) и однопользовательскому контуру.
3. **Push — будущая опция через SSE, а не WebSockets.** Триггеры перехода: несколько операторов с конкурентными approvals, live-логи стадий, операционные дашборды. Схема: outbox (ADR-016) → fan-out в API → `EventSource` с топиками вида `runs/{id}`; мутации остаются REST. WebSockets — только для genuinely двунаправленных сценариев. Любой push — отдельный ADR.
4. **Границы изменения**: только `console/` (`api/hooks.ts`, `lib/format.ts`, тесты, четыре экрана); контракт API и e2e-сценарии (фикстуры через `page.route`) не затронуты.

## Альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| WebSockets сейчас | Мгновенный push, двунаправленность | Жизненный цикл соединения, auth handshake, серверный fan-out, переработка e2e-моков; нет требований на двунаправленность и realtime | Отклонено: непропорционально темпу данных (минуты) и однопользовательскому контуру |
| SSE сейчас | Однонаправленный push поверх обычного HTTP, авто-reconnect | Новый серверный компонент (fan-out outbox→stream), изменения в e2e-контуре | Отложено до появления триггеров (п.3) |
| react-query с `refetchInterval` | Готовый кэш, поллинг, дедупликация | Новая зависимость вопреки намеренно минимальному слою данных (ADR-021 п.6) ради одной возможности | Отклонено: тонкого `useAsync` достаточно |
| Условные GET (ETag/If-None-Match) | Дешёвый поллинг на проводе | Изменение API-контракта T035 и клиента ради почти нулевой выгоды в локальном контуре | Отклонено на сейчас |
| Экспоненциальный backoff при неудачах | Щадящая нагрузка на деградировавший API | Дополнительное состояние и конфигурация ради контура «один оператор, локальный API» | Отклонено как избыточное: неудачный тик просто задерживает цикл на один интервал; вернуться при появлении разделяемого контура |
| Статус-кво (ручной reload) | Ноль работы | Устаревшие статусы на открытой вкладке — оператор решает по несвежим данным | Отклонено: реактивность нужна |

## Последствия

**Позитивные**
- «Достаточно живой» UI без изменений API, chart и зависимостей; тестовые швы (мок fetch, `page.route`) сохранены; поллинг тестируется fake-таймерами.
- Явный контракт реактивности в одном месте (`useAsync`); экраны включают поллинг декларативно (`{ pollMs: POLL_MS }`).
- Индикатор «обновлено» делает окно свежести видимым оператору — поллинг не создаёт иллюзии моментальности.

**Негативные / риски**
- Окно свежести данных — до 10 с; приемлемо на темпе reconciler/стадий.
- Без backoff деградировавший API опрашивается каждые 10 с, пока вкладка видима; приемлемо в локальном контуре, при разделяемом контуре — вернуться к backoff/SSE (п.3).
- Поллинг — не событийный механизм: при появлении нескольких операторов или live-логов потребуется миграция на SSE (отдельный ADR).

**Дальше**
- Наблюдать за триггерами п.3; при появлении — ADR о outbox → SSE fan-out.
- При появлении динамики лимитов/профилей (T-062, ADR-021 п.5) — пересмотреть поллинг экранов 4–5 и источники `/api/v1/meta/*`.
