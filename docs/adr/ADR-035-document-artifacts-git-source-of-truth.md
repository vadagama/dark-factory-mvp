# ADR-035: Document artifacts — git as the source of truth, revisions and drafts

- **Статус**: принято с условиями
- **Дата**: 2026-09-19
- **Автор**: architect
- Решение согласовано оператором 2026-09-19 (вопрос 6: git — истина). Условие: механика хранения черновика автосейва (серверный draft store vs локальный) уточняется при старте M2 (T063).

## Контекст

- Видение требует показывать оператору артефакты (спеку, ADR, UI-спеки, план) как markdown-файлы, давать править их и из консоли, и напрямую в GitHub, с историей версий, сравнением и комментариями.
- Сегодня артефакт представлен как `ArtifactRef{artifact_type, uri, revision, sha256, producer}` (`src/dark_factory/changes/refs.py`) — ссылка на что-то, лежащее в git/CI; поверхности чтения/diff/правки нет.
- Канонический SDD-слой — Native SDD Core (ADR-020): ChangeSet живёт в `.factory/changes/<year>/<id>/`, Product Baseline — `.factory/product/`; самостоятельно адресуемые артефакты имеют YAML frontmatter и являются узлами OKF-графа.
- Оператор подтвердил: git — источник истины (вопрос 6). Значит, правка из консоли обязана становиться ревизией в git, а не отдельным состоянием в БД фабрики.
- ADR-015 п.5 требует immutable-refs и запрет `latest`; ADR-009 п.7 — версионную привязку согласований.

## Решение

1. **Источник истины документов — git.** Артефакты ChangeSet — файлы в репозитории продукта (`.factory/changes/...`), ревизия документа = коммит (SHA). Фабричная БД хранит read-model и метаданные (привязки, обсуждения, решения), но не является хранилищем содержимого.
2. Вводится **read-model дерева артефактов ChangeSet**: типы (`spec`, `design`, `adr`, `ui`, `plan`), пути, ревизии, frontmatter-свойства; используется CLI и Console.
3. **Правка из интерфейса = коммит** в ветку изменения через `RepositoryPort.publish_commit` (идемпотентность по `effect_key`, ADR-006/ADR-024). Правка в GitHub — тот же результат, наблюдается как новая ревизия; конфликт (обе стороны изменили один фрагмент) не разрешается молча.
4. **Черновик автосейва — вне git**: незавершённые правки хранятся отдельно и коммитятся явным действием «сохранить». Это защищает источник истины от «мусорных» ревизий и позволяет показать состояние сохранения.
5. **YAML frontmatter** отображается компактным блоком «Свойства документа»; частые свойства редактируются полями, полный YAML доступен в исходнике; системные идентификаторы защищены от случайного изменения.
6. **Переключение режимов не теряет и не переписывает содержимое.** Неизвестные конструкции сохраняются дословно; для них доступен просмотр/правка исходника. Переключение режимов — обратимая операция над текстом.
7. **Staleness — часть модели:** новая ревизия документа делает неактуальными связанные согласования и проверки, привязанные к прежней ревизии; это отражается явно, а не «зелёным» статусом.
8. Реализация первого шага — режимы **Документ / Markdown / Чтение**; режим **Сравнение** и agent-diff-apply отложены (вне объёма MVP), при этом структура модели версий их допускает.

## Альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| Хранить документы в БД фабрики как канон (git — экспорт) | Быстрый editor, простой diff/версии в одном месте | Два канона для SDD-артефактов, рассинхрон с ADR-020 и с правками в GitHub | Противоречит ответу оператора и ADR-020 |
| Только GitHub-редактор (ссылка наружу) | Нулевой объём работ | Не выполняет видение (правка «из консоли»), нет привязки комментариев и версий внутри продукта | Не закрывает цель MVP |
| Коммитить каждое автосохранение | Всё всегда в git | Шум истории, дорогой diff, ломает ревью-поток | Источник истины засоряется |
| Полноценный WYSIWYG-редактор в MVP (ProseMirror и т.п.) | «Богатый» опыт | Тяжёлая зависимость, риск потери содержимого при round-trip в MVP | Дорого и рискованно; Markdown-редактор с режимами достаточен |

## Последствия

**Позитивные**

- Единый источник истины: правка из UI и правка в GitHub сходятся в одну ревизию.
- Комментарии и согласования получают версионную привязку (ADR-034).
- Нет второго канона SDD — согласуется с ADR-020 и ADR-015.

**Негативные / риски**

- Запись в git из UI требует аккуратной обработки гонок и ошибок сети (коммит может «не долететь» — нужен явный статус сохранения).
- Черновик вне git — дополнительное хранилище и правило «что считать сохранённым».
- Round-trip markdown ↔ редактор — источник тонких дефектов; требование «неизвестные конструкции сохраняются дословно» обязательно к тестированию.
