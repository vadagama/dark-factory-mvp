# ADR-019: Multi-Provider Source Control and CI — GitHub Adapter First

- **Статус**: принято
- **Дата**: 2026-09-13
- **Автор**: software-architect
- Решение согласовано пользователем (2026-09-13): пилот запускается на GitHub-адаптере, GitLab-адаптер — вторым провайдером.

## Контекст

- План (Этап 3) и vision §3.5 исходно строили SC/CI-контур вокруг единственного провайдера GitLab: T-030 «GitLab-адаптер», T-041 «GitLab Runner», ADR-012 (Premium). Пилот при этом зависел от корпоративного инстанса и лицензии GitLab, что не требуется для проверки ценности фабрики.
- SC/CI-функции, нужные фабрике, эквивалентны у обоих провайдеров: ветки, change request (MR у GitLab, PR у GitHub), pipeline/workflow, статусы проверок, артефакты, merge-политика, webhooks. Различие — терминология и API, не семантика Change Flow.
- T-005 уже разделяет `SourceControlPort` (`RepositoryPort` / `MergeRequestPort` / `PipelinePort`) и планирует `CIPort`; ядро обязано не знать провайдера, иначе второй провайдер потребует переделки Flow, reconcile-правил (T-063) и CI-шаблонов (T-031).

## Решение

1. **Порты — единая точка интеграции.** Провайдерские адаптеры реализуют порты из T-005: **`GitHubAdapter` реализует `SourceControlPort` и `CIPort`**; `GitLabAdapter` — то же. Ядро (Flow, reconcile, policy) не импортирует SDK провайдеров (границы импортов — ADR-015 п.3).
2. **Единая доменная модель change request.** GitLab MR и GitHub PR сведены к **`ChangeRequestRef`** — единый идентификатор, ссылка и статус в терминах ядра. Контракты Flow (T-003), reconcile-правила (T-063), run records и Console оперируют `ChangeRequestRef`, а не MR/PR.
3. **GitHub-адаптер — первый провайдер MVP.** Поддерживает: **GitHub App** (аутентификация через **короткоживущие installation tokens с минимальными permissions** — соответствует официальным рекомендациям GitHub; долгоживущие PAT у ядра и агентов отсутствуют), **webhooks** (ускоритель; журнал — состояние фабрики, ADR-006), **Actions** (запуск агентных стадий в self-hosted раннерах, T-041), **Checks API** (статусы гейтов по итоговому SHA), **artifacts** (StageResult/evidence через `ArtifactStorePort`), **merge policy** (branch protection/rulesets, обязательные checks, approvals).
4. **Выбор провайдера — на уровне репозитория**: конфигурация репозитория задаёт `provider: gitlab | github`. Репозитории одного изменения (продукт, `-gitops`, `-runs`) используют провайдер, заданный конфигурацией продуктового репозитория.
5. **Инвариант эксклюзивности исполнения**: один run исполняется ровно в одном провайдере. Провайдер фиксируется при старте run и не меняется до его завершения — один run не может одновременно исполняться в GitLab и GitHub. Смена провайдера репозитория применяется только к новым run'ам; активный run завершается в исходном провайдере, reconcile (T-063) не перепривязывает run.
6. **Единые контрактные тесты.** Контрактная тест-сюита портов (T-005) исполняется против каждого адаптера (fake → GitHub → GitLab): оба адаптера обязаны проходить один и тот же набор поведенческих тестов; провайдер-специфичные интеграционные тесты — поверх контрактов.
7. **Порядок внедрения**: T-030 — GitHub-адаптер (P0, критический путь MVP); T-034 — GitLab-адаптер (P1). ADR-012 (GitLab Premium) действует в части GitLab-провайдера; критический путь MVP от Premium-функций не зависит.

Связанные задачи: T-005, T-030, T-031, T-032, T-034, T-041, T-063; ADR-012, ADR-015.

## Альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| Только GitLab (прежний план) | Один адаптер; корпоративный контур | Пилот зависит от доступности/лицензии инстанса; потеря скорости | Пилот переносится на GitHub; GitLab — T-034 |
| Только GitHub (без GitLab-адаптера) | Минимальная поверхность поддержки | Теряется корпоративный контур (GitLab 16) | GitLab-адаптер запланирован (T-034) |
| Сторонний forge-абстракционный слой поверх Git API | Единый API «из коробки» | Новая зависимость; не покрывает CI и merge policy полностью; порты уже дают границу | Отклонено: порты + собственные адаптеры |

## Последствия

**Позитивные**
- Пилот не зависит от корпоративного GitLab (лицензия/доступность); ADR-012 перестаёт блокировать критический путь MVP.
- Короткоживущие installation tokens с минимальными permissions снижают радиус компрометации по сравнению с PAT; агентные pods по-прежнему без merge/deploy credentials (ADR-011).
- Второй провайдер добавляется без изменений ядра: контрактная сюита гарантирует эквивалентное поведение адаптеров.

**Негативные / риски**
- Две поверхности поддержки (API, webhooks, раннеры) — митигируется единой контрактной сюитой и провайдер-нейтральными CI-шаблонами (T-031).
- Ядро опирается только на общее подмножество возможностей провайдеров; провайдер-специфичные ускорители (merge train GitLab Premium, GitHub rulesets) — фичефлаги за портами.
- SaaS-зависимость GitHub.com для пилота (rate limits, доступность) — reconcile-модель переживает простой API; эскалация — GHES или смена провайдера конфигурацией репозитория.

**Дальше**
