# ADR-005: Stage-Scoped Graphs and a Light Workflow Core

- **Статус**: принято
- **Дата**: 2026-09-13
- **Автор**: software-architect
- Решение согласовано пользователем (ответы на вопросы раздела 5 plan.md, 2026-09-13)
- **Уточнено** (2026-09-13, архитектурное ревью ADR-пакета): тестовый уровень сформулирован как exhaustive-проверка конечной таблицы, а не «доказательство» property-тестом

## Контекст

- Q-4 plan §5: scope pydantic-graph — «durable Pydantic Graph как WorkflowEnginePort между CI jobs» против «TaskGraph только внутри одной стадии, продолжение через StageResult/NextAction»; промежуточная позиция — «не превращать всю фабрику в один граф», но workflow-core на pydantic-graph.
- Влияние: сложность ядра, восстановление после падения job, тестопригодность.

## Решение

1. **pydantic-graph — только внутри стадии**: TaskGraph, параллельные подзадачи (branch/join ≤2), reducers — T-015.
2. Межстадийный Flow (стадии, гейты, rework-лимиты, бюджеты, маршруты quick/standard) — **собственный лёгкий durable workflow-core**: единственный источник разрешённых переходов — неизменяемая таблица переходов; `StageResult`/`NextAction` типизированы. Гарантия корректности переходов разделена на три уровня:

   - **типы** (mypy strict): `NextAction` — закрытое размеченное объединение; обработчик стадии обязан покрыть все варианты, непокрытый обнаруживается `assert_never` на typecheck;
   - **рантайм**: переход выполняется единственной функцией, сверяющей пару (стадия, `NextAction`) с таблицей; отсутствующая пара — явная ошибка, а не неопределённое поведение;
   - **тесты**: exhaustive-тест конечной таблицы переходов (полный обход всех пар состояние × `NextAction`) проверяет, что из достижимых состояний недостижим переход вне таблицы и что мёртвых рёбер нет.

   Полная типовая гарантия «недопустимый переход невозможен по типам» была свойством отклонённого варианта на pydantic-graph, где топология выражена сигнатурами `BaseNode.run()`; детерминированная таблица даёт её в объёме, описанном выше.
3. Состояние Flow — PostgreSQL (ADR-004); продолжение между job'ами — через StageResult/NextAction, а не через длительно живущий процесс.
4. workflow-core реализует `WorkflowEnginePort` (ADR-006) — смена движка (например, Temporal, ADR-003) не меняет стадии и агентов.
5. Принцип «не превращать всю фабрику в один граф» сохранён; отличие от промежуточной позиции — межстадийный слой не на pydantic-graph, а на детерминированной таблице переходов.

Связанные задачи: T-004, T-015, T-063.

## Альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| Durable pydantic-graph как WorkflowEnginePort между CI jobs | Единая графовая модель во всём флоу | Durable-исполнение графа между процессами не поддерживается из коробки; сложное восстановление | Отклонено |
| TaskGraph только внутри стадии, межстадийная логика — ad-hoc в CI | Минимум кода ядра | Продолжение между job'ами размазано по CI-скриптам; нет единой таблицы переходов/гейтов | Отклонено: заменено собственным workflow-core |
| Лёгкий workflow-core **на** pydantic-graph (промежуточная позиция) | Один инструмент оркестрации | Тянет графовую модель и её ограничения в межстадийный слой | Не выбран: межстадийный FSM проще и детерминированнее как таблица переходов |
| «Только внутри стадии» + собственный лёгкий durable workflow-core | Детерминизм, тестопригодность, восстановление по StageResult | Два механизма оркестрации (граф внутри, FSM между) | Выбрано |

## Последствия

**Позитивные**
- Таблица переходов покрывается тестами целиком (DoD T-004); восстановление после падения job — чтение StageResult, а не интерпретация графа.

**Негативные / риски**
- Собственный FSM-код — зона регрессий; требуется полное тестовое покрытие переходов.
- Два оркестрационных механизма — граница «стадия ≠ Flow» должна быть явной в документации и ревью.
