# ADR-030: Product registry and product scope

- **Статус**: принято
- **Дата**: 2026-09-19
- **Автор**: architect
- Решение согласовано оператором 2026-09-19 (вопросы 1–3, 9).

## Контекст

- Видение оператора начинается с продукта: «захожу в консоль и добавляю новый продукт — название, ссылка на GitHub, описание»; далее продукт — точка входа в работу (baseline, активные изменения, доставки).
- В домене продукта нет: `Change.product` — это `RepositoryRef{provider, slug}` (`src/dark_factory/changes/refs.py`), то есть репозиторий, а не продукт. Нет имени, описания, baseline-ссылки, состояния dev-контура, статуса готовности репозитория.
- Консоль (6 экранов наблюдателя, `console/README.md`) не имеет уровня «Продукты»; регистрация продукта в пилоте делалась intake'ом изменения (`POST /api/v1/changes`) и операторскими шагами (журнал T043).
- Следствие: невозможно ответить на вопросы «какие продукты есть», «готов ли репозиторий», «какой baseline актуален», «что требует внимания по продукту».

## Решение

1. Вводится агрегат **`Product`** — самостоятельная сущность домена, а не поле изменения:
   - `id`, `name`, `description`;
   - `repository` — `RepositoryRef` (провайдер + slug) и опционально canonical URL;
   - `baseline_ref` — ссылка на канонический Product Baseline (`.factory/product/`, ADR-020);
   - `dev_env_ref` — ссылка на dev-контур доставки (namespace/Application);
   - `status` — состояние готовности: `created → validating → ready | error(reason)`;
   - `created_at`.
2. `Change` получает `product_id`; продукт — область группировки изменений и baseline-дельта. Обратная совместимость: изменения без продукта читаются как прежде (поле опционально до миграции данных пилота).
3. Продукт — **верхний уровень навигации** Console и CLI: `Продукты → Продукт → ChangeSet`; регистрация продукта — первое действие оператора, а не побочный эффект intake'а.
4. Готовность репозитория — часть продукта (`status`), а не «побочный факт» изменения: «Фабрика подтверждает, что с репо всё ок» (видение, шаги 2–3) выражается статусом `ready` со ссылкой на провижининг ([ADR-031](ADR-031-repository-provisioning.md)).
5. Продукт владеет baseline-представлением (принятое состояние) и отделяет его от предлагаемых изменений; reconciliation обновляет baseline по подтверждению человека (ADR-020).
6. Регистрация продукта — мутирующая операция, требующая authenticated-токена оператора (как approvals), с audit-записью; провижининг репозитория — асинхронная операция с наблюдаемым статусом.

## Альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| Оставить продукт как `RepositoryRef` внутри изменения (статус-кво) | Ноль изменений домена | Нет места для имени/описания/baseline/dev-статуса; невозможен уровень «Продукты»; каждая регистрация — это регистрация изменения | Не отвечает видению; не поддерживает переиспользование baseline и мультипродуктовость |
| Хранить продукты как узлы Product Baseline в git без агрегата в state store | Git — источник истины, минимум БД | Нет быстрого read-model списка/статусов, нет связи с изменениями и планировщиком | Продукт — operational-сущность (статусы, dev-контур), а не только документ |
| Внешний каталог (Plane/сторонний реестр) как источник продуктов | Меньше кода | Трекер отключаем и не блокирует конвейер (FR-020); продукт — не задача | Зависимость от внешней системы в критическом пути |

## Последствия

**Позитивные**

- Появляется уровень «Продукты», из которого начинается любое изменение; baseline и активные изменения получают область видимости.
- Провижининг репозитория и его статус перестают быть операторским скриптом — становятся наблюдаемой частью продукта.
- Мультипродуктовость и мультирепозиторность выражаются в модели, а не в соглашениях.

**Негативные / риски**

- Миграция и обратная совместимость изменений пилота (изменения без `product_id`); требуется аккуратность при backfill.
- Ещё одна сущность с правами и аудитом — нужно согласовать scope токена с существующими (`changes:write`, `approvals:write`).
