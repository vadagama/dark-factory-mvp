# ADR-032: Phase projection over Flow stages

- **Статус**: принято
- **Дата**: 2026-09-19
- **Автор**: architect
- Решение согласовано оператором 2026-09-19 (вопрос 4): Phase-проекция допустима, если не ломает описанную логику процесса.

## Контекст

- Оператор описывает 8 пользовательских фаз: Инициатива, Требования, Архитектура, Интерфейс, План, Исполнение, Демонстрация и проверка, Доставка.
- Ядро имеет 5 стадий `Flow`: `specification → planning → construction → review_verification → release` (`src/dark_factory/changes/enums.py`), с неизменяемой таблицей переходов, идемпотентностью по `operation_key` и гейтами (ADR-005, ADR-006).
- Фазы участия человека уже зафиксированы ADR-018 п.1, а четыре человеческие точки контроля — ADR-023 п.4 (`problem`, `solution`, `ux`, `discovery_release`); ADR-029 п.2 перенёс `ux` в фазу проектирования (стадия `specification`, гейт `ui`).
- Наивное решение — добавить `Stage.INTENT`/`DESIGN`/`UI` — потребовало бы правок таблиц переходов, миграций enum, ревизии CI-шаблонов («один job = одна стадия») и пересмотра ключей идемпотентности. Выгоды нет: пользователю нужна навигация, а не новые состояния исполнения.

## Решение

1. `Stage` **не расширяется**. Вводится **`Phase`** — проекция над существующими стадиями и точками контроля, вычисляемая из состояния ChangeSet:

| Фаза | Стадия | Точка контроля / гейт | Источник артефакта |
|---|---|---|---|
| Ф0 Инициатива | до запуска (intake) | — | бриф оператора |
| Ф1 Требования | `specification` | `problem` / `specification` | дельта требований, вопросы |
| Ф2 Архитектура | `specification` | `solution` (ADR-029) | ADR, design |
| Ф3 Интерфейс | `specification` | `ux` / `ui` (ADR-029) | UI-спеки, экраны |
| Ф4 План | `planning` | `solution` / `planning` | Implementation Contract, задачи |
| Ф5 Исполнение | `construction` | автономно | код, MR, CI |
| Ф6/Ф7 Демонстрация | `review_verification` | `discovery_release` / `review` | AC, evidence, превью |
| Ф8 Доставка | `release` | `release` + reconciliation | dev, smoke, baseline |

2. `Phase` — **read-model**: не влияет на переходы, не хранит собственных переходов и не может разрешить запрещённый переход. Единственный источник правды о переходах — таблица `Flow` (ADR-005).
3. Фазы Ф2 и Ф3 разделяются внутри одной стадии `specification` по факту наличия и согласованности артефактов проектирования (ADR/ui) и по точкам контроля `solution`/`ux`; Ф6 и Ф7 объединяются в пользовательскую область «Демонстрация и проверка», оставаясь раздельными во внутренней модели.
4. Каждая фаза объявляет **предусловия гейта** (что должно быть истинно для согласования) и **следующее действие** — так фаза становится единицей навигации и единицей диалога с оператором ([ADR-033](ADR-033-operator-guidance.md)).
5. Согласование фазы остаётся версионно привязанным человеческим решением на соответствующем гейте (ADR-009 п.7, ADR-023 п.5); пропуск фазы фиксируется явно с основанием (например, UI не требуется для backend-only изменения).

## Альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| Расширить `Stage` до 8 значений | «Честная» модель, фаза = стадия | Правки таблиц переходов, enum, миграций, CI-шаблонов, ключей идемпотентности; дублирует уже существующие точки контроля ADR-023 | Дорого и не даёт пользовательской ценности |
| Только UI-представление фаз без проекции в ядре | Нет изменений ядра | Логика навигации и «следующего шага» разъезжается между CLI и Console | Противоречит принципу единого источника (ADR-033) |
| Оставить 5 стадий как единственную единицу навигации | Ничего не делать | Оператор не понимает, чего от него ждут на `specification` (требования? архитектура? UI?) | Именно это наблюдается в пилоте T043 |

## Последствия

**Позитивные**

- Пользовательская модель (8 фаз) и исполняемая модель (5 стадий) согласованы без переписывания движка.
- «Следующий шаг» может вести по фазам, включая разделение архитектуры и UI внутри `specification`.
- Существующие ADR-018/023/029 переиспользуются, а не дублируются.

**Негативные / риски**

- Две модели (фаза и стадия) требуют явного маппинга и тестов на согласованность; при добавлении стадии маппинг обязан обновляться.
- Разделение Ф2/Ф3 внутри одной стадии опирается на артефакты — нужна аккуратная детекция «артефакт отсутствует» vs «артефакт не согласован».
