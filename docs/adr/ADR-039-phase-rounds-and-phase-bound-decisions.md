# ADR-039: Пофазные раунды стадии `specification` и привязка решений к фазе

- **Статус**: принято
- **Дата**: 2026-09-19
- **Автор**: architect
- Решения согласованы оператором 2026-09-19 при старте M3 (T092–T099): пофазные раунды внутри одной стадии; `Decision.phase` вместо нового значения `Gate`; карточка решения — read-model над ADR-файлом в git; статус ADR производный; UI-спека — markdown с frontmatter на узел; «UI не требуется» предлагает архитектор, подтверждает оператор; галерея экранов — текстовые карточки; mermaid в Console. Уточняет [ADR-029](ADR-029-human-gates-at-design-phase.md) п.1/п.4 (гейты `specification` и `ui` на design-стадии), [ADR-032](ADR-032-phase-projection.md) п.3 (разделение Ф2/Ф3 внутри `specification`), [ADR-034](ADR-034-conversations-and-rework-orders.md) п.3 (поручение по конкретному решению) и [ADR-035](ADR-035-document-artifacts-git-source-of-truth.md) п.7 (staleness по ревизии фазы). Не меняет [ADR-005](ADR-005-stage-scoped-graphs-light-workflow-core.md) (таблица переходов остаётся единственным источником правды о переходах) и [ADR-023](ADR-023-risk-classes-and-control-points.md) п.1 (`Gate` не расширяется).

## Контекст

- ADR-032 объявил восемь пользовательских фаз проекцией над пятью стадиями и постановил, что Ф2 «Архитектура» и Ф3 «Интерфейс» живут внутри одной стадии `specification` и различаются «по факту наличия и согласованности артефактов проектирования и по точкам контроля `solution`/`ux`». Как именно стадия порождает эти артефакты и как записать согласование архитектуры отдельно от согласования требований, ADR-032 не определял; в M2 стадию целиком вёл `product` со скиллом `spec-authoring`, а «Согласовать требования» был единственным гейтом фазы.
- Оба человеческих гейта стадии (`specification`, `ui`, ADR-029) записываются как `Decision{gate, commit_sha}`. Согласование требований и согласование архитектуры ложатся на один гейт `specification` — по гейту их не различить. Расширять `Gate` запрещено ADR-023 п.1 (гейт связан с матрицами маршрутов и CHECK-констрейнтами).
- Согласование привязано к ревизии (ADR-009 п.7, ADR-035 п.7). Если ревизия фазы — голова ветки изменения, то коммит архитектора делает согласование требований неактуальным, хотя `spec/**` не менялся; оператору пришлось бы согласовывать требования заново после каждого раунда.
- Оператор требует «Запросить альтернативу» без ухода с экрана и по конкретному решению (T093), честный статус неавтоматизируемых проверок UI (axe, visual regression — T097) и явный пропуск фазы UI для backend-only изменений (ADR-032 п.5).

## Решение

1. **Стадия `specification` исполняется раундами по фазам**: `requirements` → `architecture` → `interface`. Раунд — новая операция той же стадии (свой `input_revision` = голова ветки изменения, своя попытка), роль и скилл раунда выбираются по фазе: `product`/`spec-authoring`, `architect`/`solution-design`, `design`/`ui-spec` (`orchestration/stages/agent.py: PHASE_ROLE`, `PHASE_SKILL`). `Stage` не расширяется; `StageContext.phase` и `StageResult.phase` несут фазу раунда (аддитивно, схема записи не меняется).
2. **Текущая фаза стадии вычисляется, а не хранится**: первая фаза без действующего решения (`orchestration/phases.py: specification_phase`). Действующее решение — `approved`, привязанное к текущей ревизии артефактов фазы, или `waived`. Все фазы согласованы — стадия завершена. Набор фаз определяет маршрут: `interface` есть только там, где маршрут требует гейт `ui` (на `quick` фаза «не требуется» политикой маршрута — это факт маршрута, не решение человека).
3. **`Decision.phase`** (nullable, миграция `0007_phase_rounds`) различает решения на общем гейте `specification`. `NULL` — решение до M3, читается как фаза своего гейта (`phase_of_gate`). API `POST /changes/{id}/approvals` принимает `phase` и проверяет его согласие с `gate` (422 при расхождении); `factory change approve --phase architecture` работает без изменений интерфейса команды.
4. **Ревизия фазы — последний коммит, тронувший её артефакты** (`spec/**` — требования; `design/**` без `design/ui` — архитектура; `design/ui/**` — интерфейс). `PhaseGate.current_revision` фазы стадии `specification` — ревизия фазы, согласование привязывается к ней; коммит раунда другой фазы согласование не устаревает, правка артефактов самой фазы — устаревает (DoD T099). Прочие фазы по-прежнему привязаны к голове ветки.
5. **Новый вариант `NextAction` — `phase_round`** (`PhaseRoundAction{phase}`), разрешён только для `specification` в `FLOW_TRANSITIONS`. Согласование нефинальной фазы завершает ожидающую попытку статусом `succeeded` без результатов гейтов и заново входит в ту же стадию для следующего раунда — раунд доработки при этом **не** тратится (это прогресс, не возврат). Согласование (или пропуск) последней фазы завершает стадию: `specification` — `passed`, `ui` — `passed` или `skipped` (при `waived`). Наблюдение резолюции (`GateObservation.phase`, `next_phase`) собирает store-слой (`state/conversations.py: with_store_facts`): `phase` — раунд, которому принадлежит ожидающий checkpoint (`StageResult.phase`), а не «первая несогласованная фаза» по решениям — согласование, записанное после раунда, резолвит именно этот раунд (живой прогон T099: иначе ожидание не резолвилось никогда); `next_phase` — следующий раунд маршрута. Поиск committed-результата операции учитывает `input_revision`: раунды одной стадии начинают нумерацию попыток заново.
6. **Пропуск фазы UI**: архитектор пишет в frontmatter `design/overview.md` `ui: not_required` + `ui_reason`; гейт фазы `interface` показывает «Не требуется: <основание>» с источником (`route | agent | operator | default`) и предлагает ровно одно действие — подтвердить пропуск решением `waived` (ADR-018: человеческий гейт закрывает человек). Пропуск может быть записан без `subject_revision`: он относится к фазе, а не к документу. Раунд `design` при этом не запускается.
7. **Честный статус неавтоматизируемых проверок**: `PhaseGate.checks` для фазы `interface` перечисляет `axe` и `visual_regression` со статусом `planned` («запланировано на исполнении») — зелёного статуса до реализации нет; при `ui: not_required` или пропуске — `not_required`.
8. **Карточка решения — read-model над ADR в git** (`context/decisions.py`): frontmatter (`id`, `status`, `impact`) и секции по заголовкам (Решение/Обоснование/Альтернативы/Последствия). Статус карточки **производный**: `accepted` — действующее согласование фазы `architecture`; `needs_revision` — открытое поручение по этому решению или устаревшее согласование; `superseded` — из frontmatter; иначе `proposed`. Согласование не пишет `accepted` в файл: оно не порождает коммит и не устаревает само себя.
9. **«Запросить альтернативу»** — `ReworkOrder` фазы `architecture` с `decision_ids` (`POST /changes/{id}/decisions/{adr}/alternative`, `factory change alternative`): отказ относится к конкретному решению, идёт через существующий ограниченный цикл доработки (ADR-034 п.3) и записывает `rejected`-решение фазы. После пересмотра показаны затронутые артефакты (файлы, изменённые после ревизии поручения).
10. **UI-спека — markdown с YAML frontmatter на узел**: `design/ui/scenarios/SCN-NNN-*.md` (шаги `S<n>` со ссылкой на экран) и `design/ui/screens/SCR-NNN-*.md` (`route`, `preview_url`, пять состояний `loading|empty|error|success|access`, элементы `EL-*` с компонентом UIKit, `transitions`). Идентификаторы `SCN-/SCR-/EL-/S<n>` — стабильные якоря комментариев; потерянная привязка — `detached` (ADR-034). Read-model — `GET /changes/{id}/ui`; галерея экранов в M3 — текстовые карточки, dev-ссылка из `preview_url` (префикс `dev_url` baseline), иначе честное «dev-окружение появится после доставки».
11. **Проекция фаз — один источник для CLI и Console**: `GET /changes/{id}/phases` / `factory change phases` отдают восемь фаз с состоянием (`pending | active | needs_decision | approved | waived | not_required | stale | done | blocked`), ревизией фазы, счётчиками и итерацией; Console рендерит её и не вычисляет состояние сам (ADR-037 п.5–6).

## Экраны Ф2/Ф3 (условие ADR-037, роль `design`)

- **Ф2 «Архитектура», вкладка «Результат»**: обзор `design/overview.md` (документ, ```mermaid``` рендерится в режиме «Документ», в «Markdown» — исходник); ниже — карточки решений: заголовок, id, статус, предложение, обоснование, таблица альтернатив, последствия, влияние, ревизия; действия «Открыть ADR» (редактор) и «Запросить альтернативу» (inline-форма на карточке: инструкция + выбор открытых замечаний; 409, пока другое поручение фазы открыто). Карточка с открытым поручением показывает его статус, после раунда — сводку «что изменил / что осталось» и затронутые артефакты. Нижняя панель — единственная CTA из `Guidance` («Согласовать архитектуру»).
- **Ф3 «Интерфейс», вкладка «Результат»**: подвкладки `Сценарии / Экраны / Связи`, по умолчанию «Сценарии» (карточки шагов со ссылками на экраны); «Экраны» — галерея карточек: id, маршрут, назначение, пять состояний (отсутствующее — явная пометка «не описано»), элементы с компонентами и комментарием к элементу (якорь `EL-*`, `detached` показан явно), «Открыть на dev» или честный текст; «Связи» — таблица переходов. Вкладка «Проверки» — `checks` (`planned` не зелёный), блок `ui_requirement` и «Подтвердить пропуск UI».
- Левая колонка фаз — из `GET /changes/{id}/phases`; процента готовности нет.

## Альтернативы

| Вариант | Плюсы | Минусы | Почему не выбран |
|---|---|---|---|
| Один раунд `product` пишет спеку, ADR и UI сразу | Быстрее, без изменений в flow | Качество ADR/UI хуже, «Запросить альтернативу» переписывает всё, роли `architect`/`design` не задействованы | Противоречит ролевой модели ADR-007 и цели M3 |
| Три отдельные стадии вместо раундов | Явные переходы | Расширяет `Stage` и таблицу переходов, ломает контракты записей и маршрутов | ADR-032 п.1–2: `Stage` не расширяется |
| Новое значение `Gate.SOLUTION` | Простая фильтрация решений | Нарушает ADR-023 п.1, трогает матрицы маршрутов и CHECK-констрейнты | Достаточно `Decision.phase` |
| Отдельная таблица `phase_approval` | Не трогает `decision` | Два источника решений, дублирование version-bound логики | Один источник решений |
| Таблица решений в БД как канон, ADR — рендер | Структурные запросы | Второй канон SDD-артефактов (против ADR-035/ADR-020) | Git — истина |
| Записывать `status: accepted` в ADR при согласовании | Статус виден в git | Каждое согласование — коммит, который сам делает согласование stale; нужна атомарность «коммит → decision» | Статус производный |
| Привязывать все согласования к голове ветки | Проще | Раунд архитектора устаревает согласование требований | Ревизия фазы |

## Последствия

**Позитивные**

- Оператор ведёт требования, архитектуру и интерфейс как три согласования с этапными подписями и одним следующим шагом; отказ адресуется конкретному решению.
- Согласование устаревает ровно тогда, когда меняются артефакты его фазы.
- CLI, API и Console читают одну проекцию фаз и один гейт; ничего не вычисляется в UI.

**Негативные / риски**

- Ревизия фазы требует чтения истории коммитов по путям (`RepositoryPort.list_commits(path=…)`) — на GitHub это несколько запросов на проекцию; кэш read-model — кандидат в техдолг при росте.
- `phase_round` — новое ребро в `FLOW_TRANSITIONS` (внутри стадии); тесты таблицы переходов и `assert_never` покрывают его, но записи с `phase_round` не читаются кодом до M3.
- Решения до M3 (`phase = NULL`) читаются как решения фазы своего гейта: изменение, ожидавшее в `specification` при обновлении, продолжит с фазы `architecture`, если согласование требований привязано к ревизии `spec/**`.
