# Figma VS Код HTML, CSS, JS

Да, для вашего сценария это очень хороший вариант. Если Small UIKit достаточно зрелый, то code-first прототипирование может полностью заменить Figma примерно для 80–90% внутренних корпоративных интерфейсов: форм, таблиц, реестров, кабинетов, workflow и мобильных web-интерфейсов.

Но важно разделить:
- **HTML/CSS/JS-прототип** — исполняемое описание интерфейса.
- **Требования** — роли, сценарии, состояния, ограничения и критерии приёмки.

Один только визуальный HTML не заменяет требования полностью.

Главное преимущество: вы устраняете перевод между тремя представлениями:

```plain text
Требования → Figma → программный код
```

Остаётся:

```plain text
Требования → исполняемый интерфейс → промышленная реализация
```

## Как я бы это организовал

Каждый прототип — небольшой статический проект:

```plain text
prototypes/
  order-create/
    index.html
    screen.css
    screen.js
    scenarios.js
    screen.spec.js
```

Назначение файлов:
- `index.html` — композиция экрана из компонентов Small UIKit;
- `screen.css` — только раскладка и допустимые локальные стили;
- `screen.js` — навигация и пользовательские действия;
- `scenarios.js` — данные, роли и состояния экрана;
- `screen.spec.js` — проверяемые сценарии и критерии приёмки.

Например, `scenarios.js` должен содержать не только тестовые данные, но и состояния:

```javascript
export const scenarios = {
  default: {},
  loading: {},
  empty: {},
  validationError: {},
  accessDenied: {},
  backendUnavailable: {},
  readOnly: {}
};
```

Каждое состояние желательно открывать отдельным URL:

```plain text
/order-create?scenario=default
/order-create?scenario=validation-error
/order-create?scenario=access-denied
```

Это позволяет человеку, тестировщику и другому агенту обсуждать не абстрактный «экран заказа», а конкретное состояние.

## Критически важные ограничения для агентов

Без них агенты быстро превратят UIKit в набор визуально похожих, но разных интерфейсов.

1. **Запрет самостоятельного рисования компонентов**

Агент может компоновать существующие `Button`, `Select`, `Table`, `Modal`, но не создавать новый вариант кнопки через произвольный CSS.

1. **CSS только через токены**

```css
.panel {
  padding: var(--small-space-4);
  border-radius: var(--small-radius-md);
  background: var(--small-color-surface);
}
```

Запретить произвольные цвета, размеры шрифтов, тени и `z-index`.

1. **Новый паттерн — только через расширение UIKit**

Если агенту не хватает компонента, он должен сформировать предложение:

```javascript
export const uiKitGap = {
  requestedComponent: "BulkActionToolbar",
  reason: "Групповая обработка выбранных заказов",
  usedOn: ["order-list"]
};
```

1. **Обязательные состояния**

Для каждого экрана агент проверяет:
- загрузку;
- отсутствие данных;
- ошибку;
- отсутствие прав;
- частичные данные;
- мобильную ширину;
- клавиатурное управление;
- длинные казахские и русские тексты.

1. **Доступность как автоматический gate**

Минимальной целью стоит сделать WCAG 2.2 AA. WCAG распространяется не только на статическое содержимое, но и на динамические web-интерфейсы; критерии соответствия формализованы и могут проверяться в CI. [W3C WCAG 2](https://www.w3.org/WAI/standards-guidelines/wcag/)

## Не делал бы vanilla-прототип отдельным миром

Если production-фронт Small построен на React, а UIKit — это React-компоненты, есть риск получить два продукта:
- хороший HTML-прототип;
- заново написанный React-интерфейс, уже отличающийся от прототипа.

Поэтому оптимальная модель такая:
- агент пишет прототип на настоящих компонентах Small UIKit;
- исходники могут быть React/TypeScript;
- для согласования публикуется статическая сборка, состоящая из HTML/CSS/JS;
- потребителю не нужны ни Figma, ни локальная среда разработки.

То есть **формат обмена — HTML/CSS/JS**, но исходная технология не обязана ограничиваться vanilla JS.

Если принципиально нужен именно чистый HTML, UIKit можно представить как Web Components:

```html
<small-page-header title="Заказы"></small-page-header>

<small-select
  label="Магазин"
  name="store">
</small-select>

<small-button variant="primary">
  Создать заказ
</small-button>
```

Web Components обеспечивают браузерные custom elements и изоляцию реализации, однако перевод существующего React UIKit на такую модель потребует отдельной платформенной работы. [MDN: Web Components и Shadow DOM](https://developer.mozilla.org/en-US/docs/Web/API/Web_components/Using_shadow_DOM)

## Чем заменить рабочее пространство Figma

Я бы использовал каталог прототипов на базе Storybook или аналогичную внутреннюю витрину:
- слева — продукты и экраны;
- внутри экрана — состояния;
- переключение desktop/mobile;
- выбор роли пользователя;
- ссылка на спецификацию и задачу;
- кнопка «согласовано»;
- история изменений через Git;
- preview для каждого merge request.

Storybook stories как раз фиксируют варианты и состояния компонентов, поддерживают interaction tests и визуальное тестирование. [Storybook: stories](https://storybook.js.org/docs/9/writing-stories), [Storybook: interaction testing](https://storybook.js.org/docs/9/writing-tests/interaction-testing)

Для защиты от случайных визуальных изменений можно использовать Playwright screenshot snapshots: эталонные изображения хранятся в Git, а CI показывает пиксельные различия. Важно генерировать эталоны в одинаковом окружении, поскольку рендеринг зависит от ОС, браузера и шрифтов. [Playwright: visual comparisons](https://playwright.dev/docs/test-snapshots)

## Где отказ от Figma будет работать хуже

Figma всё ещё удобнее для:
- поиска совершенно нового визуального языка;
- сложных иллюстраций и маркетинговых страниц;
- свободных концептуальных набросков;
- сложной анимации до выбора технологии;
- работы дизайнеров, которые не готовы взаимодействовать с Git и браузерным кодом.

Но для Small, где большинство систем используют общий UIKit и повторяемые enterprise-паттерны, это скорее исключения.

## Моя рекомендация

Я бы принял решение:

> **Small использует executable UI specifications. Согласуемым артефактом является опубликованный интерактивный прототип на компонентах Small UIKit. Figma не является обязательной частью процесса.**

При этом:
- не ограничивать исходники искусственно vanilla HTML;
- публиковать результат как статический HTML/CSS/JS;
- использовать настоящие компоненты UIKit;
- хранить состояния и сценарии рядом с прототипом;
- проверять UIKit-ограничения, accessibility, interaction и visual regression в CI;
- разрешать Figma только как исключение для исследовательского дизайна.

Такой подход особенно хорошо ложится на Software Dark Factory: прототип становится одновременно результатом аналитики, контрактом для реализации, тестовым стендом и входом для следующего агента.
