# UIKit на Radix + Shadcn

Короткий вывод: для SMALL я бы не выбирал между «Small UIKit» и shadcn. Оптимальный вариант — создавать **Small UIKit на React, используя Radix + shadcn как технологический фундамент**. Web Components стоит оставлять только там, где действительно требуется поддержка нескольких frontend-фреймворков.

Важно: shadcn сам определяет себя не как готовую библиотеку компонентов, а как способ построения собственной библиотеки: вы получаете исходный код компонентов и собственный registry для их распространения. Поэтому он хорошо подходит именно как основа Small UIKit. [Документация shadcn/ui](https://ui.shadcn.com/docs)

## Что реально дают Web Components

Главное преимущество — независимость от фреймворка. Один `<small-button>` потенциально можно использовать в React, Vue, Angular, старом портале или обычном HTML.

Также Shadow DOM позволяет защитить внутреннюю разметку и стили компонента от случайного воздействия приложения. Это действительно полезно для встраиваемых виджетов и сильно разнородного ландшафта. [MDN: Shadow DOM](https://developer.mozilla.org/en-US/docs/Web/API/Web_components/Using_shadow_DOM)

React 19 уже полноценно поддерживает Custom Elements, поэтому прежние проблемы с properties значительно уменьшились. Но при SSR React передаёт только примитивные значения как атрибуты, а сложные объекты и функции не сериализует. Это значит, что полноценная серверная отрисовка внутренних Web Components всё равно требует отдельной архитектуры. [React 19: Custom Elements](https://react.dev/blog/2024/12/05/react-19#support-for-custom-elements)

Цена этих преимуществ:
- отдельная модель событий, properties, slots и lifecycle;
- менее естественная интеграция с React context, hooks и формами;
- дополнительные TypeScript-декларации или React-обёртки;
- усложнение SSR, hydration и тестирования;
- Shadow DOM одновременно защищает компонент и затрудняет стилизацию, Tailwind-интеграцию и некоторые виды композиции;
- компоненты фактически приходится реализовывать с нуля, включая accessibility;
- React Native всё равно потребует отдельной реализации.

То есть Web Components оправданы, только если независимость от React является реальным требованием, а не теоретической возможностью.

## Почему нельзя просто разрешить каждой команде докручивать shadcn

Это самый быстрый способ начать, но для 20 команд он быстро приведёт к форкам:
- в одном приложении будет один `Button`, в другом — уже изменённый;
- исправление accessibility придётся разносить по десяткам репозиториев;
- агенты Dark Factory начнут генерировать визуально похожие, но несовместимые варианты;
- дизайн-система фактически превратится в рекомендации;
- миграции между версиями станут отдельным проектом.

Открытый код shadcn — одновременно его преимущество и риск. Поэтому исходники должны копироваться и адаптироваться **один раз — в репозитории Small UIKit**, а не независимо в каждом продукте.

## Рекомендуемая целевая структура

```plain text
Radix primitives
       ↓
shadcn component source
       ↓
@small/ui-react
       ↓
@small/ui-patterns
       ↓
Продуктовые приложения и Dark Factory
```

Предлагаю разделить решение следующим образом:
- `@small/design-tokens`

    Цвета, типографика, интервалы, размеры, радиусы, elevation, breakpoints и CSS variables. Этот слой независим от React и может использоваться также в React Native.
- `@small/ui-react`

    Базовые компоненты Small: Button, Input, Dialog, Select, Tabs, Table и прочие. Реализация на React с использованием Radix и адаптированного кода shadcn. Radix уже предоставляет хорошую основу для keyboard navigation и WAI-ARIA, хотя итоговая проверка всё равно остаётся ответственностью SMALL. [Radix Accessibility](https://www.radix-ui.com/primitives/docs/overview/accessibility)
- `@small/ui-patterns`

    Не просто атомарные компоненты, а корпоративные паттерны: AppShell, PageHeader, фильтры, таблица сущностей, мастер создания, подтверждение операции, offline/error/empty states.
- `@small/icons`

    Единый набор иконок.
- `Small UI Registry`

    Приватный shadcn registry с компонентами, страницами, конфигурациями, правилами и шаблонами. Registry официально предназначен для распространения собственных компонентов и может быть закрытым. [shadcn Registry](https://ui.shadcn.com/docs/registry)
- `Small UI Skill`

    Машиночитаемые правила для Dark Factory: разрешённые компоненты, композиции, UX-инварианты, примеры, запрещённые практики и команды запуска проверок.

Базовые компоненты лучше распространять как версионируемый npm-пакет, чтобы централизованно доставлять исправления. Через registry следует распространять более крупные блоки и шаблоны, которые допустимо включать в код приложения.

## Роль отдельной команды

Отдельная команда Small UIKit нужна, но Web Components для этого не обязательны. Команда должна владеть:
- дизайн-токенами и API компонентов;
- accessibility и UX-инвариантами;
- Storybook как живой спецификацией вместо Figma;
- визуальными regression-тестами;
- browser и responsive matrix;
- changelog, semver и migration guides;
- registry, генераторами и AI-скиллом;
- запретом прямого импорта Radix/shadcn продуктами.

## Итоговое решение для SMALL

Учитывая уже выбранный стек React + TypeScript + Tailwind и ориентацию на Dark Factory:
1. **Не использовать Web Components как основной Small UIKit.**
2. Создать **Small UIKit на React поверх Radix + адаптированного shadcn**.
3. Не разрешать продуктам импортировать Radix или копировать shadcn напрямую.
4. Сделать токены независимыми от React.
5. Web Components выпускать точечно — для встраиваемых виджетов, legacy-систем или реальных non-React потребителей.

Если текущий Web Components UIKit уже зрелый и массово используется, переписывать его сразу не нужно. В таком случае разумна переходная модель: сохранить существующие компоненты, добавить React-адаптеры, а новые сложные компоненты и паттерны развивать в `@small/ui-react`.
