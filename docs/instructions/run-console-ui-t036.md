## Простыми словами: что мы сейчас сделаем

Консоль — **веб-пульт оператора** над REST API фабрики. Пять экранов: список изменений с формой приёмки, карточка изменения, гейты и согласования, бюджеты, настройки. Консоль ничего не решает сама — она вызывает тот же API, что и `curl`: чтение (GET) открыто, записи (POST) требуют Bearer-токен оператора.

Мы поднимем **настоящий кластерный контур**: PostgreSQL уже работает в кластере (bootstrap T029/T040), API и консоль поставятся Helm-чартом в namespace `factory`, а доступ на ваш ноутбук дадим `kubectl port-forward` (штатный локальный путь — Ingress-контроллера в bootstrap нет).

Что **уже работает** как настоящий пульт:

- **приёмка изменений** — создали изменение, оно появилось в списке (POST с дедупликацией);
- **согласования** — записали решение по гейту с привязкой к ревизии (это настоящая авторизация человека, ADR-011: merge — только человек);
- **настройки и справочники** — токен, адрес API, режим фабрики, профили ролей.

Что **пока пустое** (и это честные пустые состояния, а не поломка):

- **прогоны** (стадии, evidence, usage) — в базу API их пока никто не пишет: `factory stage run` исполняет стадию детерминированно и складывает артефакты в `--evidence-dir`, а персистенция run-стейта в PostgreSQL («durable state-store wiring») ещё не сделана (`docs/descriptions/cli.md`). Публикация записи прогона в репозиторий `dark-factory-runs` (`factory run publish`, T-039/T-061) уже есть, но это другой источник: API читает PostgreSQL, поэтому в консоли прогонов не видно;
- **расход бюджетов** — считается по прогонам, а их нет; сами лимиты видны, но в дефолтной политике token/cost не заданы — «не задан», `max_rework_rounds` = 3 (T-062, `docs/descriptions/budget.md`);
- **переключение режима фабрики** — информационный вывод, API для переключения нет.

План:

1. проверим кластерный фундамент (namespace, PostgreSQL),
2. соберём два образа локально и положим в кластер секреты,
3. поставим API и консоль Helm-чартом,
4. прокинем порты и откроем консоль в браузере,
5. примем первое изменение через форму, посмотрим карточку, запишем решение по гейту,
6. попробуем сломать вход и посмотрим, как консоль и API вежливо откажутся.

## Что понадобится

- Docker Desktop с включённым Kubernetes (Settings → Kubernetes → Enable) — **кластер уже должен быть забутстраплен** (namespace `factory`, PostgreSQL, quotas — это делает `deploy/bootstrap/bootstrap.sh`, T029/T040; на машине разработки он уже есть);
- [kubectl](https://kubernetes.io/docs/tasks/tools/) (идёт с Docker Desktop) и [helm](https://helm.sh/) v3+;
- [Node.js 22](https://nodejs.org/) (см. `console/.nvmrc`) с `npm` — для сборки статики консоли;
- [docker](https://www.docker.com/) — для сборки двух образов;
- **клон этого репозитория** и терминал в его корне;
- **Не понадобится**: ключи LLM, ghcr-образ, реальные секреты — токен оператора придумываете сами (это локальный контур).

## Почему собираем образы локально

Chart по умолчанию ссылается на плейсхолдеры `ghcr.io/vadagama/dark-factory:bootstrap` и `ghcr.io/vadagama/dark-factory-console:bootstrap` (`values.yaml`) — это не конкретный образ, а заглушка. CI при этом уже собирает и публикует immutable-образы с тегом `sha-<sha>` (`ci.yml` → `factory-image.yml` / `console-image.yml`, прогон на `main` — зелёный), однако пакеты в ghcr **приватные** (анонимный pull отвечает 401), а в chart нет `imagePullSecrets` — значит, скачать такой образ кластер не сможет, и локальный путь остаётся обязательным. Поэтому для локального прогона мы собираем образы **из клона** и подставляем их в chart через `--set`. Шаг сборки и `--set` станут не нужны, когда chart начнёт ссылаться на опубликованный digest и у подов появится pull-доступ (отдельная работа — T-042; см. «Чего пока нет»).

## Шпаргалка: как консоль читает API

Ошибки API приходят в формате RFC 7807, и консоль показывает их как красные уведомления. Что значат:

| Код | Что значит | Что вы увидите в UI |
|---|---|---|
| 200 (повтор) | такой POST уже был — вернулся прежний результат: приёмка опознаёт изменение по `id` из тела, решение — по `Idempotency-Key` | успех, дубля не будет |
| 201 | запись создана | зелёное уведомление «Изменение создано: chg_…» / «Решение записано: dec_…» |
| 401 | мутация без токена или токен неизвестен | красное уведомление с текстом ошибки; без токена формы просто заблокированы |
| 403 | токен есть, но скоупа нет (или не роль `operator` для решений) | красное уведомление «Scope … is required» |
| 409 | чужая ревизия: `expected_state_revision` не совпал | консоль **молча перечитает карточку и повторит один раз**; при повторе — красное уведомление |
| 422 | тело не прошло валидацию (например, пустой `subject_revision`) | красное уведомление с перечнем ошибок |
| пустой список | прогонов ещё нет — норма: записывать их в базу API пока некому («durable state-store wiring») | серые пустые состояния «нет запусков» |

## Шаг 0. Проверить кластерный фундамент

Убедитесь, что kubectl смотрит на нужный кластер и фундамент жив:

```bash
kubectl config current-context      # например docker-desktop
kubectl -n factory get pods
```

Ожидаемо: `factory-postgres-0` в статусе `Running` — это база фабрики (ADR-004), плюс, возможно, `Completed`-поды `factory-postgres-backup-…` (CronJob бэкапа из bootstrap — это норма, не ошибка). Если namespace `factory` пустой или его нет — сначала прогоните bootstrap кластера: `deploy/bootstrap/bootstrap.sh` (T029/T040), затем вернитесь сюда.

## Шаг 1. Собрать два образа локально

**Образ API** (двухстадийный, воспроизводимый — T-044; `GIT_SHA` попадает в метку образа и в ответы API, `SOURCE_DATE_EPOCH` фиксирует времена файлов):

```bash
docker build -f deploy/ci/image/Dockerfile \
  --build-arg SOURCE_DATE_EPOCH=$(git log -1 --pretty=%ct) \
  --build-arg GIT_SHA=$(git rev-parse HEAD) \
  -t dark-factory:local .
```

**Образ консоли**: сначала собираем статику SPA (`dist/`), потом образ nginx с ней (Dockerfile копирует готовый `dist/` — пропустить сборку нельзя):

```bash
cd console && npm ci && npm run build && docker build -t dark-factory-console:local . && cd ..
```

Проверка:

```bash
docker images | grep dark-factory
```

Ожидаемо: две строки — `dark-factory:local` и `dark-factory-console:local`. Docker Desktop видит локальные образы без registry — кластер сможет их поднять.

## Шаг 2. Положить в кластер секрет с токеном оператора

Chart секреты не создаёт (паттерн T028: секреты живут вне git), поэтому кладём вручную. Значение токена придумайте своё; здесь для примера `dev-operator-token`:

```bash
kubectl -n factory create secret generic factory-api-tokens \
  --from-literal='DARK_FACTORY_API_TOKENS=[{"token":"dev-operator-token","actor":"oleg","role":"operator","scopes":["changes:write","approvals:write"]}]'
```

- Секрет содержит **список** токенов в формате JSON: каждый с ролью и скоупами (`changes:write` — приёмка, `approvals:write` — решения).
- Если секрет уже существует, команда скажет `AlreadyExists` — тогда либо используйте известный вам токен из него, либо пересоздайте: `kubectl -n factory delete secret factory-api-tokens` и повторите команду.

## Шаг 3. Поставить API и консоль Helm-чартом

```bash
helm upgrade --install dark-factory charts/dark-factory -n factory \
  --set image.repository=dark-factory --set image.tag=local \
  --set console.image.repository=dark-factory-console --set console.image.tag=local \
  --set auth.existingSecret=factory-api-tokens \
  --wait --timeout 180s
```

Что здесь что:

- `--set image.*` и `--set console.image.*` — подмена плейсхолдеров ghcr на локальные образы (см. «Почему собираем образы локально»); после починки CI эти четыре флага исчезнут;
- `--set auth.existingSecret=factory-api-tokens` — берём токены из секрета шага 2;
- `--wait` — команда вернётся, когда поды станут Ready (миграции базы выполняются helm-hook'ом до старта API).

При повторных запусках та же команда с флагом `--reuse-values` переиспользует прежние `--set`.

Проверка:

```bash
kubectl -n factory get pods
```

Ожидаемо: `dark-factory-…` (API) и `dark-factory-console-…` — оба `1/1 Running`. Вывод helm закончился строкой-подсказкой (NOTES) с port-forward — это то, что мы делаем в следующем шаге.

## Шаг 4. Прокинуть порты и открыть консоль

Каждый port-forward держит терминал (или запустите их фоново):

```bash
kubectl -n factory port-forward svc/dark-factory 8000:8000          # API
kubectl -n factory port-forward svc/dark-factory-console 8080:80    # консоль
```

Вместо ручных туннелей можно поставить launchd-агентов, которые переживают перезапуск кластера и перезагрузку ноутбука: `deploy/local/port-forward/install.sh` (детали и удаление — README рядом).

⚠️ **Именно `8080:80`**: у консольного Service порт `80` (nginx внутри пода слушает `8080`). Вариант `8080:8080` упадёт с ошибкой «does not have a service port 8080».

⚠️ **Перед проверкой убедитесь, что порты свободны** (на них не остались слушатели старых контуров — например, забытый `port-forward` прошлого прогона или docker-лаборатория из приложения ниже):

```bash
lsof -nP -iTCP:8000 -iTCP:8080 -sTCP:LISTEN
```

Если слушатель есть, а это не `kubectl` — убейте его, иначе curl молча попадёт не в кластер и проверки дадут ложный «зелёный».

Проверка контура:

```bash
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8080/    # → 200
curl -s http://127.0.0.1:8080/api/v1/changes                        # → [] или список
```

Вторая команда важна: она доказывает, что nginx консоли **в кластере** проксирует `/api` на кластерный API. Если здесь 404 — под console не отрендерил конфиг (см. «Чего пока нет», пункт про envsubst).

Откройте в браузере: **http://localhost:8080**

## Шаг 5. Выдать себе токен

Экран **«Настройки»** → поле «Новый токен» → введите `dev-operator-token` → **«Сохранить токен»**.

Ожидаемо:

- зелёное уведомление «Токен сохранён (localStorage, только на этом устройстве)»;
- вместо «Токен не задан…» появится «Текущий токен: ••••••••oken» — виден только **суффикс из 4 символов** (маскировка, чтобы не утечь в скриншоты).

Зачем так: токен хранится только в localStorage вашего браузера и прикладывается **только к POST-запросам**; чтение ходит без него (ADR-021 п.4, SC-008). Потерять кэш — не страшно: вводится повторно.

Ниже на том же экране посмотрите «Режим фабрики» и «Профили ролей» — это снапшот из Python-источников (`console/src/generated/meta.json`); он обновляется отдельной командой и охраняется drift-тестом.

## Шаг 6. Принять первое изменение

На главной странице (**«Изменения»**), форма «Приёмка изменения»:

- **Название**: `My first console change`
- **Провайдер**: `github`
- **Репозиторий (slug)**: `my-org/my-product`
- **Класс риска**: `R1`
- **Описание**: что угодно

Нажмите **«Создать изменение»**.

Ожидаемо: зелёное уведомление «Изменение создано: chg_<12 шестнадцатеричных>», список перезагрузится, в таблице появится строка с колонками ID/Название/Продукт/Риск/Источник(`console`)/Статус(`нет запусков`)/Дата.

Куда делись поля из CLI-версии задания (`change.yaml`)? Консоль собирает `Change` за вас: `source` всегда `console`, ID генерируется в браузере (`chg_` + 12 hex). Дедупликация приёмки — по этому `id`: повтор с тем же `id` вернёт уже существующее изменение с кодом `200`. Заголовок `Idempotency-Key` (UUID v4) клиент добавляет сам, но для приёмки он служит только записью в audit — настоящий дедуп-ключ он даёт у решений (шаг 8).

Нажмите кнопку ещё раз с теми же полями — создастся **второе** изменение (у нового свой ID и свой ключ идемпотентности). Дедупликация защищает от повторной отправки **того же** запроса, а не от сознательного дубля.

Данные упали в **кластерную** PostgreSQL (`factory-postgres`) — они переживут переустановку release и перезапуск Docker Desktop (PVC), так что можно продолжать работу в другой день.

## Шаг 7. Карточка изменения

Кликните по названию изменения в таблице (или откройте `/changes/<id>` напрямую — deep links работают).

Ожидаемо: карточка с заголовком, риском, продуктом; ниже секция прогонов с честным пустым состоянием «У изменения ещё нет запусков». Это не баг: прогоны появятся в консоли, когда run-стейт начнёт персиститься в PostgreSQL («durable state-store wiring», `docs/descriptions/cli.md`). Пока `factory stage run` пишет только артефакты в `--evidence-dir`, а `factory run publish` — запись в репозиторий `dark-factory-runs` (T-039/T-061), который API не читает.

## Шаг 8. Записать решение (согласование)

На карточке перейдите **«Гейты и согласования»** (или `/changes/<id>/gates`). Вверху — пустое состояние «У изменения нет прогонов — гейты появятся после запуска». Но форма «Новое решение (version-bound)» — рабочая и сейчас:

- **Гейт**: `Specification`
- **Решение**: `approved`
- **subject_revision**: короткий SHA любого коммита (например, `git rev-parse --short HEAD` вашего клона фабрики) — ревизия, которую вы авторизуете
- **expected_state_revision**: не трогайте — консоль сама вывела `1` (правило: `1 + число решений`)
- **Комментарий**: «Спецификация согласована»

Нажмите **«Записать решение»**.

Ожидаемо: зелёное уведомление «Решение записано: dec_<hex>», в таблице «Решения» появилась строка (гейт/решение/кем=human/ревизия/когда/комментарий), а `expected_state_revision` в форме обновился на `2` — форма синхронизируется с карточкой после каждой записи.

Смысл привязки к ревизии (ADR-009 п.7): решение авторизует **конкретную** версию. Приедет новая ревизия — прежние допуски больше не действуют, нужно новое решение.

## Шаг 9. Попробуем сломать вход

**9.1. Без токена.** «Настройки» → «Удалить токен» → главная. Форма приёмки заблокирована: поля неактивны, сверху серая подсказка «Мутации недоступны: введите токен оператора…». Того же на экране гейтов: «Запись решения недоступна…». Fail-closed: консоль даже не пытается отправить то, что заведомо отклонят.

**9.2. Неправильный токен.** Верните токен, но с опечаткой (например, `dev-operator-tokem`). Примите изменение — красное уведомление «Ошибка приёмки: A valid bearer token is required». API ответил 401, консоль показала текст ошибки и ничего не создала.

**9.3. Чужая ревизия (409).** На экране гейтов впишите в поле `expected_state_revision` заведомо неверное число (например, `99`) и запишите решение. Уведомление будет «Решение записано: dec_… **(после перечитывания карточки — 409)**»: консоль получила 409, молча перечитала карточку, пересчитала ревизию и повторила запрос с тем же `Idempotency-Key`. Это штатный сценарий (ADR-006 п.4) — 409 означает, что ничего не записалось, поэтому повтор безопасен.

**9.4. (по желанию) Роль `service` не согласовывает.** Если добавить в секрет шага 2 токен роли `service` и перезапустить API (`kubectl -n factory rollout restart deploy/dark-factory`), попытка записи решения даст 403 «The operator role is required» — агенты никогда не аппрувят (api.md, ADR-009 п.7).

## Шаг 10 (по желанию). Проверить API руками

Тот же результат минус UI:

```bash
# Токен читаем в переменную, а не подставляем значение в команду: значение
# остаётся только в секрете шага 2 и в браузере (шаг 5), но не в истории шелла.
read -rsp 'Операторский токен: ' TOKEN; echo

# дедупликация приёмки: изменение опознаётся по `id` из тела, поэтому повтор
# вернёт 200 и тот же change (Idempotency-Key уходит в audit)
curl -s -o /dev/null -w "%{http_code}\n" -X POST http://127.0.0.1:8080/api/v1/changes \
  -H "Content-Type: application/json" -H "Authorization: Bearer $TOKEN" \
  -H "Idempotency-Key: once-only" \
  -d '{"id":"chg_curl_demo1","title":"Curl demo","source":"console","product":{"provider":"github","slug":"my-org/my-product"},"risk_class":"R0"}'
curl -s -o /dev/null -w "%{http_code}\n" -X POST http://127.0.0.1:8080/api/v1/changes \
  -H "Content-Type: application/json" -H "Authorization: Bearer $TOKEN" \
  -H "Idempotency-Key: once-only" \
  -d '{"id":"chg_curl_demo1","title":"Curl demo","source":"console","product":{"provider":"github","slug":"my-org/my-product"},"risk_class":"R0"}'
```

Ожидаемо: на свежей базе — `201`, затем `200` (реплей). На **непустой** базе (а именно такой контур остаётся после прошлого прогона, где `chg_curl_demo1` уже создан) `200` придёт **на оба** запроса: приёмка узнаёт изменение по `id` из тела и возвращает реплей. Чтобы увидеть `201`, поменяйте `id` (например, на `chg_curl_demo2`). Оба запроса идут через консольный nginx (`:8080`) — тот же путь, что и у браузера. API также доступен напрямую: `http://127.0.0.1:8000/docs` (Swagger UI, port-forward из шага 4).

## Docker-лаборатория (без кластера, для разработки консоли)

Канонический рантайм фабрики — Kubernetes (ADR-010), но иногда нужен быстрый контур **без кластера**: правка фронтенда, отладка API на живом `uv`. Это песочница — она не совпадает с продом и **не** проверяет k8s-специфику (readOnlyRootFilesystem, probes, helm). PostgreSQL поднимается в docker, API — прямо из клона:

⚠️ **На хосте нужна libpq** (ADR-022): драйвер — чистый `psycopg` без бинарного колеса, поэтому API из клона (в отличие от образа, где лежит `libpq5`) требует системную библиотеку — без неё первое же обращение к базе падает с `ImportError: no pq wrapper available` (проверено 2026-09-16 на macOS с keg-only формулой `libpq`). Проверка: `uv run python -c "import psycopg.pq; print(psycopg.pq.__impl__)"` → должно быть `python`/`c` (а не ошибка). Лечение на macOS — как в `README.md`: `brew install libpq` и её каталог `bin` в `PATH`; для keg-only установки работает и `export DYLD_LIBRARY_PATH=/opt/homebrew/opt/libpq/lib` (проверено). Кластерного контура (шаги 0–10) это не касается.

```bash
docker run -d --rm --name df-pg \
  -e POSTGRES_USER=dark_factory -e POSTGRES_PASSWORD=dark_factory -e POSTGRES_DB=dark_factory \
  -p 55432:5432 postgres:16.4

DATABASE_URL=postgresql+psycopg://dark_factory:dark_factory@127.0.0.1:55432/dark_factory \
  uv run alembic upgrade head

DATABASE_URL=postgresql+psycopg://dark_factory:dark_factory@127.0.0.1:55432/dark_factory \
DARK_FACTORY_API_TOKENS='[{"token":"dev-operator-token","actor":"oleg","role":"operator","scopes":["changes:write","approvals:write"]}]' \
  uv run factory api serve --host 127.0.0.1 --port 8000
```

Консоль в лаборатории — тот же образ, что и в кластере (проксирует `/api` на ваш локальный API через `host.docker.internal`):

```bash
docker run -d --rm --name df-console -p 8080:8080 \
  -e API_UPSTREAM=host.docker.internal:8000 dark-factory-console:local
```

Дальше — шаги 5–10 без изменений (адрес тот же: http://localhost:8080). Остановка: `docker stop df-console df-pg` и `pkill -f "factory api serve"`. База с `--rm` стирается вместе с контейнером.

⚠️ Не смешивайте лабораторию и кластер: слушатели на `8000`/`8080` ловят curl друг друга (см. предупреждение в шаге 4). Проверяйте `lsof -nP -iTCP:8000 -iTCP:8080 -sTCP:LISTEN` перед тем, как верить проверкам.

## Чего на этом участке конвейера пока нет

Чтобы не искать лишнего:

- **chart не ссылается на опубликованный образ**: CI-воркфлоу (`ci.yml` → `factory-image.yml`/`console-image.yml`) уже зелёный и публикует immutable-теги `sha-<sha>`, но пакеты ghcr **приватные** (анонимный pull — 401), а `imagePullSecrets` в chart нет; поэтому в `values.yaml` стоят плейсхолдеры `:bootstrap`, а k8s-путь требует локальной сборки и `--set` (шаги 1 и 3). Шаги 1 и `--set` исчезнут, когда chart начнёт доставлять опубликованный digest и под сможет его скачать (T-042);
- **envsubst-рендер конфига консоли** — чувствительное место: entrypoint nginx рендерит шаблон в `/etc/nginx/conf.d`, которое read-only при `readOnlyRootFilesystem`. Chart монтирует туда emptyDir (исправлено в revision 2); если когда-нибудь снова увидите «UI открывается, но всё `/api` даёт 404» — проверьте логи пода: `kubectl -n factory logs deploy/dark-factory-console | grep envsubst` — там не должно быть `ERROR: /etc/nginx/templates exists, but /etc/nginx/conf.d is not writable`;
- **прогоны и гейты из прогонов**: run-стейт пока не персистится в PostgreSQL («durable state-store wiring» — `docs/descriptions/cli.md`), поэтому карточка/гейты/бюджеты показывают пустые состояния. T-039/T-061 закрыт, но это публикация записи в репозиторий `dark-factory-runs` (`docs/descriptions/execution.md`), а не запись в базу, из которой читает API;
- **расход бюджетов** — считается по прогонам, которых нет; сами лимиты видны в снапшоте, но по умолчанию не заданы: `DEFAULT_BUDGET_POLICY` не фиксирует ни одного измерения (T-062, `docs/descriptions/budget.md`), поэтому в таблице «не задан», а `max_rework_rounds` = 3;
- **переключение режима фабрики** («С согласованиями»/«Автономно до MR») — только информационный вывод, API нет (ADR-021);
- **Ingress-контроллера в bootstrap нет**: доступ только через port-forward (штатный локальный путь, NOTES.txt chart); Ingress из `values-local.yaml` инертен без контроллера;
- **ручные `kubectl patch` поверх release**: helm upgrade их затрёт — правьте chart, а не живой объект;
- **интерактивные pause/retry/cancel прогонов**, live-обновление — вне скоупа MVP (ADR-021).

## Справочник терминов

| Термин | Простыми словами |
|---|---|
| Console MVP | веб-пульт оператора: 5 экранов над REST API (T036, ADR-021) |
| Namespace `factory` | «квартал» кластера, где живёт фабрика: PostgreSQL, API, консоль |
| Helm release | экземпляр установки chart; `helm list -n factory` покажет его ревизии |
| Chart `charts/dark-factory` | описание того, как поставить API и консоль в кластер (Deployment/Service/миграции) |
| `factory-postgres` | кластерная база фабрики (ADR-004); данные изменений живут здесь, переживают переустановку release |
| Секрет (kubectl) | объект кластера с чувствительными данными; создаётся вне git (T028), chart только ссылается |
| port-forward | туннель «порт ноутбука → сервис кластера»; штатный локальный доступ без Ingress |
| `svc/… 8080:80` | «порт 8080 ноутбука → порт 80 Service»; порт Service ≠ порт контейнера (nginx слушает 8080 внутри пода) |
| Под (pod) | минимальный юнит кластера — работающий контейнер; `kubectl -n factory get pods` |
| ImagePullBackOff | под не может скачать образ; с плейсхолдером `:bootstrap` это норма до подстановки локального образа |
| `readOnlyRootFilesystem` | корень контейнера read-only (безопасность, T029); всё, куда пишет процесс, — отдельные tmpfs/emptyDir |
| envsubst | шаг entrypoint nginx: рендерит шаблон конфига в `/etc/nginx/conf.d`; ему нужен writable emptyDir, иначе `/api`-прокси молча не появится |
| Приёмка / intake | создание изменения через форму (POST `/changes`, `source=console`) |
| `chg_…` | ID изменения: `chg_` + 12 шестнадцатеричных символов, генерируется в браузере |
| `dec_…` | ID записанного решения (approvals) |
| Токен оператора | Bearer-токен для мутаций; живёт в localStorage, маскируется в UI, прикладывается только к POST; список токенов — в секрете `factory-api-tokens` |
| Скоуп | право токена: `changes:write` (приёмка), `approvals:write` (решения) |
| Роль `operator` | человек; роль `service` (агенты) согласовывать не может |
| Гейт | «ворота»-проверка: `specification`, `planning`, `code`, `ui`, `review`, `verification`, `release` |
| Решение (decision) | исход по гейту: `approved` / `rejected` / `waived` |
| `subject_revision` | ревизия, которую авторизует решение (например, SHA); обязательна |
| `expected_state_revision` | оптимистичная блокировка (ADR-006 п.4): консоль выводит её как `1 + число решений`; при 409 перечитывает карточку и повторяет раз |
| Idempotency-Key | заголовок UUID v4, который клиент ставит на каждый POST и который попадает в audit: решения дедуплицируются по нему (повтор → `200` и прежнее `dec_…`), а приёмка — по `id` изменения; второй эффект не создаётся ни в одном случае |
| 409 | «state_revision mismatch»: кто-то записал решение раньше вас; для консоли — сигнал перечитать и повторить |
| meta.json | коммиченный снапшот лимитов/профилей/режима из Python-источников; охраняется drift-тестом |
| nginx-образ | контейнер консоли: раздаёт собранный SPA и проксирует `/api` на API (`API_UPSTREAM`) |
