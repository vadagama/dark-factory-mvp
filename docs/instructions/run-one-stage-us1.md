# Как запустить одну стадию фабрики руками (US1) — без клона репозитория фабрики

**Кому**: оператору фабрики — человеку за клавиатурой.
**Время**: ~7 минут.
**Проверено**: 2026-09-13, фабрика 0.1.0 (коммит `aabc39f88bca03cdd68c8d6ef0401c12ba20413e`), запуск через `uvx`/`uv tool install` из git-URL.
**Фича**: Phase 3 / User Story 1 «Исполнение одной стадии фабрики» (`specs/001-dark-factory-mvp/tasks.md`).

## Простыми словами: что мы сейчас сделаем

«Тёмная фабрика» — конвейер, который превращает задачу в готовый код. Фабрика — это **установленный инструмент** (как `git` или `uv`): ставится один раз, работает из любой папки и не требует клонировать свой репозиторий. Репозиторий фабрики при выполнении ваших задач **не изменяется** — он меняется только собственными задачами самой фабрики.

Ваш проект — отдельная папка (будущий продуктовый репозиторий). В ней живут: задание (`change.yaml`) и протоколы прогонов (`evidence/`). Сейчас на конвейере фабрики работает первый участок (US1): по команде фабрика берёт описание изменения, выполняет **один этап** конвейера и выдаёт «протокол» — что сделано, что проверено, чего ждёт. Никакого ИИ на этом участке нет: всё детерминированно, как калькулятор.

План:

1. установим фабрику как инструмент,
2. создадим свою папку проекта и задание,
3. проверим окружение,
4. запустим этап,
5. посмотрим, что фабрика записала (у вас в проекте),
6. повторим запуск и убедимся, что повтор ничего не ломает,
7. попробуем сломать вход и посмотрим, как фабрика вежливо откажется.

## Что понадобится

- [uv](https://docs.astral.sh/uv/) — менеджер Python-проектов (сам скачает фабрику, создаст ей изолированное окружение и положит команду `factory` на место);
- `git` — стандартный, отдельно ставить обычно не нужно;
- интернет — для первого скачивания фабрики (дальше работает кэш);
- **Не понадобится**: клон репозитория фабрики, ключи LLM, база данных, секреты.

## Шпаргалка: как читать ответы фабрики

Фабрика — программа командной строки. Ответ она даёт текстом и кодом выхода (после команды наберите `echo $?`):

| Код | Слово | Что значит |
|---|---|---|
| 0 | `succeeded` | всё получилось, стадия завершена |
| 10 | `waiting` | всё хорошо, стадия ждёт внешних проверок — это **норма**, не ошибка |
| 20 | `blocked` | стадия не может продолжаться, нужна помощь человека |
| 1 | `failed` | ошибка во время выполнения |
| 2 | — | «я даже не начинал»: неправильный вход или окружение |

Важно не пугаться кода 10: стадия сделала всё, что могла локально, и честно сообщила, кого ждёт.

## Шаг 0. Установка фабрики (без клона)

```bash
uv tool install --python 3.12 \
  git+https://github.com/vadagama/dark-factory-mvp@aabc39f88bca03cdd68c8d6ef0401c12ba20413e
which factory
```

- SHA в конце адреса **фиксирует версию** фабрики — все прогоны воспроизводимы. Чтобы обновиться, повторите команду с новым SHA (флаг `--force`, если версия та же, а нужно переустановить).
- `which factory` должен показать путь вида `~/.local/bin/factory`. Если команда не нашлась — добавьте `~/.local/bin` в PATH (uv подскажет как) или используйте вариант ниже.

Вариант Б — вообще без установки (каждый раз полная команда):

```bash
uvx --python 3.12 \
  --from git+https://github.com/vadagama/dark-factory-mvp@aabc39f88bca03cdd68c8d6ef0401c12ba20413e factory doctor
```

Проверка установки:

```bash
factory doctor
```

Ожидаемый вывод:

```
factory doctor
python_runtime: ok (Python 3.12.13)
package: ok (dark_factory 0.1.0)
state_store_config: warn (DATABASE_URL is not configured; the deterministic local stage (US1) runs without the state store)
summary: status=warn ok=2 warn=1 error=0
```

Предупреждение (`warn`) про базу данных — нормально: для этого сценария база не нужна. Тревожиться стоит только при `error` в summary.

## Шаг 1. Ваш проект и задание

```bash
mkdir -p ~/projects/my-product && cd ~/projects/my-product
```

Создайте файл `change.yaml` — это задание для фабрики (**Change**):

```yaml
id: my-first-change
title: My first factory change
description: >-
  Learning run: one deterministic construction stage without LLM.
source: cli
product:
  provider: github
  slug: my-org/my-product
risk_class: R0
```

Поля простыми словами:

- `id` — имя изменения;
- `product` — какой репозиторий когда-нибудь будем менять (сейчас это просто данные: US1 никуда по сети не ходит);
- `risk_class: R0` — уровень риска, самый низкий.

Сделайте папку git-репозиторием и зафиксируйте задание:

```bash
git init -q
git add change.yaml
git -c user.email=you@example.com -c user.name="You" commit -q -m "init change"
```

Зачем: фабрика обязана записать в журнал прогона точную версию продукта (`product_commit`) — она возьмёт HEAD этого репозитория. Без git-репозитория (или явной переменной, см. шаг 2) стадия с журналом не стартует.

## Шаг 2. Версия фабрики в окружении

```bash
export DARK_FACTORY_COMMIT=aabc39f88bca03cdd68c8d6ef0401c12ba20413e
```

Зачем: в журнале прогона фабрика пишет и свою точную версию (`factory_commit`). Мы работаем не в её репозитории, поэтому сказать версию нужно явно. Переменная живёт до закрытия терминала — если открыли новый терминал, повторите команду.

## Шаг 3. Запуск стадии (главный шаг)

```bash
factory stage run --change ./change.yaml --stage construction \
  --evidence-dir ./evidence --run-id run_manual_demo
```

Ожидаемый вывод:

```
stage construction: waiting (run_id=run_manual_demo, change_id=my-first-change, operation_key=run_manual_demo:construction:10e5d637..., next_action=wait_for_input)
reason: required gates not evaluated: code, ui (machine checks run on the final SHA in CI (FR-009))
```

Код выхода — `10` (`waiting`).

Перевод на человеческий: «Этап construction выполнен настолько, насколько возможно без CI. Жду машинных проверок code и ui — они по правилам выполняются в CI на финальном коде, а не у тебя на ноутбуке».

Длинный код после имени прогона — отпечаток вашего задания (`input_revision`): он зависит от байтов `change.yaml`, поэтому у вас будет свой.

Что значат опции:

| Опция | Смысл |
|---|---|
| `--change` | путь к заданию (yaml-файлу) |
| `--stage` | какой этап конвейера выполнить (`construction` — «строительство») |
| `--run-id` | имя прогона — придумываете вы сами |
| `--evidence-dir` | папка для документов прогона (мы кладём в свой проект) |
| `--json` | добавить, если хотите полный протокол в JSON |

Увидели `waiting` (код 10) — шаг пройден.

## Шаг 4. Что фабрика записала (у вас в проекте)

```bash
ls -lT ./evidence
```

Три файла:

- `change_snapshot.yaml` — фотокопия задания «как было на входе»;
- `stage_result.json` — протокол стадии;
- `run_record.json` — журнал запуска.

Откройте журнал:

```bash
cat ./evidence/run_record.json
```

На что смотреть глазами:

- `manifest.factory_commit` — точная версия фабрики (ваш `DARK_FACTORY_COMMIT`); фабрика всегда фиксирует точные версии, никаких «latest»;
- `manifest.product_commit` — точная версия вашего проекта (сравните с `git rev-parse HEAD`);
- `run.budget` — лимиты прогона (например, максимум 3 раунда доработки);
- `tokens_used: 0` — ИИ не вызывался, потрачено ноль.

Файлы лежат в вашем проекте — решайте сами: закоммитить как доказательства или добавить `evidence/` в `.gitignore`.

## Шаг 5. Главный фокус: повторный запуск ничего не делает заново

Повторите команду из шага 3 **слово в слово**, затем снова:

```bash
ls -lT ./evidence
```

Вывод команды тот же, код снова `10`. А теперь самое интересное: **время изменения файлов не обновилось** (смотрите колонку с датой). Значит, второй запуск реально не выполнял работу — он узнал «себя» по имени прогона и вернул уже готовый результат.

Это называется **идемпотентность**: одинаковый запуск можно смело повторять — работа не задвоится. Для этого нужны два условия:

- одинаковое `--run-id` (имя прогона);
- одинаковый `--evidence-dir` (там хранится готовый результат).

Что будет, если условия нарушить:

- убрать `--run-id` — фабрика придумает новое имя → это уже другая операция → работа выполнится заново;
- убрать `--evidence-dir` — фабрике негде хранить результат → всегда выполняется заново.

## Шаг 6. Попробуем сломать вход

```bash
factory stage run --change ./no-such-change.yaml --stage construction
echo $?
```

Ожидаемо — фабрика не начала работу и вежливо отказалась:

```
factory stage run: cannot read change snapshot './no-such-change.yaml': No such file or directory
```

Код выхода — `2`. Хороший отказ: ранний, понятный, без «полузавершённой работы».

Второй негативный сценарий — если запустить без `DARK_FACTORY_COMMIT` в папке, где нет git-репозитория, фабрика тоже откажется (код `2`): «cannot determine the factory commit: set DARK_FACTORY_COMMIT (or GITHUB_SHA) to the exact commit». Это защита воспроизводимости: без точной версии фабрики журнал прогона был бы бесполезен.

## Шаг 7 (по желанию). Ещё немного экспериментов

- **Другой этап**: замените `--stage construction` на `--stage specification` — снова `waiting`, но ждать будет проверка `specification`.
- **Полный протокол**: добавьте `--json` — получите протокол в JSON (удобно копировать в отчёт).
- **То же самое в CI**: в репозитории фабрики есть джоба `factory-us1-parity`, которая прогоняет те же `doctor` и `stage run` в GitHub Actions — локальный и CI-результаты совпадают, потому что версия фабрики зафиксирована SHA.

## Чего на этом участке конвейера пока нет

Чтобы не искать лишнего:

- фабрика пока **ничего не коммитит в ваш проект сама**: она читает задание и складывает протоколы в `evidence/`; коммиты делаете вы (автосоздание репозитория продукта из blueprint и автоматические MR — задачи T-061/T-070 и US2+);
- команды `stage resume`, `run status`, `reconcile`, `outbox dispatch` пока отвечают «не реализовано» (код 2) — появятся в следующих задачах;
- ИИ-агенты (Product, Developer и др.), веб-консоль — это следующие user stories (US2+).

## Справочник терминов

| Термин | Простыми словами |
|---|---|
| Стадия | этап конвейера: `specification → planning → construction → review_verification → release` |
| Change / снапшот | yaml-файл с заданием: что меняем, где, какой риск |
| `StageResult` | протокол выполнения стадии: статус, следующий шаг, проверки |
| Гейт | «ворота»-проверка; стадия не завершится, пока ворота не пройдены |
| `waiting` (код 10) | «сделал всё локально, жду внешних проверок» — норма |
| `run_id` | имя прогона, придумываете вы |
| `operation_key` | паспорт операции: имя прогона + стадия + отпечаток задания |
| `input_revision` | отпечаток задания: по нему фабрика отличает одно задание от другого |
| Evidence | папка с документами прогона: копия входа, протокол, журнал |
| `factory_commit` | точная версия фабрики в журнале прогона (`DARK_FACTORY_COMMIT`) |
| `product_commit` | точная версия вашего проекта в журнале прогона (git HEAD) |
| `DARK_FACTORY_COMMIT` | переменная окружения: сообщает фабрике её собственную версию |
| Идемпотентность / replay | повтор того же запуска не делает работу заново |
| `uvx` / `uv tool install` | запуск/установка Python-инструмента из git-URL без ручного клонирования |
