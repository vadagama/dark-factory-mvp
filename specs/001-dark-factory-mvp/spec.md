## User Scenarios & Testing *(mandatory)*

### User Story 1 - Исполнение одной стадии фабрики (walking skeleton) (Priority: P1)

Оператор запускает одну стадию фабрики (например, реализацию или проверку) как локально через CLI, так и через job в CI-провайдере (MVP — GitHub Actions; GitLab — второй провайдер, ADR-019) — без обращения к LLM. Фабрика исполняет стадию, публикует типизированный результат этапа (статус, ссылки на артефакты, расход, следующее допустимое действие) и запись запуска. Процесс не требует постоянно работающего сервиса: ожидание завершает job, продолжение возможно новым запуском.

**Why this priority**: Это фундамент конвейера: контракты стадий, публикация результатов и одинаковый запуск локально/в CI нужны всем остальным сценариям. Без него фабрика не существует.

**Independent Test**: Может быть полностью проверено запуском одной стадии с валидным входом локально и в CI без LLM; ценность — работающее ядро с наблюдаемым результатом.

**Acceptance Scenarios**:

1. **Given** инициализированная фабрика и валидный вход стадии, **When** оператор запускает стадию через CLI локально, **Then** стадия исполняется, публикуются StageResult (статус, ссылки на артефакты, расход, следующее допустимое действие) и запись запуска (manifest + результат + ссылки на evidence), доступные из Git/CI.
2. **Given** тот же вход, **When** та же стадия запускается через CI job (MVP — GitHub Actions), **Then** выполняется тот же релиз ядра, результат эквивалентен локальному, а долгое ожидание освобождает runner.
3. **Given** LLM endpoint недоступен, **When** стадия состоит из детерминированных шагов (сборка контекста, машинные проверки, агрегация, решение о доработке), **Then** они исполняются без LLM и результат публикуется.

### User Story 2 - От задачи к согласованной спецификации (Priority: P2)

Оператор (или событие трекера) подаёт задачу; фабрика нормализует её, фиксирует снапшот задачи (scope, ограничения, репозиторий, контекст), агент Product уточняет требования и публикует MR с proposal'ом изменения (требования, критерии приёмки, открытые вопросы либо утверждённые допущения). Человек согласовывает конкретную ревизию спецификации; без согласования реализация не начинается.

**Why this priority**: Спецификация — контракт человека с агентами (docs/hld.md): контроль значимых решений до генерации кода. Это второй обязательный камень конвейера.

**Independent Test**: Подать задачу → получить MR с proposal'ом → согласовать → убедиться, что реализация разрешена только для согласованной ревизии.

**Acceptance Scenarios**:

1. **Given** новая задача из Console, CLI или трекера, **When** выполняется intake, **Then** создаётся идентификатор изменения и снапшот задачи (цель, scope, ограничения, repo, закреплённый контекст), зафиксированный в записях запуска.
2. **Given** снапшот задачи, **When** агент Product выполняет уточнение, **Then** формируется proposal изменения с проверяемыми критериями приёмки, ролями, обработкой ошибок и открытыми вопросами либо допущениями, публикуемый MR'ом.
3. **Given** proposal с неразрешёнными критическими вопросами, **When** человек не согласовывает ревизию, **Then** реализация блокируется gate'ом, статус — ожидание ввода, занятый runner отсутствует.
4. **Given** согласование получено, **When** процесс переходит к реализации, **Then** согласование связано с конкретной ревизией (SHA) спецификации; изменение ревизии инвалидирует согласование.

---

### User Story 3 - Агентная реализация с независимым review и ограниченным rework (Priority: P3)

На согласованной спецификации фабрика реализует изменение пилотного продукта: агент-исполнитель работает в изолированном рабочем пространстве и ветке, независимый reviewer (отдельный контекст) возвращает замечания, исправления идут в том же MR, обязательные машинные проверки выполняются на итоговом SHA, ограниченное число раундов доработки и общий бюджет попытки. Merge — ручной либо доверенным финализатором по правилам.

**Why this priority**: Производство кода агентами с проверяемым качеством — главная ценность фабрики (docs/vision-2026-09-13-v1.md: стабильное качество, автономность).

**Independent Test**: На согласованной спецификации одного небольшого изменения пройти цикл реализация → review → rework → зелёный CI → merge; проверить соблюдение лимитов.

**Acceptance Scenarios**:

1. **Given** согласованная ревизия спецификации, **When** выполняется реализация, **Then** каждый исполнитель работает в отдельном workspace/ветке, результат — commit и MR с описанием, ссылками на спецификацию и evidence.
2. **Given** MR с реализацией, **When** выполняется независимое review, **Then** замечания формализованы (id, источник, severity, файл/строка, проверяемый SHA, требуемое действие, статус) и включают человеческие комментарии MR как данные.
3. **Given** блокирующие замечания и доступный лимит раундов, **When** выполняется доработка, **Then** исправления идут в тот же MR; новый SHA делает прежние проверки устаревшими, и обязательные проверки повторяются.
4. **Given** исчерпан лимит раундов (по умолчанию 3) или бюджет попытки, **When** доработка невозможна, **Then** попытка завершается статусом Blocked с причиной и evidence; решение передаётся человеку.
5. **Given** итоговый SHA, **When** выполняются обязательные проверки (стиль, типы, модульные тесты), **Then** все они зелёные именно на этом SHA; итоговое резюме агента не заменяет машинные результаты.
6. **Given** две независимые задачи одного этапа, **When** используется параллельное исполнение, **Then** параллельно не более двух агентов, патчи интегрируются последовательно, проверки повторяются на объединённом SHA.

### User Story 4 - Автономный MR-контур и merge по правилам (Priority: P4)

При включённом расписании периодической сверки фабрика сама продолжает активные инициативы: перечитывает состояние MR и CI, запускает разрешённые попытки, объединяет результаты независимого review и человеческих замечаний. Для явно разрешённого класса изменений доверенный финализатор выполняет merge; всё остальное требует человека.

**Why this priority**: Сокращает ручные операции между шагами (docs/vision-2026-09-13-v1.md: Human Off The Loop), но зависит от US3.

**Independent Test**: Включить расписание сверки и правила merge; провести инициативу от реализации до merge без ручного запуска промежуточных шагов; проверить, что изменения вне разрешённого класса требуют человека.

**Acceptance Scenarios**:

1. **Given** расписание сверки включено и инициатива активна, **When** изменились состояние CI или замечания, **Then** сверка перечитывает MR/SHA/CI/замечания/записи запусков и запускает не более одной разрешённой попытки; вебхук только ускоряет реакцию.
2. **Given** изменение разрешённого класса (согласованная спецификация, зелёный CI, независимое review без блокеров), **When** правила merge разрешают, **Then** доверенный финализатор выполняет merge с проверкой ожидаемого SHA перед операцией.
3. **Given** изменение вне разрешённого класса (права доступа, CI-конфигурация, критерии приёмки, рискованные миграции данных), **When** наступает merge, **Then** требуется явное согласование человека; отсутствующие или неоднозначные правила трактуются как ручной режим.
4. **Given** повторное событие вебхука, **When** выполняется сверка, **Then** дубликаты действий не создаются: перед повтором выполняется поиск существующего MR/эффекта по идентификатору изменения.

---

### User Story 5 - Релиз в dev через GitOps (Priority: P5)

После merge фабрика собирает образ с неизменяемым digest, предлагает GitOps-изменение с этим digest, целевая GitOps-система применяет версию в dev-среде, smoke-проверка подтверждает работоспособность; только после успешного smoke задача помечается как выпущенная.

**Why this priority**: Замыкает ценность — результат доезжает до работающей среды (docs/vision-2026-09-13-v1.md: от идеи до результата). Зависит от US3/US4.

**Independent Test**: После merge пилотного изменения проверить цепочку сборка → GitOps MR → деплой → smoke → статус «выпущено»; провал smoke не даёт статус «выпущено».

**Acceptance Scenarios**:

1. **Given** принятый MR, **When** post-merge pipeline завершается, **Then** собран образ с неизменяемым digest и подготовлен GitOps-запрос на изменение.
2. **Given** GitOps-изменение принято, **When** целевая система применяет версию, **Then** пилотное приложение развёрнуто в dev-среде той же версией.
3. **Given** деплой выполнен, **When** smoke-проверка проходит успешно, **Then** задача переводится в статус «выпущено»; при провале — статус неуспешного релиза с диагностикой и решением человека.

---

### User Story 6 - Контекст, знания, трекер и наблюдаемость (Priority: P6)

Фабрика собирает контекст для агентов из закреплённых источников (репозиторий продукта, база знаний с идеями и документами, архитектурные знания) с фиксацией версий и происхождения. Статусы синхронизируются с одним выбранным трекером через сменный адаптер. Оператор наблюдает в Console за инициативами: текущая стадия, вопросы/блокеры, стоимость, критерии-гейты, ссылки на MR/проверки/evidence.

**Why this priority**: Качество решений зависит от контекста, а прозрачность — условие доверия человека (docs/vision-2026-09-13-v1.md: знания, трассируемость); обогащает, но не блокирует ядро.

**Independent Test**: Для одной инициативы собрать контекст из закреплённых источников (проверить фиксацию версий), синхронизировать статусы с трекером и убедиться, что Console показывает полную картину; отключение трекера не останавливает конвейер.

**Acceptance Scenarios**:

1. **Given** задача со связанными источниками знаний, **When** контекст собирается, **Then** пакет контекста фиксирует закреплённые версии/ревизии и происхождение каждого источника.
2. **Given** задача в трекере, **When** статусы меняются в фабрике, **Then** адаптер обновляет трекер без дублирования задач; недоступность трекера сохраняет выполненную работу и восстанавливается повторной синхронизацией.
3. **Given** активная инициатива, **When** оператор открывает Console, **Then** видны стадия, вопросы/блокеры, стоимость попыток, гейты и ссылки на MR/проверки/evidence; потеря локального кэша Console не влияет на процесс.
4. **Given** принятое изменение, **When** запрашивается трассировка, **Then** восстанавливается цепочка: задача → спецификация (SHA) → план → код (SHA) → проверки → релиз.

### Edge Cases

- Ошибка LLM/API → ограниченный повтор в рамках бюджета текущей попытки; повтор дорогих агентных заданий по умолчанию отключён.
- Job погиб после дорогих шагов → потерянный расход учитывается консервативно; повтор этапа либо явное использование checkpoint.
- MR уже создан → поиск по идентификатору изменения/ветке/сохранённой ссылке; дубль не создаётся.
- Ответ внешней системы потерян → сверка фактического эффекта перед повтором.
- Человек отвечает через несколько дней → этап и его результат сохранены; продолжение новым запуском без занятого runner.
- Трекер или система трассировки LLM недоступны → работа сохраняется; синхронизация повторяется отдельным заданием.
- Деплой неуспешен → статус «выпущено» не ставится; диагностика и решение человека сохраняются.
- Рабочая станция выключена/спит → локальные задания останавливаются; после запуска состояние сверяется и этап повторяется.
- Отмена job → задание прекращается; внешние эффекты проверяются отдельно; выполненный merge не откатывается автоматически.
- Исчерпание бюджета/лимитов → Blocked с причиной и evidence; при неизвестном остатке новые дорогие вызовы блокируются.
- SHA изменился после review → прежние проверки устаревают; обязательные проверки повторяются на новом SHA.
- Конфликт при merge → повторный review/CI либо завершение попытки с блокером.
- Утрачена ссылка на результат предыдущей попытки → продолжение блокируется до подтверждения либо явного повтора проверки.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST принимать задачи из Console, CLI или трекера и фиксировать снапшот задачи (идентификатор изменения, цель, scope, ограничения, репозиторий) до начала любой агентной работы.
- **FR-002**: Система MUST формировать proposal изменения в формате OpenSpec (требования, критерии приёмки, открытые вопросы/допущения) и публиковать его MR'ом.
- **FR-003**: Система MUST требовать явного согласования человека перед реализацией; согласование MUST быть связано с конкретной ревизией спецификации, и её изменение инвалидирует согласование.
- **FR-004**: Система MUST выполнять реализацию агентами в изолированных workspace/ветках; кодовые агенты не имеют прав merge/deploy и не могут менять собственные критерии приёмки.
- **FR-005**: Система MUST ограничивать параллельную работу внутри одного агентного задания двумя агентами и выполнять интеграцию патчей последовательно с повтором проверок на объединённом SHA.
- **FR-006**: Система MUST выполнять независимое review в контексте, отдельном от автора, с формализованными замечаниями (id, источник, severity, расположение, проверяемый SHA, требуемое действие, статус).
- **FR-007**: Система MUST включать человеческие замечания MR в общий набор замечаний; текст обсуждений трактуется как данные и не влияет на права и гейты.
- **FR-008**: Система MUST ограничивать циклы доработки (по умолчанию не более 3 раундов) и общий бюджет попытки; при исчерпании — завершать попытку статусом Blocked с причиной и evidence.
- **FR-009**: Система MUST выполнять обязательные машинные проверки (стиль, типы, модульные тесты) на итоговом SHA; резюме агента не заменяет машинные результаты.
- **FR-010**: Система MUST выполнять merge исключительно доверенным финализатором: человеком либо автоматически для явно разрешённого класса изменений (согласованная спецификация, зелёный CI, независимое review без блокеров); отсутствующая или неоднозначная политика означает ручной режим.
- **FR-011**: Система MUST проверять неизменность ожидаемого SHA перед merge и деплоем; при изменении — останавливать операцию.
- **FR-012**: Система MUST после merge собирать образ с неизменяемым digest, создавать GitOps-изменение и разворачивать пилотное приложение в dev-среду.
- **FR-013**: Система MUST выполнять smoke-проверку после деплоя; статус «выпущено» ставится только при её успехе.
- **FR-014**: Система MUST сохранять результат каждого этапа (статус, артефакты, блокеры, расход, внешние эффекты, следующее действие) и записи запусков: операционное состояние (execution/stage/attempt/lease/outbox/usage) — в хранилище состояния фабрики (ADR-004), evidence — в репозитории записей запусков и CI-артефактах; данные предыдущих попыток не перезаписываются.
- **FR-015**: Система MUST возобновлять процесс между заданиями на основе сохранённых результатов этапов и перечитывания фактического состояния внешних систем; долгое ожидание освобождает runner; без настроенного расписания сверки доступен ручной режим.
- **FR-016**: Система MUST сохранять бюджет, лимиты раундов и дедлайны между запусками одной инициативы; повторный запуск не обнуляет расход.
- **FR-017**: Система MUST обеспечивать идемпотентность внешних эффектов: поиск существующего MR/эффекта перед созданием, сверка фактического результата перед повтором, уникальные идентификаторы попыток.
- **FR-018**: Система MUST резервировать и учитывать расход всех агентов, review и повторов в общем бюджете попытки; неизвестный расход трактуется консервативно и блокирует новые дорогие вызовы до сверки.
- **FR-019**: Система MUST предоставлять Console со списком инициатив и запусков, текущей стадией, вопросами/блокерами, стоимостью, гейтами и ссылками на MR/проверки/evidence; согласования выполняются через внешнюю систему контроля версий либо проверенную операцию от имени авторизованного пользователя.
- **FR-020**: Система MUST поддерживать один сменный трекер-адаптер (MVP — Plane, ADR-013; замена — новым адаптером TrackerPort); отсутствие трекера не блокирует работу через CLI/Console.
- **FR-021**: Система MUST собирать контекст агентов из закреплённых источников (репозиторий продукта, база знаний, архитектурные знания) с фиксацией версий/ревизий и происхождения в пакете контекста.
- **FR-022**: Система MUST запускать один и тот же релиз ядра локально через CLI и в CI; локальные результаты не являются авторитетными для merge сами по себе.
- **FR-023**: Система MUST изолировать агентные задания: временные исполнители без привилегий, минимальные credentials, без доступа к секретам управляющего контура; публикацию, merge и деплой выполняют отдельные доверенные задания.
- **FR-024**: Система MUST фиксировать метрики каждой инициативы: стоимость принятого изменения с учётом попыток, доля принятых с первого прохода, число раундов доработки, время до принятого MR, число ручных вмешательств.

### Key Entities

- **Change**: изменение продукта; идентификатор, снапшот задачи, scope, ограничения, ссылки на спецификацию/согласования/запуски, статус.
- **TaskSnapshot**: нормализованная задача на входе; цель, источник, приоритет, ограничения, закреплённый контекст.
- **RunSnapshot**: версии всех составляющих запуска (flows, роли, skills, правила, packs, harness, модели, SHA репозиториев и спецификаций); активный запуск не подхватывает изменения извне.
- **StageResult**: результат одного этапа; статус, ссылки на выходы, блокеры, расход, внешние эффекты, следующее допустимое действие.
- **TaskEnvelope / AgentResult**: задание агенту (цель, критерии приёмки, входы, разрешённые tools, бюджет, дедлайн) и его структурированный результат (статус, артефакты, evidence, блокеры, расход).
- **AgentProfile**: ролевой профиль (одна из девяти ролей); политика моделей, skills, разрешённые tools, лимиты.
- **FlowProfile**: фазы процесса, привязки ролей к стадиям, политика: параллелизм, раунды доработки, бюджет, human-гейты, режим merge.
- **Finding**: замечание; id, источник (review/человек), severity, расположение, проверяемый SHA, требуемое действие, статус.
- **Approval**: согласование; предмет (ревизия спецификации или SHA кода), согласующий, решение, время.
- **ArtifactRef**: ссылка на артефакт; тип, URI, ревизия, хеш, производитель.
- **ContextBundle**: пакет контекста; источники, закреплённые версии, provenance.
- **RunRecord**: запись завершённой попытки; manifest, итоговый результат этапа, сводка расхода, ссылки на evidence.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: На пилотном продукте сквозной цикл «задача → развёрнутое в dev изменение» выполняется полностью, при этом ручные действия ограничены только явными гейтами (согласование спецификации, merge вне разрешённого класса, production-релиз).
- **SC-002**: Для типового небольшого изменения (feature/bugfix в границах ADR-018 — без изменения публичного API, схемы данных, IAM, без миграций; дифф ≤ 10 файлов и ≤ 200 строк, числа уточняются на планировании) время от согласованной спецификации до принятого MR не превышает одного рабочего дня при доступном согласующем и отсутствии внешних ожиданий.
- **SC-003**: Для каждой инициативы доступен отчёт с измеримыми показателями: стоимость с учётом всех попыток, число раундов доработки, время до принятого MR, число ручных вмешательств.
- **SC-004**: 100% обязательных машинных проверок (FR-009) выполняются на итоговом SHA; ни одно изменение не получает статус «выпущено» без успешной smoke-проверки (FR-013).
- **SC-005**: В сценариях сбоя и повтора (погибший job, повтор вебхука, повторный запуск после долгого ожидания) — 0 дубликатов MR и 0 потерь подтверждённых результатов этапов.
- **SC-006**: При исчерпании бюджета или лимита раундов 100% попыток завершаются статусом Blocked с причиной и evidence; при неизвестном остатке бюджета новые дорогие вызовы блокируются.
- **SC-007**: 100% принятых изменений имеют полную трассируемую цепочку: задача → спецификация (SHA) → план → код (SHA) → проверки → релиз.
- **SC-008**: Весь контур работает на одной рабочей станции одного оператора без постоянно работающего исполнителя процессов; потеря локального кэша Console не влияет на процесс.

## Assumptions

- Один оператор, один пилотный продукт, одно активное агентное задание на инициативу (до двух параллельных агентов внутри задания).
- SC/CI-провайдер: MVP стартует на GitHub (GitHub App, Actions; ADR-019); GitLab 16 доступен как второй провайдер — точная минорная версия и лицензия проверяются перед вторым адаптером.
- Трекер пилота — Plane (self-hosted, webhook + HMAC; ADR-013); замена изолирована TrackerPort. UI-набор пилота — Small UIKit (ADR-014); детали минимума уточняются на фазе планирования.
- Класс изменений для автоматического merge определяется владельцем проекта при включении режима; до этого действует ручной merge.
- Production-релиз вне MVP — всегда отдельное действие человека.
- LLM доступна через внешний endpoint; локальные модели не используются. Бюджетные лимиты (раунды, стоимость попытки) — стартовые и калибруются по пилоту.
- Рабочая станция: одна машина; локальный кластер и задания укладываются примерно в 10–12 GB памяти, одновременность runner — 1 для тяжёлых агентных заданий.
- Пилотный технический профиль — веб-приложение (интерфейс + API + база данных продукта); база данных продукта не является хранилищем состояния фабрики.
- Секреты передаются отдельным механизмом начальной настройки и никогда не попадают в Git.
- Спецификация описывает производственный контур фабрики; имена внешних систем (GitHub, GitLab, OpenSpec, Console, Plane, GitOps-развёртывание) — требования интеграции из `docs/hld.md`, а не выбор внутренней реализации (он выполняется на фазе `/speckit-plan`).
