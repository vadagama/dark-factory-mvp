# Дизайн: рабочее пространство ChangeSet

## Решение в одном абзаце

Добавляем продуктовый слой поверх готового ядра: **продукт** как область работы, **провижининг репозитория**, **intake** с брифом/сценарием/лимитом, **обсуждения и документы** вокруг ChangeSet, **фазы архитектуры и UI**, **план и исполнение**, **демонстрация и доставка**. Движок при этом не переписывается: восемь пользовательских фаз — проекция над существующими стадиями и точками контроля, а «что делать дальше» считается в ядре и лишь рендерится в CLI и Console.

## Ключевые решения

| Решение | Содержание | ADR |
|---|---|---|
| Продукт как область работы | Агрегат `Product` (имя, ссылка на репозиторий, описание, baseline, dev-контур, статус готовности); изменение принадлежит продукту | ADR-030 |
| Провижининг репозитория | Порт `validate` / `ensure_mirror` / `bootstrap_baseline`; адаптеры `LocalMirror` (текущее) и `ProviderClone` (клон на короткоживущем installation-токене GitHub App); пустой репозиторий — штатный случай | ADR-031 |
| Фазы без изменения движка | `Stage` и таблица переходов не меняются; восемь фаз выводятся из стадий и точек контроля (`problem`, `solution`, `ux`, `discovery_release`) | ADR-032 |
| Единый «следующий шаг» | `Guidance` — детерминированная серверная проекция (`headline`, `why`, `primary`, `secondary`, `blockers`, `after`); CLI и Console только рендерят, тупиков нет | ADR-033 |
| Обсуждения | `Question`/`Answer` (choice/text/number), `Comment` с якорем `artifact + anchor_id + revision`, `ReworkOrder`, staleness, «просмотрено» ≠ «согласовано», лимит 3 раунда | ADR-034 |
| Документы | git — источник истины: артефакты ChangeSet живут в `.factory/changes/...`, правка из интерфейса становится коммитом, черновик автосейва — вне git | ADR-035 |
| Помощник merge | Merge остаётся человеческим решением; чек-лист готовности из наблюдаемого состояния, версионно-привязанное решение, merge как явное действие | ADR-036 |
| IA консоли | Три уровня: Продукты → Продукт → ChangeSet; главный экран с фазами, вкладками Результат·Изменения·Проверки·История и панелью решения | ADR-037 |

## Phase-проекция

| Фаза | Стадия ядра | Точка контроля / гейт |
|---|---|---|
| Ф0 Инициатива | до запуска (intake) | — |
| Ф1 Требования | `specification` | `problem` / `specification` |
| Ф2 Архитектура | `specification` | `solution` (ADR-029) |
| Ф3 Интерфейс | `specification` | `ux` / `ui` (ADR-029) |
| Ф4 План | `planning` | `solution` / `planning` |
| Ф5 Исполнение | `construction` | автономно |
| Ф6/Ф7 Демонстрация | `review_verification` | `discovery_release` / `review` |
| Ф8 Доставка | `release` | `release` + reconciliation |

## Границы

**В объёме:** продукт, провижининг, intake, обсуждения и документы, фазы архитектуры и UI, план и управление исполнением, демонстрация по AC, доставка в dev со smoke, помощник merge, CLI и Console поверх одного API.

**Вне объёма (осознанно):** Activity feed (кроме inbox «Требует внимания»), WorkGraph-граф, детект пересечений ChangeSet, Plane-sync, четвёртый режим редактора (Сравнение), axe/visual regression (показываются как запланированные), интерактивный UI-canvas, agent-diff-apply, multi-user auth.

## Декомпозиция

Канонический граф (`tasks/graph.yaml`) держит вехи **M0–M5**; детальный перечень работ — `specs/001-dark-factory-mvp/tasks.md`, Phase 11 (T062–T118, 57 задач), где каждая задача несёт DoD, зависимости и пути. Соответствие: M0 → TASK-001, M1 → TASK-002, M2 → TASK-003, M3 → TASK-004, M4 → TASK-005, M5 → TASK-006. Полный план с обоснованием — `docs/plan-changeset-workspace-mvp.md`.

## Риски и ограничения

- **TD-031** (модель промоушена не описывает multi-image продукт) закрывается в M5 отдельным ADR; до него живой прогон `release` не заявляется.
- **M0** — не новая функциональность, а предусловие: дефекты, найденные живым пилотом T043 (B1, B2, TD-030); без них демонстрация упрётся в гейты.
- Риск расхождения CLI и Console снят серверным `Guidance`; риск «красивого, но пустого» интерфейса — правилом «каждый экран закрывается рабочим API».
