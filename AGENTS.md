# AGENTS.md

Руководство для ИИ-агентов, работающих в этом репозитории. Файл автоматически читается агентом Zed (и другими агентными инструментами) в начале каждой сессии. Здесь только правила, которые обязан соблюдать каждый агент. Кратко и по делу.

## Что это за проект

**Software Dark Factory** — MVP «тёмной фабрики» разработки ПО: конвейер, в котором специализированные агенты-роли (аналитик → архитектор → инженер → DevOps) превращают задачу в работающий, протестированный и задокументированный код с минимальным участием человека.

- Статус: pre-MVP, каркас кода и базовый CI готовы (T-002); архитектурные решения приняты (ADR-001…ADR-019).
- Стек: Python (модульный монолит), PydanticAI за `HarnessPort`, pydantic-graph внутри стадии, FastAPI, PostgreSQL как state store, React + Radix/shadcn для Console, локальный Kubernetes + Helm + Argo CD — см. ADR-002, ADR-004, ADR-005, ADR-010, ADR-014. Изменение стека — только новым ADR.
- Язык: документация и общение с пользователем — русский; код, идентификаторы, коммиты — английский.

## Роли (скиллы)

| Скилл | Назначение | Продукт работы |
|---|---|---|
| `dark-factory` (локальный, `.agents/skills/`) | Оркестратор конвейера: классификация задач, план, координация, приёмка | План работ, отчёт |
| `speckit-*` (локальные, `.agents/skills/speckit-*`) | SDD-слой bootstrap-фазы (ADR-001, действует до T-020): constitution, specify, clarify, plan, tasks, analyze, implement, converge | `.specify/`, `specs/<фича>/` |
| `analyst` | Продуктовое видение, скоуп MVP, приоритизация | `docs/vision-<дата>-<версия>.md`, `docs/plan.md` |
| `software-architect` | Архитектура, ADR, техдолг, health score | `docs/architecture*.md`, `docs/adr/ADR-NNN-*.md`, `docs/tech-dept.md` |
| `software-engineer` | Реализация: код, тесты, рефакторинг | Изменения в коде |
| `devops` | CI/CD, деплой, инфраструктура, секреты, git-цикл задачи (ветка, коммиты, MR) | Конфиги CI/CD, IaC, ветка и MR задачи |
| `yandex-cloud-engineer` | Инфраструктура Yandex Cloud (только этот провайдер) | HLD/ADR, Terraform |

Глобальные скиллы лежат в `~/.agents/skills/<имя>/SKILL.md` — при активации читать их целиком.

## Конвейер (как решаются задачи)

1. **Вход**: задача от пользователя.
2. **Оркестрация** (`dark-factory`): классифицировать задачу, определить последовательность ролей, зафиксировать план.
3. **Продукт** (`analyst`): для задач без чёткого ТЗ — сначала видение и план.
4. **Архитектура** (`software-architect`): для значимых решений — ADR до кода.
5. **Ветка задачи** (`devops`): до реализации создать от актуального `main` рабочую ветку `feat/t-<NNN>-<slug>` и запушить её.
6. **Реализация** (`software-engineer`): код по существующим паттернам, SOLID/DRY/KISS/YAGNI, минимум лишнего — в ветке задачи.
7. **Проверка**: диагностика, тесты, lint/typecheck по изменённым файлам фактически запущены и зелёные; CI повторяет их на MR.
8. **MR** (`devops`): после зелёной проверки закоммитить (Conventional Commits), запушить ветку и открыть MR против `main` с evidence.
9. **Merge — человек** (ADR-011): агенты MR не мержат.
10. **Приёмка**: проверка DoD (см. ниже) и краткий отчёт пользователю.

Git-цикл задачи обязателен для любой задачи с изменениями кода и детализирован в `docs/development-workflow.md`. Роль `devops` дополнительно подключается, когда задаче нужны CI/CD, деплой или секреты.

SDD-слой для фич. Каноническая модель — **OpenSpec** (ADR-017): профили `factory-sdd` (изменения самой фабрики) и `product-sdd` (изменения продуктов); артефакты — `openspec/changes/<change-id>/`, действующие требования — `openspec/specs/`.

До контрольной точки **T-020** действует bootstrap-фаза на Spec Kit (ADR-001): `/speckit-constitution` — один раз на проект, затем `/speckit-specify` → `/speckit-clarify` (опц.) → `/speckit-plan` → `/speckit-checklist` (опц.) → `/speckit-tasks` → `/speckit-analyze` (опц.) → `/speckit-implement` → `/speckit-converge`; артефакты — `specs/<фича>/`. После T-020 новые изменения создаются только в OpenSpec; `.specify/` и `specs/<фича>/` сохраняются как bootstrap evidence и немедленно не переписываются.

Два параллельных SDD-процесса не допускаются: в каждый момент действует ровно один канонический формат. Оркестратор выбирает строгость под тип задачи: быстрому fix SDD-артефакты не нужны.

## Жёсткие правила

- Сначала читай `docs/` — там контекст проекта. Не переспрашивай то, что уже задокументировано.
- Значимые технические решения — только через ADR в `docs/adr/` (шаблон: `docs/adr/ADR-000-template.md`).
- Не менять стек, зависимости и структуру репозитория без ADR или явного согласования.
- Каждое изменение кода валидировать: тесты (если есть) + диагностика. Не заявлять о пройденной проверке, если она фактически не запускалась.
- Коммиты: Conventional Commits (`feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`) на английском.
- Git-цикл задачи — штатная часть конвейера (см. выше): `devops` создаёт ветку до реализации и открывает MR после зелёной проверки. Коммиты и пуши — только в ветку задачи; push в `main` запрещён, merge в `main` — только человек (ADR-011). Вне этого цикла коммитить и пушить без явной просьбы пользователя нельзя.
- Ветки задачи: `feat/t-<NNN>-<slug>`, `fix/t-<NNN>-<slug>`, `chore|docs|refactor|test/t-<NNN>-<slug>`; `main` — всегда стабильный.
- Секреты и ключи — никогда в коде и в git; только через механизм секретов (env, хранилище).
- Не чинить попутно несвязанные баги; упомянуть их в финальном сообщении.
- Не трогать файлы и изменения, созданные не тобой, без запроса.

```
│   └── vision-*.md, plan.md   # создаются скиллом analyst

│   └── changes/<change-id>/   # артефакты изменения

```

## Definition of Done

- [ ] Требования задачи выполнены; побочных изменений нет
- [ ] Работа велась в отдельной ветке задачи (создана ролью `devops` до реализации)
- [ ] Диагностика по изменённым файлам чистая
- [ ] Тесты (если применимо) запущены и зелёные
- [ ] Документация и ADR обновлены
- [ ] MR против `main` открыт ролью `devops` с evidence; merge не выполнен — решение человека (ADR-011)
- [ ] Пользователю дан краткий отчёт: что изменено, что проверено, что осталось

## Интеграции

- MCP-серверы подключаются через `.zed/context_servers.json` (создать при необходимости; не выдумывать серверы, которых нет).
- SDD: канонический формат — OpenSpec (ADR-017). Spec Kit — CLI `specify` v1.0.6 (установлен через `uv tool`), используется в bootstrap-фазе до T-020 (ADR-001).
- CI/CD: не настроено (pre-MVP). Настроить через скилл `devops`, когда появится код.
